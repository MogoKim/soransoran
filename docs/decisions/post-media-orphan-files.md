# 글에서 빠진 사진을 지울 것인가 — 1차 보류

작성: 2026-09-02 · 대상: 글쓰기 미디어 1차 MVP(사진 · 유튜브)

## 결론

**1차에서는 지우지 않는다.** 무엇이 빠졌는지 셀 수 있게만 해 두고, 실제 삭제는 하지 않는다.

- 만든 것: `src/lib/post-media.ts` — `extractImageUrls` · `extractOwnImageKeys` · `removedImageKeys`
- 만들었지만 **부르지 않는 것**: `src/lib/r2.ts` 의 `deleteFromR2`
- 글 수정·삭제 경로 어디에서도 R2 오브젝트를 지우지 않는다

## 왜 보류하는가

### 1. "이 글에서 빠졌다" 는 "아무 데서도 안 쓴다" 가 아니다

`removedImageKeys(before, after)` 가 내는 것은 **그 글 하나** 의 앞뒤 차이다.
같은 사진 주소가 다른 글에 붙어 있을 수 있다.

- 사람이 자기 글을 복사해 다른 게시판에 다시 올린다
- 운영자가 신고 글의 본문을 다른 글로 옮긴다(어드민 본문 수정에서 실제로 하는 일이다)

참조를 세지 않고 지우면 **살아 있는 글의 사진이 깨진다.** 그것도 조용히 —
지운 쪽은 성공했고, 깨진 쪽은 아무도 보고 있지 않다가 나중에 발견된다.

### 2. 되돌릴 수 없다

R2 오브젝트 삭제에는 휴지통이 없다. 잘못 지우면 원본이 사라진다.
소란소란의 다른 삭제는 전부 soft 다 — 글은 `status='HIDDEN'`, 댓글은 `isDeleted=true`.
"지우지 않는다" 가 이 서비스의 기본값인데, 파일만 hard delete 를 먼저 여는 것은 앞뒤가 맞지 않는다.

### 3. 지금 규모에서 급하지 않다

글 26 건, 사진 0 장에서 시작한다. 사진 한 장은 WebP 1200px 로 줄여 대개 100~300KB 다.
쌓이는 속도보다 참조 계산을 제대로 만드는 편이 싸다.

### 4. 우나어의 결함을 "다르게" 물려받지 않기 위해

우나어는 글을 지울 때 `thumbnailUrl` **한 장만** R2 에서 지운다
(`src/lib/actions/posts.ts:292`, `admin.content.ts:157·260`).
본문 안의 나머지 사진·동영상은 그대로 남는다 — 50MB 짜리 동영상까지.

그 반대편 실수, 즉 **참조를 세지 않고 지워서 살아 있는 글을 깨뜨리는 것**은
용량이 남는 것보다 나쁘다. 둘 다 피하려면 세는 것이 먼저다.

## 열려면 무엇이 필요한가

순서대로 갖춰지면 그때 연다.

1. **참조 조회** — 특정 R2 key 를 본문에 쓰고 있는 Post 를 세는 쿼리.
   `Post.content LIKE '%key%'` 는 26 건에서는 되지만 늘어나면 못 쓴다.
   본문에서 뽑은 key 를 따로 담는 테이블(`PostImage`)이 있어야 한다.
2. **유예** — 지우기로 판정한 뒤 바로 지우지 않고 N 일 뒤에 지운다.
   글 수정을 되돌리는 사람이 있고, 되돌린 자리에 사진이 없으면 안 된다.
3. **감사 기록** — 무엇을 언제 왜 지웠는지. 없으면 사고가 났을 때 설명할 수 없다.
4. **삭제 경로의 단일화** — 지금 R2 를 건드릴 수 있는 자리가 업로드 하나뿐이라는 것이
   이 보류의 안전장치다. 지우는 자리가 여럿 생기면 그 전에 한 곳으로 모아야 한다.

## 그때까지 무엇을 하는가

**아무것도 하지 않는다.** 용량이 문제가 되면 그때 위 1~4 를 갖춘다.
지금 부분적으로 열어 두는 것(예: "글 삭제 때만 지운다")이 가장 나쁘다 —
반쯤 도는 정리는 무엇이 남아 있는지도 알 수 없게 만든다.
