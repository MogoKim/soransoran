## 1. Codex / Claude의 역할

- **단순 구현자가 아니다.** 소란소란 운영 마스터 기준을 따르는 판단 주체다.
- 우선순위는 **North Star → 검색 성장 → 신뢰 → 정체성 → 자동화 통제** 순이다.
- **우나어의 코드·정책을 그대로 복붙하지 않는다.** 가져올 것은 §11 표에 명시된 것뿐이다.
- 사용자가 요청하더라도 **D-day 기준(§4·§5)과 충돌하면 먼저 경고한다.**
  요청을 거부하라는 뜻이 아니라, **충돌 사실과 위험을 먼저 말하고 판단을 구한다**는 뜻이다.
- 확신이 없으면 실행하지 않고 **read-only 진단 → 보고 → 승인** 순서를 지킨다.
- 추측과 사실을 분리해 보고한다. 실측하지 않은 것을 확정으로 쓰지 않는다.

> 우나어에서 반복된 실패: `grep` 결과를 확인 없이 집계해 잘못된 결론을 낸 사례가 여러 건 있었다.
> **집계 전에 라인 출력으로 맥락을 확인한다. 숫자와 목록은 반드시 일치시킨다.**

## 2. 서비스 목적 / North Star

```
North Star   주간 재방문 참여 유저 수
             (최근 7일 재방문 + 글/댓글 1회 이상 고유 사용자)
```

| 항목 | 값 |
|---|---|
| 서비스 본질 | 40대 중반~60대 초반 여성 커뮤니티 |
| 핵심 타겟 | **50대 여성** |
| 2순위 | 40대 후반 여성 |
| 3순위 | 60대 초반 여성 |
| 성공 상태 | "나만 이런 게 아니구나"를 느끼고 **반복 방문**하며 글·댓글을 남긴다 |

### 검색 성장이 왜 North Star에 종속되는가

커뮤니티는 광고비만으로 키우기 어렵다. **검색 유입이 계속 들어오고, 그 유입이 글·댓글·재방문으로 전환**되어야 살아난다.
따라서 SEO는 부가 기능이 아니라 **핵심 성장 엔진**이다.

### 순서가 중요하다

```
❌ 커뮤니티를 활발해 보이게 만들고 → 검색 신뢰를 기대한다
✅ 정체성 있는 매거진으로 검색 신뢰를 먼저 만들고 → 사람이 오면 커뮤니티가 산다
```

우나어는 앞의 순서로 갔다. 결과는 §11 표의 "버릴 것" 목록이다.

## 4. D-day 운영 원칙

상세는 `m3-new-brand-readiness.md` §13-2. 아래는 요약이다.

### D+0 ~ D+7 — 정체성 각인

| 구분 | 내용 |
|---|---|
| 켜는 것 | 매거진 발행 1경로 (사람 검수 후 승인 발행) · **실제 회원 글쓰기·댓글** · GitHub Actions 1개 |
| 끄는 것 | ~~커뮤니티 글·댓글 자동화 전부~~ → **봇 커뮤니티 글·댓글 자동화** · 봇 대댓글 · 봇 연결촉진 · 크롤러 · 시트 |
| 정상 OFF | **봇** 글 0건 · **봇** 댓글 0건 · 봇 로그 0건 |
| 관찰 | **실제 회원** 글·댓글 0건 — 참여 미발생. 장애가 아니며 봇으로 채우지 않는다 |
| 정상 대기 | 색인 미형성 · 방문자 없음 |
| WARN | 매거진 24h 0건 |
| FATAL | 매거진 48h 0건 · DB write 실패 |

> 🔴 **정정 (2026-08-21)**: 이전 표의 "커뮤니티 글·댓글 자동화 전부 OFF"는
> **실제 회원 참여까지 막는 것으로 읽혔다.** 정본은 **실제 유저 참여는 열고, 봇이 활발한 척하는 것은 막는다**이다.
> D-day부터 실제 회원 글쓰기·댓글은 ON이며, 게스트 글쓰기·댓글은 OFF를 권장한다.

발행량은 **일 1~2편 후보**로 두되 확정 수치가 아니다. **품질·검색 의도·사람 검수를 우선**한다.
**좋은 글이 없으면 내지 않는 것이 정상이다.**

> 🔴 **D+7에 성패를 판정하지 않는다.** 새 도메인은 검색 신뢰를 쌓는 데 수 주가 걸린다.

### D+8 ~ D+30 — 소수 seed

| 구분 | 내용 |
|---|---|
| 켜는 것 | 매거진 + `user-post-wave`(실회원 글에만 반응) · GitHub Actions 2개 |
| 끄는 것 | `comment-activator` · `reply-chain-driver` · `connection-facilitator` · humor · popular · sheet · job · crawler |
| 정상 대기 | `user-post-wave` 0건 (실회원 글이 없으면 당연히 0) |
| WARN | 외부 스케줄러 30분 무발생 |
| FATAL | 매거진 48h 0건 · 외부 스케줄러 2h 무발생 · 전역 cap 없이 봇 ON |

### D+30 ~ D+90 — 조건부 확대

```
확대 조건 (전부 충족)
  [ ] 색인율이 제출 대비 충분히 올라왔다
  [ ] 실회원 가입이 발생했다
  [ ] 실회원 글 또는 댓글이 1건 이상 있다
  [ ] noindex 대상이 0건이다
  [ ] 봇 글·댓글 절대 cap이 코드 상수로 있다
  [ ] heartbeat가 가동 중이다

정상   조건이 안 되면 확대하지 않고 그대로 두는 것
FATAL  조건 미충족인데 자동화를 늘리는 것
```

### D+90 이후 — 판정

**유지 / 병렬 지속 / 소란소란 집중 / 우나어 종결** 중 하나를 결정한다.
확대하더라도 **실행 계층 3개 초과 금지 · launchd 금지**는 유지한다.

## 5. 자동화 ON/OFF 원칙

```
🔴 D+0~D+7 커뮤니티 자동화 전면 OFF
🔴 D+0~D+7 매거진 중심 · 사람 검수 후 발행
🔴 D+30 전 comment-activator / reply-chain-driver / connection-facilitator 기본 OFF
🔴 launchd 금지 (로컬 머신 의존 + 침묵 실패)
🟡 cron-job.org 는 heartbeat · 문서화 · ON/OFF 기준 없이는 금지
🟢 GitHub Actions 는 1~2개부터 시작 · concurrency 필수
🟡 manual scripts 는 사람 판단과 실행 로그가 있을 때만 허용
🟡 user-post-wave 는 D+8 이후, 실회원 글이 있을 때만 조건부
```

### 🔴 "활발한 척" 금지

```
D+30 전에 커뮤니티가 활발해 보이게 만드는 모든 자동화를 금지한다.
  대량 댓글 · 대댓글 체인 · 인기글 조작성 노출 · 봇 글 대량 발행
```

**사람이 안 오면 봇을 늘리지 않는다. 유입·참여 원인을 다시 본다.**
우나어는 반대로 했고, 봇 댓글을 대량 운영한 기간에 실회원 반응은 매우 낮았다.
**봇 증량이 참여 증가로 이어졌다는 증거는 확인되지 않았다.**

### 절대 cap이 비율보다 우선한다

초기에는 **사람 글이 0이면 어떤 비율도 의미가 없다.**

```
BOT_POST_DAILY_TOTAL      하루 봇 글 총량      미정 — D+8 전 확정 필요
BOT_COMMENT_DAILY_TOTAL   하루 봇 댓글 총량    미정 — D+8 전 확정 필요
BOT_COMMENT_PER_POST      글당 봇 댓글 최대    미정 — D+8 전 확정 필요
MIN_PUBLISH_LENGTH        발행 최소 분량       미정 — D+0 전 확정 필요

불변 규칙  실회원 글이 0이면 user-post-wave 도 0이다 (구조적으로 그렇게 만든다)
           cap 은 코드 상수로 잠근다. 설정값이 아니라 상수여야 한다
```

> 우나어는 파이프라인별 cap 은 있었으나 **서비스 전체 봇 글 총량 상한이 없었다.**
> 회차가 늘면 총량도 함께 늘어나는 구조였다.

## 6. BotLog / 관측성 원칙

```
✅ BotLog details 는 처음부터 JSON        평문 혼재 금지
✅ postId / commentId 추적 가능해야 한다   집계 숫자만 남기지 않는다
✅ safeBotLog fallback 필수               DB write 실패를 침묵시키지 않는다
✅ magazine publish heartbeat 필수         D-day blocker
✅ 자동화 ON/OFF 상태 SSoT 필수            D-day blocker
🟡 itemCount 0 은 정상/장애를 구분해야 한다  queue empty(정상) ↔ 실행 실패(장애)
🟡 skipReason 은 D+30 전후 고도화 후보
```

### 상태 SSoT 의 정의

D-day 필수는 **화면이 아니라 SSoT(단일 진실의 원천)** 다.

```
최소 요건    문서 · 설정파일 · 리포트 중 하나로
             "지금 무엇이 켜져 있는지"를 확인할 수 있으면 된다
어드민 화면   D+7 또는 D+30 구현 후보. SSoT 를 보여주는 UI 구현체이지 SSoT 자체가 아니다
```

> 우나어에는 부분 heartbeat 가 2개 있다(`crawler-health` 24h 무실행 감지 · `qa-verifier` 기대 실행 목록 대조).
> **패턴은 가져가되 커버리지를 write 전 경로로 넓힌다.**

## 7. 콘텐츠 / SEO 원칙

```
✅ 매거진이 D-day 핵심이다
✅ 품질 · 검색 의도 · 사람 검수를 우선한다
🔴 MIN_PUBLISH_LENGTH 는 D+0 전 확정 필요
🚫 짧은 글 대량 발행 금지
🚫 sitemap 에 넣을 수 없는 글은 만들지 않는다
🚫 noindex 될 글을 대량 생산하지 않는다
🚫 HUMOR 성격 / 범용 STORY 대량 자동화 금지
🚫 Googlebot 전용 복잡 noindex 구조 금지
✅ canonical · sitemap · board registry 는 한 기준으로 유지한다
```

### 핵심 원칙 — 게이트를 발행 단계에 둔다

```
❌ 우나어   많이 만들고 → 나중에 noindex 로 가린다
✅ 소란소란  기준 미달이면 → 애초에 발행하지 않는다
```

우나어는 이 순서 때문에 색인 후보의 절반이 noindex 대상이 됐고, 기준을 네 번 고쳤다.

### canonical / sitemap 규칙

```
✅ canonical 은 SSoT 1곳에서 생성한다. 도메인 문자열 하드코딩 금지
✅ metadataBase 단일 선언 + 라우트별 상대경로 canonical
✅ 보드 매핑은 registry 1파일 (누락 시 컴파일 에러가 나게 잠근다)
✅ 기준 미달 허브는 noindex + sitemap 제외
🚫 검색 결과 페이지를 sitemap 에 넣지 않는다
🚫 콘텐츠 없는 조합 랜딩(지역 × 카테고리 등) 생성 금지
```

```
🚫 block 을 저장만 하고 필터에 쓰지 않는 구조 금지
✅ 댓글 신고 UI 연결 확인 필요
🚫 이용자가 보호받는다고 믿는데 실제로는 보호되지 않는 상태 금지
```

### 왜 이것이 중요한가

우나어는 `UserBlock` 을 저장만 하고 **어떤 쿼리도 필터로 쓰지 않는다.**
차단해도 그 사람의 글과 댓글이 그대로 보인다. **미구현보다 나쁘다 — 사용자가 보호받는다고 믿기 때문이다.**

소란소란은 사람이 적다. **한 명의 악성 이용자가 미치는 영향이 크고, 피해자는 조용히 떠난다.**

### 방어 최소선

```
✅ 로그인 체크 · 사유 화이트리스트 · 중복 신고 방어 · 자기 신고 방어
🟡 rate limit (D+7 이후)
🟡 신고 누적 시 임시 숨김 (D+30 이후)
```

## 10. 인프라 / 실행 계층 원칙

```
🔴 실행 계층 3개 초과 금지
🚫 launchd 금지 (별도 승인 시에만)
🟡 cron-job.org 조건부 — 아래 5개 전부 충족 시
🚫 임의 스크립트 실행 workflow 금지
🚫 workflow_dispatch 남발 금지
🚫 concurrency 없는 workflow 금지
```

### 모든 자동 실행에 4가지가 있어야 한다

```
① 소유자    누가 책임지는가
② 목적      무엇을 위해 도는가
③ ON/OFF    어디서 끄는가 (한 곳이어야 한다)
④ heartbeat 안 돌면 누가 아는가
```

### cron-job.org 사용 조건 (전부 충족)

```
[ ] 잡 목록이 repo 문서에 고정되어 있다
[ ] 토큰 이름 · 권한 · 대상 repo 가 문서화되어 있다
[ ] 대상 workflow 가 명확하다
[ ] heartbeat 또는 침묵 실패 감지가 있다
[ ] ON/OFF 통제 위치가 명확하다
```

⚠️ **cron-job.org 자체는 금지가 아니다.** GitHub schedule 단독은 실측상 커버리지가 매우 낮아 외부 스케줄러가 현실적 주 경로다.
금지되는 것은 **문서화되지 않은 외부 스케줄러 의존**이다.

### 토큰 원칙

```
✅ repo 단일 접근 · 최소 권한 · 이름에 용도 명시 (예: soran-cafe-wave-dispatch)
🚫 모호한 이름 금지 — 나중에 무엇을 부르는지 역추적하게 된다
🟡 만료일은 신중히 — 여러 잡에 흩어진 토큰에 만료를 걸면 하나씩 조용히 죽는다
```

## 13. 작업 시작 체크리스트

**소란소란 작업을 시작하는 모든 세션이 먼저 확인한다.**

```
[ ] 현재 repo 와 branch 는 무엇인가
[ ] git status --short --branch — 추적 파일 수정 / untracked 확인
[ ] origin/main 최신 커밋은 무엇인가
[ ] 지금 작업 대상이 우나어인가 소란소란인가   ← 가장 중요
[ ] 현재 D-day 구간은 어디인가 (D+0~7 / D+8~30 / D+30~90 / D+90~)
[ ] 자동화 ON/OFF 상태는 어떤가 (상태 SSoT 확인)
[ ] 건드릴 DB · env · workflow 대상은 무엇인가
[ ] §12 금지 작업에 해당하는가
[ ] 관련 문서를 읽었는가
      m3-new-brand-readiness.md §3 (병렬 운영) · §13 (D-day 운영 기준)
      cron-job-dispatcher-ops.md (외부 스케줄러)
      본 문서
```

⚠️ **"작업 대상이 우나어인가 소란소란인가"** 를 확인하지 않고 시작하면 정책이 섞인다.
병렬 운영 기간에는 이 확인이 매 세션 필수다.
