# Raw 공급망 설계 (PR-S2 · 2026-09-03)

> **이 문서의 역할**: 원문 공급 경로의 **레인 분리 · 상한 · 실행 환경 · 확장 검토**의 단일 지도.
> 상위: [자동화 전환 정본 §7](2026-09-03-controlled-activity-automation-strategy.md) ·
> [헌법 §6-9-F · §12-2](../constitution/MICRO_SEED_LANE_CONSTITUTION.md)
>
> 🔴 **이 문서가 여는 것은 공급뿐이다.** 공개 발행 · 댓글 · reaction · best 는 이 문서 밖이다.

---

## §0 🔴 한 문장

**원문 재고 15건이 전체 속도의 1위 병목이었고, 그 원인은 크롤 속도가 아니라
"적재기가 Micro Seed 승인 게이트와 묶여 있어서 한 번에 1건밖에 못 넣는 것" 이었다.**

---

## §1 병목의 실제 모양

```
MicroSeedRawContent   15건   (82cook 14 · navercafe:remonterrace 1)
초안 생성 누적        48건   ← 원문 15건을 여러 번 갈았다
```

### 🔴 진짜 원인은 크롤이 아니라 적재 경로였다

기존 importer 는 한 건을 넣을 때마다 **세 곳**에 쓴다.

```
MicroSeedRawContent  +  MicroSeedCandidate  +  Google Sheet 행 1개
                                               ↑ 창업자가 읽는 승인 게이트
```

그래서 `--apply --limit=1` 이 하드 요구였다. **그 제약은 옳다** —
Sheet 에 한 번에 50행이 꽂히면 그 화면은 게이트로서 기능하지 않는다.

**그런데 Original Post 레인은 Sheet 를 쓰지 않는다.**

```
original-post-generate.mts:139
  prisma.microSeedRawContent.findMany({ select: { id, rawTitle, rawBody, sourceSite, sourceCapturedAt } })
```

승인은 `OriginalPostApprovalQueue` 에서 따로 받는다.
**즉 그 레인에 `MicroSeedCandidate` 행도 Sheet 행도 아무 역할이 없다.**

한 importer 가 두 레인을 같은 문으로 통과시키느라, **재료만 필요한 쪽까지 승인 게이트 상한을 쓰고 있었다.**

## §2 해법 — 문을 두 개로 나눈다

| | **Micro Seed 레인** | **Original Post 공급** |
|---|---|---|
| 명령 | `--apply --limit=1` | `--apply --raw-only --batch=N` |
| RawContent | ✅ | ✅ |
| `MicroSeedCandidate` | ✅ HOLD | 🔴 **만들지 않는다** |
| Google Sheet | ✅ 행 1개 | 🔴 **읽지도 않는다** |
| 예약 제안 | ✅ | 해당 없음 |
| 한 실행 상한 | **1건** | **50건** |
| 승인 주체 | 창업자 · Sheet | `OriginalPostApprovalQueue` (별도) |

### 🔴 Sheet 를 "쓰지 않는다" 가 아니라 "읽지도 않는다"

읽기만 해도 자격 증명이 필요하고, **그 경로가 살아 있으면 언젠가 쓰기로 이어진다.**
레인을 나눈 이유가 사라진다. raw-only 는 `createGoogleSheetSource` 를 아예 부르지 않는다.

### 🔴 두 스위치 원칙은 그대로다

```
--apply 만                    → dry-run
--raw-only 만                 → dry-run
--apply --raw-only (batch 없음) → dry-run
--apply --raw-only --batch=30 → 🔴 적재
```

### 🔴 섞은 명령은 거부한다

```
--batch 단독            🛑 Micro Seed 레인은 배치를 열지 않는다
--raw-only --limit=1    🛑 두 레인의 상한을 같은 이름으로 부르지 않는다
--batch=51              🛑 상한 초과
```

**모호한 명령을 통과시키면 Sheet 에 50행이 꽂히는 사고가 오타 하나로 난다.**
판정은 `scripts/lib/micro-seed-supply.mts` 의 순수 함수가 하고 fixture 가 96가지 조합을 전수 검증한다.

## §3 자동 선별 (`collect --auto`)

기존에는 목록을 사람이 보고 `--fetch=<id,id>` 로 골랐다. 300/day 에는 맞지 않는다.

```
--list --pages=3 --auto --live
   목록 3p 수집 → 선별 점수 계산 → 상위 N건 자동으로 상세 열기
```

| 상수 | 값 | 근거 |
|---|---|---|
| `AUTO_FETCH_MAX` | **30** | 요청 간격 2초 고정 → 상세만 60초. 한 실행 ~1분 30초 |
| `AUTO_MIN_SCORE` | **20** | 여는 순서와 범위만 정한다 |
| `AUTO_SKIP_LIST_FLAGS` | `politicalOrPublicFigure` · `politicalTopicLikely` | ① 목록 단계 — **열기 전** |
| `AUTO_HOLD_DETAIL_FLAGS` | `medicalOrAdLikely` · `publicFigureMention` | ② 상세 단계 — **연 뒤, 적재 전** |

### 🔴 자동 제외는 **두 단계**다 (2026-09-03 실측 정정 · PR-S2-a)

초판은 하나였다: `AUTO_SKIP_FLAGS = ['politicalOrPublicFigure', 'medicalOrAdLikely']`.
**그런데 자동 선별은 목록 단계에서 일어난다.** 목록에는 제목과 댓글수뿐이다.

`medicalOrAdLikely` 는 (시설|시술) **AND** 가격, 또는 상업유도 조합을 요구한다.
제목만으로 그 조합이 성립하는 일은 사실상 없어 **목록 단계에서 한 번도 붙지 않았다.**

**첫 live 수집(2026-09-03 · 10건) 실측**

| 글 | 목록 단계 플래그 | 결과 |
|---|---|---|
| 4234890 `불안으로 정신과약 드셔본 분 계신가요` | `highEngagement` 뿐 | 🔴 자동 수집 통과 |
| 4234897 `뇌MRI 사진에서 치매 및 어지럼증…` | `highEngagement` 뿐 | 🔴 자동 수집 통과 |
| 4234894 `나라별 극우의 특징` | `highEngagement` 뿐 | 🔴 자동 수집 통과 |

> 🔴 **"목록에 적힌 이름" 과 "그 단계에서 실제로 붙는 플래그" 는 다르다.**
> 이름만 적어 두면 가드가 있는 것처럼 보이지만 아무것도 막지 않는다 —
> `noGoTopics` 0/28 히트와 같은 종류의 실패다.

**정정 후**

```
① 목록 단계 제외 (열기 전)     politicalOrPublicFigure · politicalTopicLikely
      → 상세를 아예 열지 않는다. 82cook 요청도 발생하지 않는다

② 상세 단계 보류 (연 뒤, 적재 전)  medicalOrAdLikely · publicFigureMention
      → 상세 JSONL 에는 남는다. raw-only **자동 적재 대상에서만** 뺀다
```

### 🔴 재발 방지 — 이름이 아니라 **발화 증명**을 요구한다

fixture 가 `AUTO_SKIP_LIST_FLAGS` 의 각 플래그에 대해 두 가지를 검사한다.

```
① DETAIL_ONLY_FLAGS 에 없는가              (이름 검사)
② 🔴 제목 하나만 주고 실제로 발화하는가     (발화 증명)
```

②가 핵심이다. `medicalOrAdLikely` 는 ①은 통과하지만 ②를 통과하지 못한다 —
그래서 목록 단계 목록에 둘 수 없다. **이 검사가 있으면 같은 실패가 다시 들어올 수 없다.**

### 🔴 정치 주제는 공인·실명과 **다른 축**이다

`politicalOrPublicFigure` 는 **누가 언급됐는가**를 본다(POLITICS 어휘 · 한자 성 · 직함+이름).
그래서 `나라별 극우의 특징` 을 놓쳤다 — 사람 이름도 직함도 없고 **주제만 정치**인 글이다.

```
politicalTopicLikely   극우·극좌·좌파·우파·수구·빨갱이·좌빨·친일파·토착왜구·개딸·
                       태극기 부대·진영 논리·정치 성향·이념 갈등·정치 글
```

🔴 **최소 어휘로 시작한다. 과차단이 더 나쁘다.**
`보수`(보수공사) · `진보`(진보하다) · `시위` · `집회` · `노조` · `파업` 은 넣지 않았다 —
생활글에서 정상적으로 쓰인다. fixture 가 그 6종을 과차단 회귀로 잡는다.

### 🔴 자동 경로와 수동 경로는 다르다

| | 자동 (`--auto` · raw-only 적재) | 수동 (`--fetch=<id>` · `--sourceArticleId=<id>`) |
|---|---|---|
| 목록 단계 제외 | ✅ 적용 | 🚫 미적용 — 지정하면 열린다 |
| 상세 단계 보류 | ✅ 적용 | 🚫 미적용 — `humanDesignated` |
| 근거 | **경로에 사람이 없다** | 사람이 이미 판단했다 |

> `--sourceArticleId=<id>` 는 "이 글을 넣겠다" 는 명시적 판단이고, **코드가 그 판단을 뒤집지 않는다.**

### 🔴 Raw Vault 저장 정책과 Originality Gate 정책을 혼동하지 않는다

```
Raw Vault 저장   발행이 아니다. 원자료 보관이다
Originality Gate 발행 자격을 본다
자동 원료 공급   🔴 위 둘과 또 다르다 — 여기서만 더 보수적으로 간다
```

자동으로 들어온 원문은 **자동으로 생성기의 재료**가 되고, 그 경로에 사람이 없다.
그래서 Vault 저장 자체를 금지하는 것이 아니라 **자동 적재에서만** 뺀다.
보류된 글도 상세 JSONL 에 그대로 있고, 사람이 지목하면 들어간다.

### 🔴 이것은 30건 슬롯 확대 전용 안전장치다

10건에서 2건(20%)이 의료·광고성이었다. **30건으로 올리면 그대로 3배가 된다.**
슬롯 확대는 이 가드가 붙은 뒤에만 한다.

### 🔴 그래도 Q-1 의 예외가 아니다

정책 Q-1 은 *"품질 플래그로 후보를 거부하지 않는다"* 이다. 이것은 유지된다.

```
🟢 목록 JSONL 에는 전부 남는다
🟢 --fetch=<id> 로 지정하면 언제든 열린다
🔴 자동 경로에서만 뺀다
```

**구분이 중요한 이유: 자동 경로에는 사람이 없다.**
사람이 고를 때는 정치·실명 글을 보고 넘기면 된다. 자동은 넘길 눈이 없고,
그 글이 그대로 Raw Vault 에 들어가 생성기의 재료가 된다.

### 🔴 자동 선별분도 robots 를 다시 본다

대상이 **목록을 받은 뒤에** 정해지므로 사전 robots 검사에 없었다.
`--auto` 경로에서 한 번 더 검사한다 — 건너뛰면 `--auto` 만 robots 밖으로 나가는 구멍이 생긴다.

### 🔴 Vault 대조는 collector 가 하지 않는다

collector 는 `prisma` 를 import 하지 않는다(파일 상단 계약). 그 계약을 깨면
"수집기가 DB 를 만지지 못한다" 는 보장이 사라진다.
중복 적재는 importer 가 `@@unique([sourceSite, sourceArticleId])` 로 막는다 —
여기서 걸러지지 않아 생기는 비용은 82cook 요청 몇 건뿐이다.

### 🔴 자동 제외는 **영구 삭제가 아니다** — 네 갈래로 나눈다 (2026-09-03 전략 싱크)

"제외" 를 한 단어로 쓰면 코드가 **삭제**로 수렴한다. 생활 Original 레인에서 뺀 원문이
다른 레인에서는 자산일 수 있다 — **연예 · 방송 · 셀럽 이슈**가 그렇다(§4-C).

🔴 **정치 · 진영은 여기에 해당하지 않는다.** 그쪽은 갈 레인이 없다 — 그냥 제외다(§4-C).

| 갈래 | 뜻 | 원자료 |
|---|---|---|
| 🟢 **적재** | 생활 Original 레인 재료로 쓴다 | Raw Vault |
| 🟡 **보류(HOLD)** | 자동으로는 안 넣는다. 사람이 `--sourceArticleId` 로 지목하면 들어간다 | JSONL 에 남는다 |
| 🟣 **shadow** | 공개 발행 재료로 바로 쓰지 않는다. 학습 · 관찰용 (예: `yeowooya` 뷰티 축) | JSONL 에 남는다 |
| 🔵 **growth 후보** | 🔴 **연예 · 방송 · 셀럽 한정.** 생활 레인엔 안 맞지만 유입 자산일 수 있다 (§4-C) | JSONL 에 남는다 |
| 🚫 **제외** | 🔴 **정치 · 진영 · 이념 · 정치인 · 공직자.** 갈 레인이 없다 (§4-C) | JSONL 에 남지만 어디에도 안 간다 |

```
🚫 "연예 글은 쓸모없다"              → 유입 자산을 스스로 버린다
🟢 "생활 Original 레인에는 안 맞다"   → 레인이 다른 것이지 가치가 없는 게 아니다
🔴 그래도 **섞지 않는다**             → 같은 레인에 넣는 순간 정체성이 무너진다

🔴 정치 · 진영은 예외다               → 다른 레인도 없다. 유입이 좋아도 가져가지 않는다
```

> 🔴 **지금 코드가 하는 일은 보류까지다.** shadow · growth 갈래는 **전략으로만 적어 둔다** —
> 분류기도 cap 도 감사 경로도 없다. 없는 것을 있는 것처럼 쓰면 다음 사람이 그걸 믿고 짠다.

## §4 300/day 를 채우는 방법 — 상한이 아니라 슬롯

```
❌ AUTO_FETCH_MAX 를 300 으로   → 한 번의 실수가 300건이 된다
🟢 30건 × 하루 10슬롯          → 실수의 크기는 30건에 머문다
```

| 항목 | 값 |
|---|---|
| 수집 슬롯 | 하루 10회 (2시간 간격) |
| 슬롯당 상세 | 최대 30건 |
| 슬롯 소요 | 약 1분 30초 (2초 고정 지연) |
| 적재 배치 | 최대 50건 / 실행 |
| **일일 상한** | **300건** |

**7일이면 2,100건.** shadow 100/day 를 감당하고도 남는다.

## §4-A 🔴 82cook 과 네이버 카페는 **양대 주요 공급망**이다 (2026-09-03 · PR-S2-b-1)

**둘 중 하나가 보조가 아니다.**

| 소스 | 무엇을 공급하나 |
|---|---|
| **82cook** | 짧고 **당일성** 있는 4050·5060 커뮤니티 언어 · 자유게시판형 소재 |
| **네이버 카페** | **깊은 생활 맥락** · 다양한 실제 고민 |

### 🔴 이중화는 처리량이 아니라 가용성의 문제다

```
2026-09-03  Raw 40건 = 82cook 39 + navercafe 1     단일 소스 99%
            82cook 접속 실패 → 30건 슬롯 전면 중단 → 그날 공급 0
```

**한 소스가 막히면 공급이 0이 된다.** 네이버를 여는 진짜 이유가 이것이다.

### 카페별 성격 (경향일 뿐 — 🔴 고정 라벨이 아니다)

| 카페 | 경향 |
|---|---|
| `wgang` 우아한 갱년기 · `remonterrace` 레몬테라스 | 4050 여성 핵심 생활권. 갱년기 · 몸 변화 · 중년 여성 고민 · 가정 · 가족 · 생활이 **섞인다** |
| `dlxogns01` 은퇴 후 50년 | 노후 · 은퇴 · 돈 · 건강 · 미래 불안 비중이 높다 |
| `goondae` 군대카페 · `masanmam` 줌마렐라 | 타겟층 일상 · 가족 · 생활 **보강** |
| `yeowooya` 여우야 | 🟡 **뷰티 · 피부 · 미용 · 성형 관심사 shadow 소스**. 버리는 소스가 아니지만 **public 발행 재료로 바로 쓰지 않는다** |

### 🔴 `sourceSite` 는 운영 단위이지 주제 라벨이 아니다

```
🚫 "이 카페는 갱년기 카페"     → 그 카페의 다른 글을 잘못 읽는다
🚫                             → 다른 카페의 갱년기 글을 놓친다
🟢 주제 · 소재 판정은 **글 단위**로 한다 (qualityFlags · Originality Gate)
```

카페마다 경향은 있지만 **코드가 그것을 고정 라벨로 굳히지 않는다.**
fixture 가 `micro-seed-supply.mts` 에 주제 라벨이 들어오지 않는지 검사한다.

### 🔴 `popular-sync` 를 네이버로 이식하지 않는다

우나어는 인기글 전용 슬롯을 3회/day 돌렸다(`popular-sync.ts` · 10:30·16:00·21:15).
**소란소란은 이 개념을 82cook 수집 슬롯이 대신한다.**

```
🚫 네이버 인기글 전용 슬롯      요청 수만 늘고, 인기글은 이미 목록 선별 점수가 본다
🟢 네이버에서 가져오는 것은     run-pipeline 성격의 **Raw 수집 구조**뿐이다
```

## §4-B 🔴 `lowEngagement` 는 품질이 아니라 **page depth · time lag 의 함수**다

**2026-09-03 첫 live 실측 (remonterrace 1p)**

```
목록 22건 → lowEngagement 22/22 (100%)
자동 선별 3건 → 상세 3건 전부 댓글 0
```

이 수치를 **"레몬테라스 품질이 낮다" 또는 "전체글보기가 나쁘다" 로 읽지 않는다.**

### 왜 그렇게 읽으면 안 되는가

```
레몬테라스 · 82cook · 우갱 · 여우야 = 대형 커뮤니티
   → 시간당 수십~수백 개 글이 올라온다
   → 최신 1~3p 는 정의상 "방금 올라온 글" 이다
   → 반응이 붙을 시간이 물리적으로 없었다
```

**댓글 수 · 조회수는 글의 속성이 아니라 `page depth × time lag` 의 함수다.**
1페이지만 보고 "반응이 없다" 고 결론내는 것은, 신문 인쇄 직후에 판매부수를 세는 것과 같다.

### 🔴 우나어가 한 게시판에서 여러 페이지를 크롤한 이유가 이것이다

우나어는 카페 하나를 1p 만 훑지 않았다. **반응이 붙은 글은 뒤 페이지에 있기 때문이다.**
이 구조는 `popular-sync`(§4-A 에서 이식 금지) 와 별개다 —
인기글 **전용 슬롯**을 두는 것과, 일반 목록을 **여러 페이지 보는 것**은 다른 이야기다.

| | |
|---|---|
| 🚫 이식 안 함 | 네이버 인기글 **전용 슬롯** (`popular-sync`) — 요청만 늘고 목록 점수가 이미 본다 |
| 🟢 반영함 | **page depth 를 1 로 고정하지 않는다** — 반응 있는 글은 뒤에 있다 |

### 정하지 못한 것 (🔴 다음 조사 대상)

```
① page depth   몇 페이지까지 내려가야 댓글 있는 글이 나오는가
② time lag     글 작성 후 몇 시간이 지나야 반응이 붙는가 → 수집 시점 설계
③ quota        ①②가 정해져야 슬롯당 상한 10 이 맞는지 재산정할 수 있다
```

### 🟢 메타 수집은 열렸다 (PR-S2-b-4) — 값은 아직 정하지 않는다

목록 JSONL 이 아래를 남긴다. **DB 컬럼은 만들지 않았고 importer 는 이 키들을 읽지 않는다.**

| 키 | 뜻 |
|---|---|
| `sourceListedAt` | 목록에서 **본** 시각 — 상세를 여는 `sourceCapturedAt` 보다 앞선다 |
| `sourcePostedLabel` | 화면에 보이는 작성 시각 **문자열 원형** |
| `sourcePostedAt` | 위를 ISO 로 해석한 값 — 🔴 **확실할 때만. 애매하면 `null`** |
| `sourcePage` · `sourceRankOnPage` | 몇 페이지 · 그 안에서 몇 번째 (page depth 축) |
| `sourceViewCount` | 조회수 — 못 읽으면 `null` |
| `sourceCommentCount` · `sourceBoardName` | 기존 |

```
🔴 모르면 0 이 아니라 null 이다.
   "댓글 0개" 와 "댓글 수를 못 읽었다" 는 다른 사실이고,
   0 으로 뭉개면 lowEngagement 통계가 거짓말을 한다.
```

**이 PR 은 조사를 **가능하게만** 한다.** `--pages` 기본값 · 슬롯 시간표 · quota 는
데이터가 쌓인 뒤 별도로 정한다 — **이 문서는 값을 정하지 않는다.**

### 🔴 셀렉터는 추정하지 않는다 (PR-S2-b-6 실측 정정)

PR-S2-b-4 는 `.td_date` · `.td_view` · `.td_name` 을 **추정으로** 넣었고 셋 다
실제 DOM 에 없었다. 그 결과 메타가 22/22 전부 null 이었다. 실측으로 확정한 값:

```
tr
  td > a.board_name                    게시판명
  td > ... > a.article                 제목·링크
          > a.cmt                      댓글 수 — 🔴 0 이면 엘리먼트가 **없다**
  td.td_normal.type_date               작성시각 "HH:mm" · "YYYY.MM.DD"
  td.td_normal.type_readCount          조회수 "1,133"
```

🔴 **댓글 링크 부재 = 진짜 0** 이다. "못 읽음" 으로 보면 댓글 0 인 글이 전부
미지값이 되어 lowEngagement 통계가 반대로 망가진다 — `rowFound` 로 판정한다.

### 🔴 브라우저 콜백에 이름 있는 함수를 두지 않는다

목록 0건(PR-S2-b-4)과 메타 전량 null(PR-S2-b-5)은 **같은 원인**이었다.

```
tsx(esbuild) 의 keepNames 가 `const pick = () => {}` 에 __name(...) 을 씌운다.
그 코드가 $$eval 로 브라우저에 넘어가면 __name 헬퍼가 없어 ReferenceError 가 난다.
  → b-4: 콜백 전체가 죽어 목록 0건
  → b-5: try 가 잡아 링크는 살고 메타만 전부 null
```

셀렉터는 콜백 **밖에서 인자로** 넘기고, 안에서는 옵셔널 체이닝으로 직접 읽는다.
fixture 가 `$$eval` 본문에 이름 있는 함수가 없는지 검사한다.

### 실행 단위 분리

산출 JSONL 이 append 라 두 실행이 한 파일에 44행으로 섞였고 **null 비율을 한 번
잘못 읽었다.** 이제 실행별 파일(`navercafe-{cafe}-{runId}.jsonl`)로 나누고
행마다 `sourceRunId` 를 남긴다. `--out` 을 주면 그 경로를 쓰되 append 하지 않는다.

이것은 §4-A 의 *"`sourceSite` 는 운영 단위이지 주제 라벨이 아니다"* 와 같은 논리를
한 단계 위로 올린 것이다 — 소스는 **quota·가용성·pacing 의 단위**다.

### 🔴 기존 scout 수치는 소스 우열 확정값이 **아니다**

지금까지 나온 숫자는 전부 **scoring calibration 표본**이다.

| run | 대상 | 표본 |
|---|---|---|
| 20260903-203109 | `wgang:all` 1~5p | 81건 · 후보 75 · A 21% |
| 20260903-204007 | `remonterrace:jjong` 2~16p | 223건 · 후보 222 · A 12% |
| 20260903-190748 | `remonterrace:humor` 1p | 23건 · 후보 14 · A 7% |

🔴 **각 소스 1회씩이고 시간대도 다르다.** 쫑알쫑알만 해도 오후 2.3h → 저녁 3.1h 로
변했다. 이 숫자로 소스의 우열을 말할 수 없다 — 점수 체계를 맞추는 데 쓴다.

### scoring 초안 (🔴 구현하지 않았다 · 값도 확정하지 않았다)

**① hard exclude — 점수를 매기기 전에 뺀다**

```
🚫 정치 · 진영 · 정당 · 선거 · 정치인 · 공직자      → 어느 레인에도 안 간다 (§4-C)
🚫 공지 · 필독 · 추천                              → 자동 상세 대상 제외
🚫 명백한 광고 · 위험 소재
```

점수로 이길 수 있는 축이 아니다. **아무리 화제성이 높아도 통과하지 않는다.**

**② 화제성**

```
댓글수 · 조회수 · 댓글/조회 비율 · 작성 후 시간 대비 반응 속도
```

🔴 비율과 속도를 함께 본다. 절대 댓글수만 보면 오래된 글이 유리해진다 —
`sourceListedAt − sourcePostedAt` 이 이미 있으므로 계산할 수 있다(PR-S2-b-4).

**③ 타겟 핏**

40대 중반~60대 중반 여성이 **자기 이야기처럼** 느낄 생활 주제인가.

**④ 대화 가능성**

우리 커뮤니티에서 댓글·공감이 붙을 만한가. 조회만 높고 대화가 안 붙는 글은
Raw 로서 가치가 낮다 — North Star 가 주간 재방문 **참여** 유저 수이기 때문이다.

**⑤ 신선도 / 재방문 가치**

지금 상세로 들어갈지, **다음 scout 에서 재평가할지.**
`(sourceSite, sourceArticleId)` 를 여러 `sourceRunId` 에 걸쳐 비교한다(§4-E).

### 🔴 source normalization — 절대값을 그대로 비교하지 않는다

```
🚫 "레몬테라스 댓글 10 = 우갱 댓글 10"
🟢 각 소스 · 게시판 · run **안에서의 상대 순위**도 함께 본다
```

카페마다 회원 수·활동량·게시 속도가 다르다. 실측만 봐도 쫑알쫑알은 시간당 약 98건,
우갱은 약 14건이다. **같은 댓글 10개가 두 곳에서 같은 의미일 수 없다.**

절대 임계값 하나로만 자르면 활동량이 많은 소스가 후보를 독식하고,
그 순간 다시 **source-first** 로 되돌아간다.

### threshold A/B 의 지위 (🔴 격하)

```
A  댓글>=10 AND 조회>=300
B  댓글>=15 AND 조회>=300
```

**운영값이 아니다. scoring input 후보다.** 화제성 축 하나를 거칠게 근사한 값이고,
②~⑤ 와 normalization 이 붙으면 형태 자체가 바뀔 수 있다.
지금 코드는 이 값으로 자동 판정하지 않고 scout 가 세어서 보여주기만 한다(PR-S2-b-9).

### 유지되는 분리

```
🔴 정치 · 진영           점수 이전 hard exclude. public · growth · shadow 어디에도 안 간다
🟡 publicFigure          실명 · 공인 언급 — 생활 Original 레인에서만 뺀다

`sourceExcludeReason` 이 셋을 나눠 기록하는 이유가 이것이다(PR-S2-b-8) —
Growth 레인이 열리면 `publicFigure` 를 거기서 되살려야 한다.

### 🔴 점수 가중치 재배분 (PR-S2-b-14 · 여전히 초안)

검수 실측에서 **화제성이 실질 1위 축**이 되어 타겟 핏 0점인 연애·외모 글이 상위를 먹었다.

| 축 | before | after | 근거 |
|---|---|---|---|
| 화제성 | 45 | **35** | 획득률 72% — 단독 최대 축이 되면 안 된다 |
| 타겟 핏 | 25 | **30** | 획득률 22% (60%가 0점) — 배정만 크고 작동하지 않았다 |
| 대화 | 20 | **25** | 짧은 질문·참여글이 화제성에서 밀리는데 이 축이 유일한 살길이다 |
| 신선도 | 10 | **10** | 이미 87% 획득 — 올리면 거의 공짜 점수가 되어 변별력이 준다 |

**타겟 핏 0점 글의 정체를 눈으로 확인했더니 두 부류였다.**

> 🔴 모집단을 밝힌다: 아래 결과의 `0점 120건` 은 **상위 200 기준**이고,
> 정체를 읽어 본 표본은 그중 **상위 120위 안의 68건**이다. 두 숫자는 모집단이 다르다 —
> 같은 절에 섞어 쓰면 다음 사람이 "68 → 67 이면 하나만 고쳐진 것" 으로 잘못 읽는다.

```
① 억울하게 0점    자녀·교육 축이 아예 없었다 — 학원·숙제·고3·내신·맞벌이
                  가족에 조카·어머님·결혼·명절 없음 / 돈에 금리·축의금 없음
                  → 사전을 넓혔다. 축을 하나 신설했다(자녀·교육)
② 진짜 off-target  외모 평가 · 썸 · 연애 눈치보기
                  → 🔴 감점(−20). **제외가 아니다** — 사람이 골라 쓸 수는 있어야 한다
```

**결과 (기존 JSONL · 상위 200)**

```
타겟 핏 획득률  22% → 37%  ·  0점 120건 → 67건
상위 80 레인    Original 69 · 참여 6 · Info 3 · Question 2   ← Question 이 처음 진입
off-target      피부·이쁘다·뚱뚱 3건은 상위 200 밖으로, 나머지 2건은 22위→61위 · 12위→157위
```

🔴 **여전히 초안이다.** 표본이 하루치 몇 회뿐이고, 자동 fetch 기준도 threshold 운영값도
정하지 않았다.

## §4-L 🔴 저장 경로 계약 — **Raw Vault 와 Seed Inbox 는 다른 창고다** (2026-09-04 제품 결정)

> 🔴 **상태: 계약만 고정한다. 구현은 0이다.**
> DB · Prisma · importer · Sheet · 라우팅 **어느 것도 이 절이 만들지 않는다.**
> 이 절은 "무엇을 어디에 넣기로 했나" 만 적는다.

### 왜 지금 정하는가

`laneHint` 7종 중 **저장 경로가 있는 것은 `originalRaw` 하나뿐이다**(§4-H).
나머지는 분류만 되고 갈 곳이 없다 — 실측 스카우팅 기준 `microSeedQuestion` 25 ·
`participationSeed` 15 · `infoSeed` 7, 합쳐 **47건이 공중에 떠 있다.**

```
🔴 갈 곳이 없으면 둘 중 하나가 일어난다.
   ① 버려진다 — 짧은 글을 나쁜 글로 취급하는 결과가 된다
   ② 아무 데나 들어간다 — Raw Vault 가 잡담 창고가 된다
   둘 다 되돌리기 어렵다. 그래서 코드보다 계약을 먼저 적는다.
```

---

### A. 🟢 Raw Vault — **긴 원문 · Original Post 재료 저장소**

Raw Vault(`MicroSeedRawContent`)의 목적은 **원문 보존**이다.
사람이 다시 읽고, Original Post 로 재가공할 수 있는 **본문**을 담는다.

**들어갈 수 있는 것**

```
🟢 originalRaw
🟢 긴 생활 고민
🟢 가족 · 돈 · 건강 · 관계 · 일 · 살림 사연
🟢 Original Post 로 재가공할 만한 본문
```

**🔴 주의 — Raw Vault 를 짧은 질문 · 잡담 seed 저장소로 오염시키지 않는다.**

```
"짧은 글이 나쁘다" 는 뜻이 아니다(§4-I).
저장 목적이 다르다는 뜻이다.
Raw Vault 는 "다시 읽을 본문" 을 담는 곳이고,
"냉장고 추천해주세요" 에는 다시 읽을 본문이 없다.
```

한 창고에 목적이 다른 두 종류를 섞으면, 나중에 **Original Post 재료를 고를 때
잡담을 매번 걸러내야 한다.** 그 비용은 영구적이다.

---

### B. 🟡 Seed Inbox — **우리 커뮤니티에 던질 질문 · 소재 후보 목록**

`infoSeed` · `microSeedQuestion` · `participationSeed` 는 Raw Vault 가 아니라
**Seed Inbox 후보**로 본다.

| | Raw Vault | Seed Inbox |
|---|---|---|
| **목적** | 원문 보존 | **소재 후보 수집** |
| **담는 것** | 본문(rawBody) | 질문 · 아이디어 |
| **쓰임** | Original Post 재가공 재료 | 우리 커뮤니티에 **던질 질문** |
| **길이** | 길다 | 짧아도 된다 |
| **원문성** | 원문이 자산 | 원문보다 **발상**이 자산 |
| **지금 상태** | 🟢 있음 (`--raw-only` 수동) | 🔴 **없음 — 개념만** |

**Seed Inbox 후보 예시**

```
🟡 냉장고 추천해주세요
🟡 다들 어떠세요
🟡 보험료 얼마 내세요
🟡 요즘 이런 거 어떻게 하세요
```

> 🔴 **중요 — 지금 Seed Inbox 를 구현하지 않는다.**
> **DB 에 만들지 Sheet 에 만들지도 이번 PR 에서 확정하지 않는다.**
> 제품상 개념만 문서에 남긴다. 그릇을 먼저 만들면 그 그릇이 판단을 결정해 버린다.

---

### C. 🟡 Info seed 예외 — 댓글에 정보가 모이는 글

`infoSeed` 중 일부는 **댓글에 정보가 모이는 글**이라 원문 저장 가치가 있을 수 있다.

```
🟡 축의금 얼마가 적당할까요
🟡 병원비 얼마 정도 들까요
🟡 보험료 얼마 내세요
🟡 관리비 얼마 나와요
```

이런 글은 본문이 한 줄이어도 **댓글이 자산**이다. 그래서 계약은 이렇게 둔다.

```
① infoSeed 는 기본적으로 Seed Inbox 후보다.
② 단, 댓글 · 조회가 높고 본문이 충분하면 Raw Vault 후보가 될 수 있다.
🔴 ③ 이 판정은 자동 라우팅이 아니다. 다음 단계 설계 대상이다.
```

🔴 **"댓글이 높으면" 의 기준값을 이 절이 정하지 않는다.** 임계값을 지금 박으면
표본 없이 정한 숫자가 계약처럼 굳는다 — §4-B 에서 이미 겪은 실수다.

---

### D. 🟡 Question / 참여 seed — 원문보다 **질문 아이디어**가 가치다

`microSeedQuestion` · `participationSeed` 는 원문 자체보다 "이런 걸 물어보면 되는구나" 가 자산이다.

```
🟢 짧다고 버리지 않는다.
🔴 하지만 Original Post 원문 재료로 바로 넣지 않는다.
🟡 사람이 볼 수 있는 후보 목록 또는 별도 Seed Inbox 가 필요하다.
🔴 Google Sheet 로 보낼지는 별도 승인 전 금지다.
```

> 🔴 **네이버 → Google Sheet 자동 전송 금지** 는 이 절에서도 그대로다.
> `judgeSourceSite` 가 코드로 막고 있고(§5-B), 이 문서는 그 계약을 바꾸지 않는다.
> Seed Inbox 를 Sheet 로 만들자는 얘기가 나오면 **그것은 별도 승인 사항**이다.

---

### E. 🔴 비용 원칙 재확인 (§4-G 와 같은 내용 · 여기서 다시 못 박는다)

```
🔴 Seed Inbox 후보를 고르는 데 LLM 을 쓰지 않는다.
🟢 laneHint 와 점수화는 cheap signal 이다 — 규칙과 메타만 본다. 돈이 들지 않는다.
🔴 LLM 보조 판정은 전체 글 대상이 아니다.
🟡 LLM 은 상위 후보 중 위험 · 애매한 것, 또는 실제 가공 대상에만 쓴다.
🔴 목적은 Daily 100 → Daily 200 으로 갈 때 비용이 선형으로 터지지 않게 하는 것이다.
```

**후보를 고르는 단계에 LLM 을 넣으면 Daily 200 에서 비용이 글 수에 비례한다.**
고르는 것은 공짜 신호로 하고, 돈은 **가공**에만 쓴다.

## §4-C 🟡 Growth Issue 레인 — **전략만 적는다. 구현하지 않았다**

> 🔴 **상태: 미구현.** 코드 · 분류기 · cap · 감사 경로 **어느 것도 없다.**
> 이 절은 "나중에 이렇게 하기로 했다" 는 기록이지 사양이 아니다.
> 착수하려면 별도 PR 과 창업자 승인이 필요하다.

### 🔴 먼저 — **정치 · 진영 이슈는 소란소란이 가져가지 않는다**

이것은 "나중에 조건을 갖추면 연다" 가 아니라 **레인 자체를 만들지 않는다** 는 뜻이다.

```
🚫 정치 · 진영 · 이념 · 정당 · 선거 · 정치인 · 공직자
   → public 대상 아님
   → Growth Issue 후보 아님
   → shadow 후보도 아님
```

**이유는 유입이 부족해서가 아니라, 유입이 좋아도 커뮤니티가 변질되기 때문이다.**

```
정치 글은 유입이 붙는다. 그리고 진영 싸움을 데려온다.
한 번 진영이 갈리면 "40대 중반~60대 중반 여성의 생활 커뮤니티" 가 아니라
"정치 얘기하는 곳" 이 된다. 이것은 되돌릴 수 없다 —
떠난 사람은 돌아오지 않고, 남은 사람이 그 성격을 다시 강화한다.
```

North Star 는 **주간 재방문 참여 유저 수**다. 진영 싸움은 참여 수를 **일시적으로 올리고**
재방문의 성격을 바꾼다. 우리가 세려는 숫자가 아니다.

> 🔴 생활 Original 레인의 `politicalOrPublicFigure` · `politicalTopicLikely` 자동 제외는
> **다른 레인으로 보내기 위한 분류가 아니라 그냥 제외다.** 갈 곳이 없다.

### 🔴 `공인` 을 한 단어로 쓰지 않는다

앞선 기록은 *"연예 · 방송 · 공인"* 처럼 뭉뚱그렸다. **그 단어가 정치인을 데려온다.**

| 대상 | 취급 |
|---|---|
| 정치인 · 공직자 · 정당 · 진영 · 선거 · 이념 | 🚫 **제외** — 레인 없음 |
| 연예인 · 방송인 · 셀럽 · 방송 프로그램 | 🔵 **조건부** Growth Issue 후보 |

**두 집합을 같은 문장에 넣지 않는다.** 같이 쓰는 순간 코드가 하나의 플래그로 합친다.

### 🔵 Growth Issue 후보 = 연예 · 방송 · 셀럽 이슈 **로 한정**

또래가 실제로 이야기하는 소재이고 검색 유입이 붙는다.
드라마 · 예능 · 배우 · 가수 · 방송 화제 — 이 범위 안에서만 후보가 된다.

### 🔴 형식이 내용보다 중요하다

```
🚫 "논란 정리"                    → 사실 판정을 우리가 하는 것이 된다
🟢 "우리 또래는 이걸 어떻게 보나"   → 대화 주제로 변환한다
```

**금지선 (연예 · 방송 · 셀럽에도 전부 적용 · 예외 없음):**

```
🔴 비난 · 단정 · 루머 · 사생활 추측 · 외모 비하 · 가족 공격
```

연예인이라고 해서 완화되지 않는다. **유입 자산이라는 이유로 사람을 깎는 글을 쓰지 않는다.**

### 🟡 이미지 — **향후 설계 항목. 지금 구현하지 않는다**

연예 · 방송 · 셀럽 Growth Issue 에서는 **원문 게시글 이미지도 장기적으로 가져갈 수 있다**
(창업자 변호사 확인 판단, 2026-09-03).

> 🔴 **다만 이 PR 은 물론이고 Growth Issue 착수 전까지도 구현하지 않는다.**
> 지금 수집기는 이미지를 가져오지 않으며(collector 계약), 그 계약을 이 문서가 바꾸지 않는다.

Growth Issue 설계 시 **별도 항목으로** 정할 것:

```
① 저장       어디에 · 원본인가 변환본인가 · 보존 기간
② 노출       어느 화면까지 · 크기 · 출처 표기 형식
③ 삭제       원본이 지워지면 · 요청이 오면 — 경로와 SLA
④ 출처       링크 · 카페명 · 작성자 표기 범위 (🔴 닉네임 정책과 충돌 확인)
⑤ noindex    public 노출 시 이미지의 색인 정책 — 🔴 텍스트와 따로 판단한다
```

⚠️ **[이미지 포함 원문 재발행 금지](../../CLAUDE.md) 교훈**(우나어 롤백 사고)이 있다.
"가능하다" 와 "지금 해도 된다" 는 다르다 — 위 5개가 정해지기 전에는 열지 않는다.

### 열기 전에 반드시 있어야 하는 것

```
① 별도 cap        생활 레인 cap 과 공유하지 않는다
② 별도 승인       레인 개방 자체가 창업자 승인 사항이다
③ 별도 감사       무엇이 왜 growth 로 갔는지 사후에 답할 수 있어야 한다
④ 레인 표식       Micro Seed · Original 과 코드에서 구분된다 (3축 게이트와 같은 강도)
⑤ 정치 배제 증명  분류기가 정치 · 진영을 growth 로 보내지 않는다는 fixture
```

**하나라도 없으면 열지 않는다.**

```

🔴 **cafeId 를 `sourceSite` 에 넣는 이유**: 네이버 articleId 는 **카페 안에서만** 유일하다.
cafeId 가 빠지면 다른 카페의 같은 번호 글이 같은 dedupKey 가 되어 **한쪽이 조용히 SKIP** 된다.

> 🟢 이 계약은 새로 만든 것이 아니다. Raw Vault 에 `navercafe:remonterrace` / `34783204` 행이
> **이미 있었고**, PR-S2-b-1 은 그것을 코드와 fixture 로 고정했을 뿐이다. **migration 0건.**

### §5-B 🔴 레인별로 받는 소스가 다르다

| 레인 | 명령 | 받는 소스 |
|---|---|---|
| **Original Post 공급** | `--apply --raw-only --batch=N` | 82cook · **navercafe:\*** |
| **Micro Seed** | `--apply --limit=1` | 🔴 **82cook 만** |

**네이버를 Sheet 레인에 넣지 않는 이유는 품질이 아니라 레인의 성격이다.**
Micro Seed 는 원문을 **그대로** 쓰고 영구 noindex 를 받는다(헌법 §10-5).
로그인 영역의 글을 그 레인에 올리는 것은 별개의 판단이고, 이 PR 이 대신 내리지 않는다.

판정은 `judgeSourceSite` 한 곳이 하고, fixture 가 **양방향**을 고정한다 —
*"raw-only 는 navercafe 를 받는다"* 와 *"micro-seed 는 navercafe 를 거부한다"* 둘 다.

### §5-C 소스별 슬롯 quota

| 소스 | 슬롯당 | 근거 |
|---|---|---|
| 82cook | **30건** | IP 차단은 네트워크를 바꾸면 회복된다 (가역) |
| **네이버 카페** | 🔴 **10건** | **계정 정지는 되돌릴 수 없다** (비가역) |

🔴 우나어의 `maxPostsPerCafe = 80` 을 그대로 쓰지 않는다.
**한 소스를 세게 긁지 않고 여러 카페 · 시간대에 얇게 분산한다.**

### §5-D 우나어 스케줄 자산 — 가져올 것 / 버릴 것

| 🟢 가져온다 | 🔴 그대로 가져오지 않는다 |
|---|---|
| 로컬 launchd **시간 분산** (7슬롯) | **네이버 크롤을 GHA 에서 돌리는 구조** |
| **lockfile** (락 TTL > subprocess timeout) | 댓글 GHA 자동 발행 |
| **SESSION_HALTED** 플래그 · 시작 직전 차단 | 공개 발행 cron |
| 쿠키 TTL 경보 (14일 준비 · 7일 중요 · 24h throttle) | reaction / best 자동화 |
| 실패 cooldown · 품질 게이트(수집 0건 → exit 1) | `popular-sync` 전용 슬롯 (§4-A) |
| **GHA 를 "수집 이후 처리" 에 쓰는 운영 리듬** | `maxPostsPerCafe = 80` |
| `randomDelay(base, 0.8, 1.3~1.5)` 사람형 pacing | 수집=저장 한 프로세스 |

> 🔴 **`randomDelay` 는 82cook 과 결정적으로 다른 지점이다.**
> 82cook 수집기는 `DELAY_MS = 2000` **고정 · jitter 없음** 이고 그것이 맞다 —
> 우리는 정직한 봇 UA 로 접근한다. **네이버는 로그인한 사람으로 접근하므로 pacing 도 사람이어야 한다.**
> 이것은 우회가 아니라 **자연화**다. UA 위장 · IP 로테이션 · robots 무시는 하지 않는다.

### 🔴 이번 PR 은 스케줄러를 등록하지 않는다

plist **템플릿**까지만 둔다 (`docs/operations/launchd/`).
`launchctl load` 는 창업자 승인 후 별도 절차다 — 등록하는 순간 되돌리는 주체가 사람이 된다.

### 네이버 카페 수집기 설계 (미구현 · PR-S2′ 또는 S2-b)

우나어 `agents/cafe/` 에서 가져올 것과 버릴 것을 먼저 적는다.

| 🟢 가져온다 | 🔴 가져오지 않는다 |
|---|---|
| Playwright + 저장 쿠키 세션 구조 | `CafePost` 테이블 — 우리는 `MicroSeedRawContent` 하나로 간다 |
| 락파일 (`/tmp/*.lock` · TTL) | 심리분석 · 트렌드 · DailyBrief (Sonnet 월 ~$328) |
| 쿠키 TTL 30일 · 28일 사전경고 | `content-curator` 발행 경로 — 🔴 원문 그대로 발행이다 |
| `killerScore` 산식 (참여 55 / 길이 20 / 미디어 5 / 게시판 15 / 최신 5) | 이미지 수집 · R2 업로드 |

| 슬롯 분산 (7회/day) · Slack 알림 | |

> "구조를 복사하고 새로 붙인다" 다.

## §6 Raw Vault 확장 검토 — 🟡 **이번 PR 에 넣지 않는다**

창업자가 검토를 요청한 세 필드다.

| 필드 | 지금 필요한가 | 판단 |
|---|---|---|
| `killerScore` | 🟡 아니다 | 선별은 **수집 시점**에 `selectionScore` 로 이미 한다. DB 에 저장할 이유는 "나중에 재정렬" 인데 그 요구가 아직 없다 |
| `sourceStage` | 🟡 아니다 | 소스가 82cook · 네이버 둘뿐이다. 사다리는 소스가 4~5개일 때 의미가 생긴다 |
| `engagementSignals` | 🟡 아니다 | 댓글 수는 `MicroSeedCandidate.sourceCommentCount` 에 이미 있다. raw-only 는 그 행을 안 만들지만, **Original Post 레인은 댓글 수를 쓰지 않는다**(길이 대리 지표로 쓰지 않기로 확정 — 레인 정본 §7) |

### 🔴 결론: migration 없이 300건을 채울 수 있다

`MicroSeedRawContent` 는 이미 필요한 것을 다 가지고 있다.

```
sourceSite · sourceUrl · sourceArticleId · sourceCapturedAt · rawTitle · rawBody
@@unique([sourceSite, sourceArticleId])   ← 멱등성
```

**그래서 이 PR 은 schema 를 건드리지 않는다.**

### PR 분리 판단

헌법 §12-3 이 *"한 PR 에 schema 와 런타임 코드를 같이 담지 않는다"* 를 확정 정책으로 두고 있다.
근거는 실측 사고다 — merge 즉시 Vercel 자동 배포이고 `migrate deploy` 는 자동 실행되지 않아,
**컬럼 없이 새 코드가 먼저 나가면 런타임이 깨진다.**

```
PR-S2  (이번)   런타임 코드 + 문서       migration 0
PR-S2′ (필요해지면)  Raw Vault 확장 3필드   schema + migration 만
```

**세 필드가 실제로 필요해지는 시점**

| 필드 | 언제 |
|---|---|
| `sourceStage` | 소스가 3개 이상이 되고 소스별 신뢰도를 나눠야 할 때 |
| `killerScore` | 수집 시점 점수와 다른 기준으로 **사후 재정렬**이 필요할 때 |
| `engagementSignals` | 댓글 반응 지도(M3)를 Raw 단계에서 보관해야 할 때 |

🔴 **지금 넣으면 셋 다 값이 채워지지 않은 채 스키마만 늘어난다.**
