## 1. 🔴 VE-M2는 비용 0원 단계로 정의한다

바로 LLM 대량 분석으로 가지 않는다. 이유는 절약이 아니라 **순서**다.

9,674건에 LLM을 돌리면 결과의 품질을 판정할 기준이 없다. 규칙으로 뽑을 수 있는 신호를 먼저 채워
**"무엇이 부족한가"를 눈으로 본 뒤에** LLM을 부른다. 그래야 LLM에게 물을 질문이 정해진다.

### 포함하는 신호 — 전부 규칙 계산

| 신호 | 계산 방법 | 입력 |
|---|---|---|
| `typingArtifacts` | 자모 분리 · 자판 인접 오류 · 반복 입력 — 사전 대조 | 원문 |
| `punctuationHabit` | `..` `~~` `ㅠㅠ` `^^` · 물음표/느낌표 개수 — 정규식 | 원문 |
| `spacingVariance` | 어절 길이 분포 · 띄어쓰기 편차 · 구어체 붙여쓰기 | 원문 |
| `mobileInputTrace` | 문단 길이 · 줄바꿈 간격 · 문장 중간 개행 | 원문 |
| `communityRegister` | 호칭 · 인사 · 커뮤니티 어투 — 사전 대조 (**§3**) | 원문 |
| **`artifactFrequency`** | 위 5종의 **정규화 빈도** | 위 5종 |
| `VoiceCommentSignal` 기초 | `ordinal` · `contentLength` · `contentHash` · `likeCount` · `replyCount` · `truncated` | topComments |
| comment `reactionType` 기초 | 공감 / 질문 / 반박 / 경험공유 / 정보제공 — 어미·문형 규칙 | 댓글 |

`artifactFrequency`가 핵심이다. 나머지는 "무엇이 있는가"를 세고,
이 축만이 **"얼마나 있어야 자연스러운가"**를 답한다. 이 값이 없으면 나중에 남발한다.

`method = 'rule'`로 고정하고, LLM 산출물과 섞지 않는다.

## 2. 🔴 계산하지 않는 7종과 그 이유

| 신호 | 왜 지금은 불가능한가 |
|---|---|
| `naturalnessScore` | "사람이 쓴 것 같은가" — 원문은 **실제로 사람이 썼다**. 물어볼 게 없다 |
| `voiceRetention` | "원문 말투가 살아 있는 정도" — 무엇에 대비해 살아 있는가 |
| `originalityDelta` | "소란소란 글로 새로워진 정도" — 새로워진 대상이 없다 |
| `overSanitizedRisk` | 과교정 위험 — 교정한 결과물이 있어야 잰다 |
| `overMimicryRisk` | 과모방 위험 — 모방한 결과물이 있어야 잰다 |
| `expressionRisk` | 고유 표현 **복제** 위험 — 복제본이 있어야 잰다 |
| `sequenceSimilarityRisk` | 문장·문단 구조 **유사** 위험 — 비교 대상이 있어야 잰다 |

**7종 전부 "소란소란이 쓴 글 ↔ 원문"의 비교 축이다.** 원문 한쪽만으로는 계산이 성립하지 않는다.
9,674건에 이 값을 채우려 하면 **의미 없는 숫자가 원장에 남는다.**

→ **VE-M3(생성·평가 단계)로 옮긴다.** 생성물이 생기는 순간 같은 `voiceSourceId`에
`method = 'llm'` 행으로 붙는다. 지금 스키마 초안이 `method`를 분리해 둔 이유가 이것이다.

> `overSanitizedRisk`와 `overMimicryRisk`는 반대 방향이라 **함께 읽어야 한다**(스타일 전략 §3-3).
> 한쪽만 재면 반대편으로 넘어간다. VE-M3에서 둘을 동시에 도입한다.

## 3. 🔴 `communityRegister` — 출처 식별 호칭을 구조로 다룬다

### 문제

우나어 코퍼스는 카페 6곳에서 왔고, 각 커뮤니티에는 **내부 호칭**이 있다.

| 호칭 | 출처 | 코퍼스 비중 |
|---|---|---|
| **우갱님들** | 우아한 갱년기 (`navercafe:wgang`) | 38.0% |
| **레테님들** | 레몬테라스 (`navercafe:remonterrace`) | 24.1% |
| **82님들** | 82cook — Micro Seed 레인의 수집원 | (Micro Seed 쪽) |
| **우나어** | 우리 나이가 어때서 — 자사 서비스 |  |

이 표현들은 **"40~60대 여성 일반 말투"가 아니다.** 특정 커뮤니티 안에서만 통하는 식별 호칭이다.
그대로 쓰면 소란소란 글이 **다른 커뮤니티에서 옮겨온 티**를 낸다.

> ⚠️ `navercafe:dlxogns01`(31.1%) · `masanmam`(5.8%) · `goondae`(0.5%) · `yeowooya`(0.4%)는
> 내부 호칭이 확인되지 않았다. **추측해서 채우지 않는다** — 확인되면 사전에 추가한다.
> 확인 전까지는 일반 호칭 규칙만 적용한다.

### 원칙 — 지우는 게 아니라 바꾸는 것

```
원문의 질문 구조와 공동체 감각  →  살린다
출처를 식별하는 호칭            →  우리 맥락으로 바꾼다
```

**호칭은 껍데기이고 "여기 있는 사람들에게 묻는다"는 감각이 알맹이다.** 알맹이를 버리면
그냥 혼잣말이 된다. 우리 또래가 서로에게 묻는 구조는 소란소란이 가져가야 할 자산이다.

### 예시

| 원문 | 방향 |
|---|---|
| "82님들 저 이거 어떻게 해야 할까요?" | "우리 또래분들, 이런 경우 어떻게 하세요?" |
|  | 또는 "여기 계신 분들은 이런 적 있으세요?" |
| "우갱님들 조언 부탁드려요" | "여기 계신 분들 조언 좀 부탁드려요" |
| "레테님들 다들 어떠세요?" | "소란소란 분들은 다들 어떠세요?" |

질문 구조("어떻게 하세요?" · "이런 적 있으세요?")와 요청의 결은 그대로 두고,
**호칭만 우리 서비스 맥락으로 옮긴다.**

### 신호 설계

`communityRegister`를 두 갈래로 나눠 기록한다.

```
communityRegister: {
  generic:         [ "다들", "혹시", "님들", "~하세요?" ],      // 우리 또래 공통 어투 → 학습한다
  sourceSpecific:  [ { term: "우갱님들", site: "navercafe:wgang", role: "address" } ],
                                                                // 출처 식별 → 변환 대상으로 표시
  addressPattern:  "collective_question"                        // 공동체 질문 구조 → 살린다
}
```

🔴 **`sourceSpecific`은 "쓰지 말 것" 목록이 아니라 "그대로 쓰지 말 것" 목록이다.**
Original Lane 생성 시 이 항목이 있으면 우리 호칭으로 치환하고, 질문 구조는 유지한다.

🔴 **원문 문장을 저장하지 않는다.** 위 구조에 담기는 것은 **호칭 어휘와 패턴 이름**이지 문장이 아니다.
누출 가드(VE-R3.1, [PR #93](./2026-08-26-voice-corpus-import-operations.md#3-100건에서-발견한-것--legacylabels-경유-원문-누출))가 여기에도 적용된다.

## 4. 데이터 제약 — 신호 계산이 반드시 반영할 것

| 제약 | 실측 | 신호에 미치는 영향 |
|---|---|---|
| 코퍼스 규모 | 고품질 **9,674건** | 전체 33,031건이 아니다 |
| **본문 잘림** | 정확히 3000자 **230건 (2.4%)** | 🔴 문장 끝맺음 · 문단 구조 신호가 오염된다. **계산에서 제외하거나 플래그** |
| **댓글 잘림** | 199자 이상 **약 4.0%** | 🔴 모르고 학습하면 "우리 또래는 200자에서 말을 끊는다"는 거짓 패턴. `truncated`로 표시 |
| 시기 편중 | **2026년 99.8%** (2023~2025 합계 19건) | 시계열 다양성이 없다. "시대별 말투 변화"는 이 데이터로 못 본다 |
| 출처 편중 | 카페 **3곳이 93%** | `communityRegister`가 3곳 어투로 쏠린다. 사전 구축 시 가중치 필요 |
| 라벨 편차 | 하위 4종(`viralType`·`conflictTrigger`·`emotionalPeak`·`betrayalFactor`) **31~35%만 존재** | 전 건에 있다고 전제하면 안 된다. 갈등형 글에만 붙는다 |
| 본문 길이 | 300자 미만이 **45.7%** | 짧은 글에서는 문체 신호 표본이 부족하다. `artifactFrequency` 신뢰구간 필요 |

### 🔴 `referenced`는 승인 정답지가 아니다

`usedAt`에서 온 `referenced` 3,093건과 나머지 6,581건을 비교하면:

| | referenced | not referenced |
|---|---|---|
| 본문 중앙 | 318자 | 327자 — **차이 없음** |
| **댓글 평균** | **16.8개** | **7.7개** — **2.2배** |
| qualityScore 평균 | 61.9 | 57.4 |
| killerScore 평균 | 57.6 | 48.8 |

**우나어 큐레이션은 "댓글이 많이 붙은 글"을 골랐다.** 글 자체의 품질 차이는 작다.

→ **"좋은 글" 라벨로 쓰면 거짓 정답지가 된다.**
→ **"댓글이 붙을 글" 예측 신호로는 유효하다.** North Star가 주간 재방문 참여 유저 수이므로
   이쪽이 오히려 우리에게 필요한 축이다. 용도를 혼동하지 않는다.

## 5. VE-M3 대비 설계 메모 — 첫 LLM 비용은 여기서 발생한다

> 🔴 아래는 **메모**다. 이번 단계에서 구현하지 않는다.

### 비용 추정 (실측 근거)

입력 1건당 **1,173자** = 본문 평균 539자 + 댓글 10.6개 × 60자. 전량 **11.35M자**.

| 환산 | 1건 | 전량 9,674건 |
|---|---|---|
| 1.0 tok/자 | 1,173 tok | 11.4M tok |
| **1.3 tok/자** (권장 가정) | 1,525 tok | **14.8M tok** |
| 1.5 tok/자 | 1,760 tok | 17M tok |

출력은 JSON 산출 기준 건당 400~500 tok → 전량 약 4.4M tok.

| 모델 | 전량 개략 | 10건 dry-run |
|---|---|---|
| **Haiku 4.5** (권장 시작점) | **$35~40** | **$0.05 미만** |
| Sonnet 5 | $105~115 | 약 $0.12 |
| Opus 5 | $540~570 | 약 $0.6 |

⚠️ **단가는 실행 전 콘솔에서 재확인한다.** 비율(약 1 : 3 : 15)은 안정적이다.

### 첫 dry-run 10건 선정 기준

```
제외:  contentLength = 3000 (잘림 230건)
       legacyLabels drop 이력이 있는 행
       commentCount = 0
선정:  contentLength 300~800자 (문체 신호가 보이는 최소 길이)
       commentCount >= 8 (중앙값 이상)
       sourceSite 분산 — 상위 3곳 각 3건 + 소수 카페 1건
       referenced 5 : not referenced 5
       desireCategory 최소 4종
```

10건인 이유는 대표성이 아니라 **사람이 전량을 눈으로 읽을 수 있는 크기**이기 때문이다.

### 🔴 cache key 설계 결함

현행 초안은 `@@unique([voiceSourceId, ruleVersion, method])`다. 여기에는
**모델과 프롬프트 버전이 없다.** 그래서:

- Haiku 산출물과 Sonnet 산출물이 **같은 키를 다툰다**
- 프롬프트를 고쳐도 **캐시가 깨지지 않는다** — 옛 결과를 새 프롬프트 결과로 착각한다

권고안:

```
cacheKey = sha256(contentHash + ruleVersion + method + model + promptVersion)
```
또는
```prisma
@@unique([voiceSourceId, ruleVersion, method, model, promptVersion])
```

`contentHash`를 넣는 것이 핵심이다 — **원문이 수정되면 캐시가 자동 무효화된다.**
9,674건 전부에 `contentHash`가 있다(100%).

> 🔴 **이번 PR에서 `schema.prisma`를 수정하지 않았다.** schema 변경은 별도 승인 대상이다.

### hard cap

| cap | 값 | 이유 |
|---|---|---|
| `--apply`는 `--limit` 필수 | — | 이미 확립된 게이트 (VE-R3) |
| burst | **10** | 첫 dry-run 크기 |
| softDaily | **200** | 하루에 사람이 관찰 가능한 양 |
| hardDaily | **1,000** | 초과 시 즉시 중단 |
| **tokenCap** | **500K / 실행** | 🔴 건수 cap만으로는 부족하다 |
| **costCap** | **$5 / 실행** | 사람이 감당 가능한 상한 |
| timeout | **30초 / 건** | Micro Seed PROCESSING과 동일 |
| **retry도 cap에 포함** | — | 🔴 cap 밖에 두면 실패가 많을수록 비용이 커진다 |

🔴 **건수 cap만으로는 폭주를 못 막는다.** max 3,000자 글이 몰리면 같은 건수에 토큰이 3배가 된다.
토큰·비용 cap이 함께 있어야 한다.

### 실패 정책

| 유형 | 처리 | 근거 |
|---|---|---|
| 429 · 503 · timeout | 지수 백오프 **최대 3회** | 일시적 장애 |
| 400 · 잘못된 입력 | **skip + 사유 기록**, 재시도 **0** | 반복해도 결과가 같다 |
| JSON 파싱 실패 | **1회만** 재시도 후 skip | 재시도가 비용을 태운다 |
| 원문 삭제 (우나어에 없음) | skip · `deletedDetectedAt` 기록 | 필드가 이미 있다 |
| **연속 실패 5회** | **배치 전체 중단** | 사고를 키우지 않는다 |
