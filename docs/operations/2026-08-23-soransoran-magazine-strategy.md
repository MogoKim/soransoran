## 0. 한 줄 판정

> 매거진은 **우리가 쓴 글**이다. 사람이 검수하지 않은 글이 공개되는 경로를 만들지 않는다.

우나어의 네이버 색인 붕괴(4,600 → 0)는 기술 실수가 아니라
"사이트 안에서 무엇이 원본이고 무엇이 외부 반응 글인지 검색엔진이 구분하지 못한 것"이었다.
매거진은 그 경계를 흐릴 수 있는 유일한 영역이라, 시작하기 전에 규칙을 고정한다.

## 1. 매거진의 역할

### 커뮤니티와 다른 점

| | 커뮤니티 | 매거진 |
|---|---|---|
| 저자 | 회원 | 소란소란 편집팀 |
| 성격 | 경험·질문·대화 | 정리된 설명 |
| 글쓰기 버튼 | 노출 | **노출하지 않는다** (IA 정본) |
| 발행 | 회원이 직접 | 창업자 검수 후 |

### SEO 최전방이지만 목적은 참여 전환

매거진은 검색 유입의 최전방이다. 갱년기·수면·감정 같은 검색어의 착지점이 된다.

**다만 유입 자체가 목적이 아니다.**
North Star는 주간 재방문 참여 유저 수다.
검색으로 들어온 사람이 글만 읽고 나가면 우나어와 같은 구조가 된다.
모든 매거진 글은 **커뮤니티로 돌려보내는 출구**를 가진다(원칙 9).

## 1.5 운영 정본은 성장 운영 전략서다 (7-A)

> **매거진 운영의 정본은
> [매거진 성장 운영 전략서](./2026-08-23-soransoran-magazine-seo-production-strategy.md)** 다.
> 이 문서는 **콘텐츠 원칙**(무엇을 어떻게 쓰는가)을 정하고,
> 그쪽이 **운영**(언제 만들고 언제 공개하는가)을 정한다. 충돌하면 그쪽을 따른다.

거기서 확정된 것 중 이 문서와 맞물리는 핵심만 옮긴다.

```
매거진은 SEO 블로그가 아니라 커뮤니티 성장 엔진이다
North Star = 4050/5060 여성이 소란소란에서 자기 이야기를 남긴 횟수

제작과 공개를 분리한다        생성 01:00 KST · 공개 10:30 KST
창업자는 매일 검수하지 않는다   주간 리포트와 예외 6가지만 본다
LOW/MEDIUM 은 자동 QA PASS 시 자동 공개
HIGH 는 자동 공개하지 않는다 (BLOCKED)
미래 publishAt 글은 목록·상세·sitemap·관련글·시리즈 UI 전부에서 숨긴다
창업자 PC 가 꺼져도 예약분은 공개된다
예약 재고 목표 14일 · 최소 7일 · 최대 21일
주제는 큐가 아니라 마케팅 캘린더로 운영한다
```

⚠️ **원칙 5(§2)의 "창업자 검수"는 매일 검수가 아니다.**
`riskLevel` 이 검수 깊이를 정하고, LOW/MEDIUM 은 자동 QA 가 대신하며,
창업자는 **HIGH 와 예외**만 본다. 자동화되는 것은 **공개 시점**이지 **판단**이 아니다.

## 2. 운영 원칙 10개

**원칙 1 — 매거진은 "우리가 쓴 글"이다.**
커뮤니티는 회원 글, 매거진은 편집팀 글. 이 구분이 흐려지면
SEO 정책 원칙 2("무엇이 대표 문서인지 헷갈리지 않게")가 무너진다.

**원칙 2 — 외부글을 수집·요약·재발행하지 않는다.**
크롤·RSS·뉴스 요약 전부 금지. 우나어 실패 F1의 정확한 재현 경로다.

**원칙 3 — 서비스 안에 AI API를 두지 않는다.**
소란소란 런타임에 LLM 호출이 없다. AI는 **창업자의 편집 도구**로만 존재한다.

**원칙 4 — 자동 발행 경로를 만들지 않는다.**
사람이 검수하지 않은 글이 공개되는 경로가 **구조적으로 존재하지 않아야** 한다.
크론·웹훅·에이전트 발행 금지.

**원칙 5 — 최종 원고의 책임은 창업자에게 있다. 검수 깊이는 위험도가 정한다.**
AI 초안은 초안일 뿐이다. 발행은 **"창업자가 위험을 확인하고 승인했다"** 는 뜻이다.

책임은 어떤 경우에도 창업자에게 있다. 다만 **모든 글의 전문을 읽는 방식으로는 365일을 갈 수 없다.**
글마다 `riskLevel` 을 매기고, 등급이 검수 깊이를 정한다(§5.1).

| 등급 | 무엇인가 | 창업자가 보는 것 |
|---|---|---|
| **HIGH** | 병원·증상 감별·질환 가능성·약/치료/검사 · 금전 손해 직결 | **본문 전문** |
| **MEDIUM** | 건강과 닿지만 치료 조언이 아님 · 제도/수치가 손해로 직결되지 않음 | 요약 + **위험 문장 5개** |
| **LOW** | 일상·공감·관계·경험 기록 (의학적 주장 0 · 금전 수치 0) | **요약 패킷** |

**등급을 낮출 수 없는 조건이 있다**(§5.2). 자동 QA 가 하나라도 FAIL 이면 등급과 무관하게 전문 검수다.
이 규칙이 없으면 "위험 기반"은 그냥 "대충 본다"가 된다.

**원칙 6 — 하루 2건 대량 발행보다 하루 1건 품질.**
속도를 목표로 삼는 순간 AI티가 난다. 발행 속도는 §4.3.

**원칙 7 — AI티를 지운다.**
반복 문형("~에 대해 알아보겠습니다", "결론적으로"), 균일한 문단 길이,
과도한 불릿, 근거 없는 수치. 발행 전 **소리 내어 읽어보고 어색하면 고친다**.

**원칙 8 — 의료·건강 글은 진단하지 않는다.**
증상 설명과 생활 관리까지. **진단·치료·약 권유 금지.**
모든 건강 글에 병원 상담 권장 문구를 넣는다(§4.4).
이건 SEO가 아니라 신뢰와 안전의 문제다.

**원칙 9 — 매거진 글은 커뮤니티로 돌려보낸다.**
모든 글 말미에 관련 게시판·질문 유도를 둔다.

**원칙 10 — 색인 규칙은 SEO 정책 문서를 따른다.**
이 문서에서 `robots`·`canonical`·`sitemap` 규칙을 다시 정의하지 않는다.
두 문서가 어긋나면 사고가 난다.

## 3. AI 사용 경계

> AI 는 **제작 보조자**이지 발행자가 아니다.
> 경계는 "AI 를 쓰느냐"가 아니라 **"사람 승인 없이 공개될 수 있느냐"** 로 긋는다.

### 3.0 역할 분리 — 누가 무엇을 하는가 (고정)

AI 를 여러 개 쓰면 "누가 최종 원고를 썼는가"가 흐려진다. 흐려지면 책임도 흐려지고,
같은 글을 두 도구가 각자 고쳐 톤이 어긋난다. **아래 분담은 고정이며 임의로 바꾸지 않는다.**

| 주체 | 하는 일 | **하지 않는 일** |
|---|---|---|
| **Claude 채팅** | 주제 해석 · 검색 의도 분석 · 글 구조 제안 · 위험 문장 후보 추출 · 의료/금전/법률 리스크 분석 · **ChatGPT 에 넘길 최종 원고 지시서 작성** | **최종 원고를 쓰지 않는다** |
| **ChatGPT 채팅** | **최종 원고 작성** · 소란소란 톤으로 문장 정리 · AI티 제거 · 4050/5060 여성 독자에게 자연스러운 표현 · **hero 이미지 생성** | 주제를 정하지 않는다 · 위험도를 판정하지 않는다 |
| **Claude Code** | ChatGPT 결과를 `drafts/` 또는 `articles.ts` 형식으로 파일화 · 자동 QA · 타입/빌드/SEO 검증 · 검수 패킷 생성 · 승인 후 발행 준비 | **원고를 새로 쓰지 않는다** · 승인 없이 공개하지 않는다 |
| **창업자** | 월간 주제 큐 승인 · **위험 기반 최종 승인** · HIGH 글 전문 검수 · **이미지 인상 최종 판단** | — (최종 책임자) |

**왜 Claude 채팅이 최종 원고를 쓰지 않는가**
분석하는 쪽과 쓰는 쪽을 나눠야 위험 문장 추출이 자기 검열이 되지 않는다.
자기가 쓴 문장을 자기가 "위험 문장 5개"로 뽑으면, 위험하다고 생각한 문장은 애초에 쓰지 않았을 것이다.
**지시서를 쓴 쪽과 원고를 쓴 쪽이 다를 때만 §5.1 의 위험 문장 검수가 실제 검증이 된다.**

**왜 Claude Code 가 원고를 쓰지 않는가**
Claude Code 는 파일을 직접 고칠 수 있는 유일한 주체다. 여기에 작성 권한까지 주면
"쓴 사람이 곧 커밋하는 사람"이 되어 원칙 4(자동 발행 경로 없음)가 구조적으로 무너진다.
Claude Code 는 **받은 것을 형식화하고 검증할 뿐**이다.

**흐름**

```
큐(사람 승인)
  → Claude 채팅  : 의도 분석 · 구조 · 리스크 · 원고 지시서
  → ChatGPT 채팅 : 최종 원고 · 톤 정리 · hero 이미지
  → Claude Code  : 파일화 · 자동 QA · 검증 · 검수 패킷
  → 창업자       : 위험 기반 승인 / 수정 요청 / 폐기      ★ 유일한 필수 게이트
  → Claude Code  : 승인분만 발행 준비 → 창업자 승인 후 push
```

**이 흐름에서도 바뀌지 않는 것**

```
🚫 자동 공개 · 자동 push · Search Console/Naver 자동 제출   — 원칙 4 · SEO 정책 §5
🚫 외부글 크롤 · 요약 · 복붙 재발행                          — 원칙 2 · 우나어 F1
🚫 소란소란 런타임의 AI API 호출                             — 원칙 3
```

세 가지는 도구를 몇 개 쓰든, 파이프라인이 얼마나 자동화되든 **예외가 없다.**

### 허용

| 항목 | 조건 |
|---|---|
| ChatGPT/Claude 로 **원고 초안 생성** | 대화창이든 Playwright 자동화든. 결과는 어디까지나 초안 |
| **구조·제목 후보 브레인스토밍** | 최종 선택은 창업자 |

🚫 자동 공개 없음
🚫 자동 commit 없음
🚫 자동 push 없음
🚫 자동 noindex 해제 없음

```

## 4. 콘텐츠 전략

### 4.1 주제 클러스터 8개

| 클러스터 | 예시 주제 |
|---|---|
| 갱년기 증상 | 안면홍조 · 발한 · 관절통 |
| 수면 | 새벽에 깨는 이유 · 잠자리 습관 |
| 감정 | 이유 없는 우울 · 짜증 · 무기력 |
| 부부/가족 | 남편과의 거리 · 자녀 독립 |
| 병원/검진 | 언제 가야 하나 · 무슨 과인가 · 검진 항목 |
| 일상관리 | 식사 · 운동 · 체중 |
| 돈/일 | 재취업 · 소득 공백 · 노후 준비 |
| 관계 회복 | 친구 · 모임 · 혼자 있는 시간 |

**관련글은 같은 클러스터 안에서 연결한다.** 클러스터를 넘나들면 주제 신호가 흐려진다.

### 4.2 글 구조 5단

```
1. 공감 도입        "저도 그랬습니다" — 증상·상황을 먼저 인정
2. 쉬운 설명        왜 그런지. 전문 용어를 쓰면 바로 풀어쓴다
3. 체크리스트/실천  오늘 할 수 있는 것 3~5개
4. 관련 글 연결     같은 클러스터의 다른 글
5. 커뮤니티 참여    "여러분은 어떠셨나요" + 게시판 링크
```

**5단이 원칙 9의 실행 수단이다.** 빠뜨리면 유입만 받고 이탈한다.

### 4.3 발행 속도

```
1주차       하루 1건       품질 기준을 잡는 기간
2주차 이후  하루 1~2건     검수 시간이 확보되는 선에서
1달 목표    25~40건
```

**속도가 품질을 넘지 않게 한다.** 검수할 시간이 없으면 그날은 발행하지 않는다.

### 4.4 의료/건강 안전 문구

건강 관련 글에는 **본문 안**과 **글 하단** 두 곳에 둔다.

```
본문 안   증상을 설명한 직후 — "증상이 오래가거나 심하면 병원에서 확인해 보세요."
하단 고정 "이 글은 정보 제공을 위한 것이며 의학적 진단이나 치료를 대신하지 않습니다.
          증상이 있다면 의료진과 상담하세요."
```

**금지 표현**: "~하면 낫습니다" · "~를 드세요"(약·보조제 권유) · 특정 병원/제품 지목 ·
"이것은 ~병입니다"(진단 단정).

## 5. 발행 루틴

```
① 주제 선택       승인된 topic queue 에서 꺼낸다 (drafts/magazine/topic-queue.ts)
                  큐는 사람이 만들고 사람이 고친다. AI 가 주제를 정하지 않는다
② 원고 초안       ChatGPT/Claude 대화창에서 생성 · 글 구조 5단 지시
③ 자동 QA         기계 판정 항목을 먼저 건다. FAIL 이면 창업자에게 올리지 않는다
④ 검수 패킷 생성   요약 5줄 · 위험 문장 5개 · 이미지 · QA 결과 · 권장 판단
⑤ 창업자 승인 ★   riskLevel 이 정한 깊이로 확인 → 승인 / 수정 요청 / 폐기
⑥ 이미지 생성     ChatGPT 등에서 수동 생성 → 내려받아 repo 에 커밋 · alt 필수
⑦ repo 반영       articles.ts + 이미지를 커밋
⑧ QA              typecheck / lint / build + 배포 후 200 · canonical 확인
⑨ 배포            창업자 승인 후 push → Vercel → smoke
```

**⑤가 유일한 필수 게이트다.** 다른 단계는 도구가 바뀌어도 되지만
⑤를 건너뛰면 원칙 5가 무너진다. ③이 ⑤를 대신하지 않는다 — **줄여줄 뿐이다.**

### 5.0 draft 패키지 구조 — 주체별로 파일이 갈린다

글 하나를 만들 때 `drafts/magazine/{slug}/` 아래에 두는 파일이다.
**파일 경계가 곧 §3.0 역할 경계다.**

| 파일 | 누가 쓰는가 | 내용 |
|---|---|---|
| `brief.md` | **원고를 쓰지 않는 Claude 세션** | 검색 의도 분석 · h2 구조안 · **마크다운 출력 규칙** · ChatGPT 지시서 |
| `article-draft.ts` | **ChatGPT 채팅** | **최종 원고** — 마크다운으로 받아 변환기가 형식만 바꾼다 |
| `review.ts` | **원고를 쓰지 않는 Claude 세션** | 요약 5줄 · 위험 문장 5개 · 의료/금전/법률 리스크 · 사실관계 확인 항목 |

템플릿: `drafts/magazine/_template/brief.md` · `drafts/magazine/_template/review.ts`

**"Claude 채팅"이 아니라 "원고를 쓰지 않는 Claude 세션"이다.**
§3.0 의 요건은 도구 이름이 아니라 **분리**다 — 원고를 쓴 주체와 위험 문장을 뽑는 주체가
달라야 한다. 최종 원고는 언제나 ChatGPT 가 쓰므로, brief·review 는 Claude 채팅이 만들든
Claude Code 가 만들든 분리가 유지된다.

⚠️ **단, Claude Code 는 원고를 쓰지 않는다.** 파일을 고칠 수 있는 유일한 주체라
작성 권한까지 가지면 "쓴 사람이 곧 커밋하는 사람"이 되어 원칙 4 가 무너진다.
그래서 ChatGPT 원고는 **blob download 로 파일에 직행**시키고, Claude Code 의 컨텍스트를
거치지 않게 한다 (제작 전략 §9.2).

**`article-draft.ts` 와 `review.ts` 를 나누는 이유**
쓴 쪽과 위험 문장을 뽑는 쪽이 같으면, 위험하다고 판단한 문장은 애초에 원고에 없었을 것이다.
그러면 "위험 문장 5개"는 검증이 아니라 자기 검열의 결과물이 된다.
**두 파일이 갈려 있어야 §5.1 의 MEDIUM 검수가 실제 검증이 된다.**

**Claude Code 는 `review.ts` 를 새로 쓰지 않는다.** 읽어서 검증하고 패킷으로 조립할 뿐이다.
검증 항목 하나가 이 규칙을 기계로 강제한다 — `riskSentences` 의 각 문장이
`article-draft.ts` 본문에 **그대로 존재하는지** 대조하고, 없으면 FAIL 이다
(원고가 수정됐거나 review 가 낡았다는 뜻).

**hero 프롬프트는 `brief.md` 안에 둔다.** 별도 `image-prompts.md` 를 두지 않는다 —
같은 사람이 같은 시점에 쓰는 것이라 파일을 나눌 이유가 없다.

**`seo-qa.md` 는 새 글부터 두지 않는다.**
QA 결과는 `scripts/magazine-qa.mjs` 가 실행 시점에 만들고, 사람이 읽을 형태는 검수 패킷이 맡는다.
손으로 QA 표를 옮겨 적는 일은 중복이고, 옮기는 과정에서 실제 검사 결과와 어긋난다.
⚠️ 이미 있는 `seo-qa.md` 2건(첫 글·두 번째 글)은 **발행 시점 스냅샷**이므로 그대로 둔다.

### 5.1 등급별 검수 패킷

| 구성요소 | LOW | MEDIUM | HIGH |
|---|---|---|---|
| 제목 · 검색 의도 · CTA | ✅ | ✅ | ✅ |
| 5줄 요약 | ✅ | ✅ | ✅ |
| 위험 문장 5개 | — | ✅ | ✅ |
| 이미지 썸네일 + alt + 나이 적합 확인 | 이미지 있을 때 | 이미지 있을 때 | ✅ |
| 자동 QA 결과 | 1줄 요약 | 항목별 | 항목별 |
| **본문 전문** | — | — | ✅ |
| 권장 판단(승인/수정/폐기) + 근거 1줄 | ✅ | ✅ | ✅ |
| 목표 소요 | **30초** | **2분** | 10~15분 |

### 5.2 전문 검수가 강제되는 조건 (등급 무관)

```
□ riskLevel = HIGH
□ 자동 QA FAIL ≥ 1건
□ 특정 질환명을 증상과 연결 / 약·호르몬 치료·영양제 등장 / 검사 수치 언급
□ 세금·연금·보험료의 구체 금액이나 계산식
□ 심장·호흡·출혈·의식 관련 증상
□ 같은 클러스터 직전 글과 제목 유사도 ≥ 0.7
□ 새 클러스터의 첫 글 · 시리즈의 첫 편
□ 직전 3건 중 1건 이상 "수정 요청"이 나온 경우 (톤 드리프트 신호)
```

### 5.3 리듬

```
매일        승인 대기 패킷 확인 → 승인/수정/폐기 (목표 5분 이내)
주 2회      제작 배치 — 큐에서 3건씩 초안 + 이미지 + QA + 패킷 (창업자 관여 0)
주 1회 30분 발행분의 색인·노출 확인 · QA FAIL 이력 · 톤 드리프트 점검 · HIGH 일괄 처리
월 1회 60분 다음 30건 큐 승인 — 주제가 정해지는 유일한 자리
```

**HIGH 는 매일 자리에서 처리하지 않는다.** 주 1회 리뷰로 모아 처리한다(주 최대 2건).
매일 5분 안에 전문 검수를 끼워 넣으려 하면 결국 대충 읽게 된다.

**소요 예상**: 글 1건에 30~60분. 그중 창업자 몫은 LOW 30초 · MEDIUM 2분 · HIGH 10~15분.

## 6. v0 구현 전제

### D1 — v0 는 Git 기반 파일 발행 (확정)

매거진 글을 **repo 안의 콘텐츠 파일**로 관리한다. 커밋 → push → 배포가 곧 발행이다.

**왜 이 방식인가**

1. **원칙 4·5가 구조적으로 강제된다.** 커밋·push 없이는 공개될 수 없고, diff 를 보지 않고 발행할 수 없다.
2. **스키마를 건드리지 않는다.** `Post` 에 slug 가 없고 `authorId` 가 필수인 문제(§9)를 피한다.
3. **이미지가 함께 커밋된다.** 업로드 인프라가 필요 없다.
4. **되돌리기가 `git revert` 한 번이다.**

### 파일 형식 — TS 데이터 파일 + 블록 배열 (6-C 확정)

`src/content/magazine/` 에 **메타데이터 + 본문 블록 배열**을 TypeScript 로 둔다.

```
types.ts     MagazineArticle · MagazineBlock(p/h2/h3/list/callout/image) · MagazineCluster
articles.ts  발행된 글 배열
```

**md + frontmatter 를 쓰지 않는다.** 6-C 감사에서 확인한 근거:

1. **의존성 0.** 파서·렌더러·플러그인을 들이지 않는다.
2. **타입이 SEO 기준을 강제한다.** 이미지 `alt` 는 optional 이 아니라 필수 필드라
   누락하면 빌드가 막는다. `cluster` 오타·slug 형식도 컴파일 타임에 걸린다.
3. **sanitize 가 필요 없다.** 우나어는 DB 에 HTML 을 저장해
   `sanitize-html`(203행) + `dangerouslySetInnerHTML` 이 필요했다.
   우리가 쓴 글만 싣고 HTML 을 쓰지 않으므로 그 표면 자체가 없다.
4. **창업자가 TS 를 직접 쓰지 않는다.** 원고는 대화창에서 나오고 repo 반영은 §5 ⑤ 에서
   Claude Code 가 한다. 창업자는 PR diff 를 검수한다. md 의 작성 편의는 실질 이득이 아니다.
5. **DB 전환 시 손실이 없다.** 블록 배열은 JSON 컬럼에 그대로 들어간다.

🚫 md/frontmatter · markdown parser · sanitize-html · MDX · `dangerouslySetInnerHTML` 도입 금지.

### D2 — URL 은 영문 slug (확정)

```
/magazine/menopause-sleep
/magazine/hot-flash-basics
```

**규칙**: 소문자 · 하이픈 구분 · 주제를 알아볼 수 있게 · 한 번 정하면 바꾸지 않는다.
(slug 변경은 URL 변경이고, 색인된 뒤에는 되돌리기 어렵다)

### D7 — 목록은 쪽으로 나누고 분류는 주소에 둔다 (확정 · 2026-09-21)

v0 의 `/magazine` 은 공개 글을 **한 화면에 전부** 뿌렸고, 분류 칩은 컴포넌트 안의
state 였다. 글이 34건이 되면서 둘 다 한계에 닿았다 — 오래된 글로 내려갈 길이 없고,
고른 분류를 주고받거나 새로고침·뒤로가기로 되찾을 수 없었다.

일반 게시판(PR #553)과 **같은 쪽 이동 UI 를 그대로 쓴다.** 매거진 전용 컴포넌트를 만들지 않는다.

| 항목 | 값 |
|---|---|
| 한 쪽 | **12건** (`MAGAZINE_PAGE_SIZE`) |
| 1쪽 주소 | `/magazine` — `?page=1` 을 붙이지 않는다 |
| 분류 | `/magazine?cluster=sleep` — 전체는 `?cluster=all` 을 붙이지 않는다 |
| 분류 + 쪽 | `/magazine?cluster=sleep&page=2` |
| 분류를 바꾸면 | 쪽이 떨어진다 (1쪽으로) |
| 쪽을 옮기면 | 분류가 따라간다 |
| 모르는 분류 | 전체로 되돌린다 (404 가 아니다) |
| 잘못된 page | 1쪽으로 되돌린다 |
| 범위 초과 page | **404** — 빈 200 은 soft-404 를 만든다 |
| canonical | **지금 보고 있는 목록**(쪽·분류 포함). 2쪽을 1쪽으로 몰지 않는다 |

**규칙 두 가지**

1. 칩은 **공개 글이 실제로 있는 분류만** 세운다. 보고 있는 쪽이 아니라
   공개 글 전체를 기준으로 계산한다 — 쪽을 넘길 때마다 고를 수 있는 것이 달라지면 안 된다.
2. 거르기 → 개수 → 범위 → 자르기는 `resolveMagazineList()` **한 줄기**다.
   목록과 total 이 서로 다른 조건을 쓰면 쪽 수가 실제와 어긋난다.
   화면은 `getMagazineListState()` 로 그 한 줄기를 부르고, 공개 글 스냅샷은
   요청당 한 번만 만든다(`page.tsx` 가 React `cache` 로 묶는다 — 실측 1회).

공개 관문(`getAllMagazineArticles()`)은 그대로다 — 쪽을 나눠도 DRAFT·BLOCKED·예약 글은
목록에도 total 에도 들어오지 않는다. 회귀는 `npm run check:pagination` 이 막는다.

### DB/admin 발행은 보류

**보류 이유**: admin 발행 화면을 만들면 권한·에디터·이미지 업로드가 함께 딸려온다.
우나어 매거진 상세가 410행이 된 경로가 이것이다.
**글이 0건이던 당시**에는 그 복잡도를 미리 만들 이유가 없었다.

**현재(2026-09-21)**: 공개 34건이다. 그래도 아래 전환 조건 셋 중 어느 것도 오지 않았으므로
Git 기반을 유지한다 — 판단 기준은 "글이 있는가" 가 아니라 아래 세 가지다.

### DB/admin 전환 조건

아래 **셋 중 하나**가 오면 재검토한다.

1. 매거진 글 **50건 이상** — 파일 관리가 버거워질 때
2. **창업자 외 편집자 추가** — git 을 요구할 수 없을 때
3. **예약 발행 · 수정 이력**이 실제로 필요해질 때

**셋 중 하나도 오지 않았다면 Git 기반을 유지한다.**

`robots` · `canonical` · `sitemap` 규칙은

### 글 단위 SEO 기준

| 항목 | 기준 |
|---|---|
| `title` | 검색어를 앞쪽에 · 40자 내외 · 낚시성 금지 |
| `description` | 본문 자동 절단이 아니라 **직접 작성** · 요약이지 예고편이 아니다 |
| `canonical` | 자기 경로(`/magazine/{slug}`) · SEO 정책 원칙 4 |
| OG 이미지 | 글 대표 이미지 → 없으면 로고 폴백 |

| 관련글 | **같은 클러스터** 안에서 2~3개(§4.1) |
| internal link | 본문에서 관련 게시판·다른 매거진 글로 연결 · 억지 삽입 금지 |

1. src/app/magazine/page.tsx 의 robots 한 줄 제거      ✅ 완료
2. sitemap.ts 에 /magazine 재포함                      ✅ 완료
3. /magazine/{slug} 는 발행 글만 index                 ✅ 완료 (공개 관문이 판정)
```

**쪼개지 않은 이유**: 먼저 noindex 를 풀면 빈 페이지가 색인되고,
먼저 글만 올리면 색인되지 않는 글이 생긴다. 둘 다 원칙 3(SEO 정책)에 어긋난다.

**여전히 유효한 조건**: 발행 글이 0건으로 돌아가면 noindex 를 다시 건다.
지금은 34건이라 해당하지 않는다.

🔴 **D7 과 모순되지 않는다.** D6 은 "언제 색인을 여는가", D7 은 "열린 목록을
어떤 주소로 나누는가" 다. D7 의 self-canonical 은 D6 이 끝난 뒤라야 의미가 있다 —
noindex 였다면 canonical 값을 크롤러가 읽지 않는다.

| 대상 | 이유 |

| 본문 HTML 파싱 FAQ JSON-LD | 복잡도 대비 실익이 낮다 |
| 목록 필터 **동적 로드** | 분류 칩 자체는 D7 로 넣었다. 버린 것은 지연 로드다 — 파일 기반이라 서버가 이미 전부 알고 있다 |
| 조회 트래커 | 트래킹 금지 |
| 410행 상세 구조 자체 | 통째로 옮기면 관리 불가 |

## 9. 스키마 미결 사항

Git 기반(D1)으로 시작하면 **아래 셋 다 지금은 건드리지 않아도 된다.**
DB/admin 전환을 검토할 때 다시 꺼낸다.

| # | 사실 | 영향 |
|---|---|---|
| **S1** | `Post` 에 **`slug` 필드가 없다** | DB 발행으로 가면 `/magazine/{slug}` 를 위해 스키마 변경이 필요하다 |
| **S2** | `Post.authorId` 가 **필수 + `onDelete: Restrict`** | 매거진 글도 User 행이 있어야 한다. "편집팀" 계정을 만들지 `source: SYSTEM` 으로 둘지 결정이 필요하다 |
| **S3** | Prisma `BoardType` 은 `MENOPAUSE`·`FREE`·`MAGAZINE` — **`BEST` 가 없다** | `board-registry` 의 타입은 4개짜리 superset 이다. 매거진은 DB 개념이지만 베스트는 아니다 |
