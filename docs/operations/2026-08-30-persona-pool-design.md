## §1 이 문서가 정하는 것

Gate ⑤ · ⑨ 판정부와 M3 반응 지도가 main 에 들어갔다.
반응 지도는 **"어떤 역할의 댓글이 붙어야 하는가"** 까지 정했고, 그다음 질문이 남았다.

> **그 역할을 누가 맡을 수 있는가.**

이 문서는 **소란소란 안에 사는 사람들의 명부**를 만든다.

### 왜 지금인가

```
반응 지도가 정한 것        가족 갈등 글에 question .30 · empathy .25 · experience .15 …
                          🔴 그런데 "experience 를 쓸 자격이 있는 페르소나" 가 없으면
                             그 weight 는 아무 의미가 없다

eligibility 는 Persona Pool 없이 정의되지 않는다
```

M3 반응 지도 §5 의 **3단 필터(자격 → 우선순위 → 참여)** 가 전부 Identity 를 입력으로 받는다.
**Pool 이 없으면 반응 지도는 돌지 않는다.**

### retention 과의 관계

```
회원이 두 달 전 시어머니 이야기를 썼고 오늘 또 썼을 때
  "저번에 말씀하신 그 일은 좀 나아지셨어요?" 라고 물을 수 있어야 한다

그 말을 하려면
  ① 그때 그 회원에게 댓글을 단 페르소나가 존재하고
  ② 지금도 살아 있고
  ③ 그 대화를 기억하고 있어야 한다

🔴 매번 새로 태어나는 봇은 관계를 쌓을 수 없다
```

**Persona Pool 은 관계가 쌓일 그릇이다.** 이것이 [전략 §2](2026-08-29-persona-network-strategy.md)의
*"핵심은 기억과 관계"* 를 실행 가능하게 만드는 첫 조각이다.

### 🔴 이 문서가 정하지 않는 것

```
🔴 실제 displayName          §3-2 참조 — 구현 시 중복 검사 후 배정
🔴 생성 프롬프트              Voice Engine 의 몫
🔴 DB schema · migration      Architecture §14 후보를 그대로 따른다
✅ 공개 · 신뢰 정책 확정         외부 비공개 / 내부 어드민 명확 구분 (§9)
```

## §2 규모 설계

| 구분 | 규모 | 근거 |
|---|---|---|
| **설계 풀** | **20~30명** | 정체성 다양성이 확보돼야 대화가 산다 |
| **MVP 초기 활성** | **3~5명** | 회원 4명 규모에서 봇 비율을 통제 |
| **장기** | 수십~수백 | 커뮤니티 성장에 따라 |

### 🔴 "초기 활성 수" 와 "아키텍처 규모" 를 혼동하지 않는다

[전략 §0](2026-08-29-persona-network-strategy.md)이 이미 정정한 실수다.

```
🔴 틀린 추론   회원이 4명이니 페르소나도 3명만 설계한다
               → 작게 설계하면 나중에 정체성 체계를 다시 만들어야 한다

🟢 옳은 순서   풀은 20~30명으로 설계하고, 활성만 3~5명으로 연다
               → isActive 플래그 하나로 규모를 조절한다
```

헌법의 *"active bot 10,000명이 아니라 voice variation 10,000개"* 와 같은 방향이다.
**계정 수는 비용을 선형으로 늘리지만 가치를 늘리지 않는다.**

이 문서는 **20명을 초안으로 제시**한다. 20~30 범위의 하한이고,
운영하며 빈 축이 보이면 10명까지 추가한다.

## §3 Persona 필수 속성 스키마 초안

[Architecture §3](2026-08-30-persona-architecture-design.md)의 필드를 그대로 쓰고,
Pool 운영에 필요한 항목만 추가한다. **새 스키마를 만들지 않는다.**

### §3-1 필드 목록

| 그룹 | 필드 | 값 · 제약 |
|---|---|---|
| **식별** | `personaId` | 내부 코드. 🔴 외부 노출 금지 |

| | `gender` | 🔴 `'female'` 고정 |

### §3-2 🔴 `displayName` 을 이 문서에서 확정하지 않는다

카드에 실제 닉네임을 적지 않고 **코드(`P01`~`P20`)와 성격 라벨**만 둔다.

```
이유 ①  Gate ⑥ 이 회원 닉네임과 실시간 대조한다
        지금 지어 두면 배정 시점에 이미 쓰이는 이름일 수 있다
이유 ②  문서에 20개 닉네임을 박으면 그것이 사실상 상수 배열이 된다
        헌법 §9-6 이 금지한 방식이다
이유 ③  출처 커뮤니티에서 본 닉네임과 우연히 겹칠 위험을 없앤다
```

**작명 정책만 고정한다.**

🔴 공개 정책이 **외부 비공개**로 확정됐으므로([전략 §10-7](2026-08-29-persona-network-strategy.md)),
`displayName` 은 **실제 회원이 쓸 법한 자연스러운 활동 닉네임**이어야 한다.

```
🟢 허용   두세 글자 순우리말 · 일상 사물 · 계절/식물 계열
🔴 금지   AI 티 (숫자 접미 · 영문 혼용 · 봇/AI 연상)
🔴 금지   운영자 티 (운영 주체가 연상되는 이름)
🔴 금지   출처 커뮤니티 호칭 계열
🔴 금지   실명형 · 지역명 포함
🔴 금지   정확한 나이 · 지역 · 병명 · 가족상태가 드러나는 이름
🔴 배정 전 필수   회원 닉네임 · 크롤 author · 기존 페르소나와 중복 검사 (Gate ⑥)
```

🔴 **어드민에서는 `displayName` 뒤가 전부 보여야 한다** — `personaId` · P 코드 · `status` ·
`identity` · `voiceCore` · `voiceVariations` · `mood` · `memory` · `activityRhythm` · `noGo`.
고객에게는 닉네임만 보이지만, 내부에서 닉네임만 보이면 추적이 불가능하다.

### §3-3 🔴 정확한 나이를 쓰지 않는다 — 밴드만

헌법 §9-3 과 Architecture §3 이 `ageBand` 4종으로 고정했다.

```
40대 후반 · 50대 초반 · 50대 후반 · 60대 초반
```

**카드에도 "52세" 같은 정확한 나이를 쓰지 않는다.**
Gate ③ 식별 디테일이 *나이 + 지역 + 가족관계* 결합을 위험으로 보는데,
페르소나 정의에서부터 그 결합을 만들면 생성물에 그대로 흘러나온다.

⚠️ **밴드 4종과 타겟(40대 중반~60대 중반)이 정확히 겹치지 않는다.**
40대 중반과 60대 중반이 밴드에 없다. 헌법 밴드를 넓힐지는 결정 사항(§10-①).
이 문서는 **현행 4밴드를 따른다.**

## §4 Pool 구성 원칙

### §4-1 다섯 축에 고르게 배치한다

M3 반응 지도의 글 유형 5종에 각각 **깊이 반응할 수 있는 사람**이 있어야 한다.

| 축 | 인원 | 이 축에서 `experience` 가능 |
|---|---|---|
| 가족 · 관계 갈등 | 5 | 자녀 갈등 · 시댁 · 남편 갈등 경험 보유 |
| 건강 · 갱년기 · 병원 | 4 | 갱년기 진행/후 · 간병 경험 |
| 돈 · 일 · 자산 | 4 | 구직 · 자영업 · 은퇴 후 형편 |
| 외로움 · 감정 토로 | 3 | 사별 · 이혼 · 독거 |
| 생활 정보 · 잡담 | 4 | 취미 · 살림 · 손주 |

🔴 **한 사람이 한 축만 담당하지 않는다.** 주축 하나에 부축 1~2개를 준다.
사람은 한 가지 주제만 말하지 않는다.

### §4-2 균형 지표

```
ageBand         40대 후반 5 · 50대 초반 6 · 50대 후반 5 · 60대 초반 4
maritalStatus   기혼 12 · 이혼 3 · 사별 2 · 별거 1 · 비혼 2
childrenCount   0명 4 · 1명 5 · 2명 9 · 3명 2
parentCare      없음 11 · 간헐 6 · 상시 3
workStatus      전업 6 · 파트타임 5 · 자영업 3 · 구직 2 · 은퇴 4
economicStatus  여유 3 · 보통 9 · 빠듯 6 · 어려움 2
region          수도권 7 · 광역시 6 · 중소도시 4 · 읍면 3
menopause       전 4 · 진행중 8 · 후 8
```

### §4-3 🔴 극단적 캐릭터를 만들지 않는다

```
🔴 금지   "빚 3억에 남편 도박에 자녀 셋 다 아픈" 식의 사연 집약
          → 드라마지 사람이 아니다. 그리고 식별 디테일 위험이 커진다

🟢 원칙   한 사람에게 **뚜렷한 축 하나 + 평범한 나머지**
          실제 소란소란에 있을 법한 조합이어야 한다
```

**어려움 2명 · 갈등 관계 3명으로 제한**한 이유가 이것이다.
힘든 사람만 모인 커뮤니티는 현실이 아니다.

## §4-1 🔴 정본 셋의 역할 — 무엇이 무엇을 정하는가 (2026-09-13 확정)

같은 Persona 를 세 곳이 들고 있다. **역할이 다르다.** 헷갈리면 한쪽만 고쳐진다.

| 정본 | 무엇 | 코드 근거 | 누가 읽나 |
|---|---|---|---|
| **이 문서 §5 카드** | Persona **정체성 원본** — 결혼·자녀·돌봄·갱년기·말투 | `persona-pool-card.parsePoolDoc` → `cardToPersona` | **생성 전** 선택 (`voice-persona-plan.planVoicePersonas`) |
| **production cohort** | 실제로 쓰는 **code universe** (24명) | `src/lib/persona-cohort.ts` `PRODUCTION_PERSONA_CODES` | 말투 자산 배정 (`planBundles`) |
| **운영 DB `Persona.identity`** | 발행 시점의 **집행 정본** — 여기에 없으면 발행되지 않는다 | `scripts/original-post-auto-publish.mts` `identity.childrenCount` 등 **top-level** | **발행 직전** `hardFilter` |

### 🔴 한 줄 원칙

```
카드 = 누구인가            (생성이 본다)
cohort = 누가 나가는가      (자산이 본다)
DB   = 지금 무엇으로 발행되는가 (발행이 본다)
```

`P09` 는 카드에는 있으나 cohort·DB 에 없다 — `persona-cohort.EXCLUDED_CODES` 에 이유가 적혀 있다.

### 🔴 밴드는 **두 가지 뜻**으로 쓰인다 — 대조할 때 섞지 않는다

| 어디 | 무엇을 담나 | 예 (P17) |
|---|---|---|
| **카드 파서** `readChildren` | 매칭이 쓸 **고유 밴드 집합** — 중복 없이 모은다 | `['성인']` |
| **운영 DB** `identity.childrenAgeBands` | **자녀 한 명당 한 칸** — 몇 명이 어느 나이대인지 | `['성인','성인']` = 성인 자녀 2명 |

`['성인','성인']` 은 **오류 중복이 아니다.** 지우면 자녀 수 정보가 사라진다.
두 정본을 맞대 볼 때는 **고유 밴드 집합끼리** 비교한다 —
`hardFilter` 도 `bands.includes(...)` 로 포함 여부만 보므로 중복은 판정을 바꾸지 않는다.

자녀 나이대의 확정 정본은 **`scripts/persona-children-age-bands.mts` (2026-09-02 창업자 확정)** 이다.
2026-09-13 대조에서 P05 카드가 `중고생·초등` 으로 어긋나 있어 **카드를 확정값에 맞춰 고쳤다**
(`대학생·중고생`). DB 는 건드리지 않았다.

### 🔴 `identity` 는 **평평하다**

```
identity.childrenCount      ✅  identity.children.count     ❌ 없는 경로
identity.childrenAgeBands   ✅  identity.children.ageBands  ❌ 없는 경로
```

중첩으로 읽으면 **전원이 무자녀로 판정된다.** 2026-09-07 에 P10·P17 이 이렇게 부당 차단됐고,
2026-09-13 검증 중 임시 스크립트가 같은 실수를 반복해 "DB 24명 전원 무자녀" 라는
잘못된 결론을 냈다. 생산 경로 3곳(`original-post-auto-publish` · `persona-capacity-planner` ·
`supply-health`)은 **전부 평평하게 읽고 있다** — 코드로 확인했다.

> | P13 | 카드 | `중간~긴 문장` → `길게(아주 길지는 않은 편)` | 방향은 §7-1 `긴` 과 같다. 매칭이 `중간~긴` 을 **보통**으로 읽어 방향이 뒤집혀 있었다 |
> | P01 | §7-1 | `중간` 목록 → `짧음` 목록 | 카드가 `짧은 문장` 으로 명확하다 |
> | P16 | §7-1 | `중간` 목록 → `짧음` 목록 | 카드가 `짧음` 으로 명확하다 |
> | P05 · P10 · P14 | §7-1 | 목록에 **추가** | 어느 밴드에도 없어 완전성이 깨져 있었다 |
>
> 🔴 **뉘앙스를 지우지 않았다.** P13 의 "아주 길지는 않은 편" 을 괄호로 보존했다.
>
> ⚠️ 괄호 안 표현을 고를 때 주의할 것이 있다. `readLengthBand` 의 별칭은
> **`보통(중간·보통)` → `짧게(짧)` → `길게(길)` 순서로 검사**한다. 그래서 괄호에 "중간" 이
> 들어가면 `길게(중간보다 조금 긴 편)` 처럼 써도 **`보통` 으로 읽힌다** — 실측으로 잡았다.
> 밴드를 바꾸고 싶지 않다면 다른 밴드의 별칭 단어를 괄호 안에 넣지 않는다.
>
> 🔴 **P09 는 고치지 않는다.** §7-1 세 목록 어디에도 없고 카드에도 길이 표현이 없다.

> §7-1 의 **`길이 미상`** 줄에 명시해 두고 planner 후보에서 계속 제외한다 —
> 지금 미상은 P09 하나뿐이다.
>
> `persona:planner-check` 가 §7-1 과 카드의 정합, 그리고 **20명 전원이 정확히 한 번씩**
> 어느 목록에 들어 있는지를 검사한다. 새로 어긋나거나 빠지면 CI 가 잡는다.

> 🔴 `displayName` 은 §3-2 정책에 따라 구현 시 배정한다. 여기서는 코드와 라벨만 쓴다.

## §7 AI 티 방지 설계

Pool 차원에서 거는 장치다. [M3 §4-7](2026-08-30-m3-reaction-map-design.md)의 8종을 페르소나에 매핑한다.

| 방지 대상 | Pool 차원 장치 | 근거 필드 |
|---|---|---|
| 같은 말투 반복 | `voiceVariations` **5~8개** · 직전 3회 제외 | 카드 variation |
| 같은 시작 문장 반복 | variation 별 `hookType` 분산 · 무호칭 옵션 필수 | 카드 variation |
| 같은 ending 반복 | `voiceCore` 말끝을 페르소나마다 다르게 배정 | §5 카드 |
| 같은 seed 반복 | `seedReuseRate` — 🔴 전체 단위로 본다 | Gate ⑧ |
| **같은 글에 같은 맞장구** | 🔴 글 단위 seed 배분 · `maxPerRole` | M3 §4-1 |
| 너무 빠른 반응 | `activityRhythm` — 페르소나별 활동 시간대 분산 | §3-1 |
| 너무 균일한 댓글 수 | `commentCount` range 추첨 + `silenceRate` | M3 §4-2 |
| 정리된 문장 · 마크다운 | 🔴 `noGoExpressions` 에 전원 공통 등록 | §7-2 |

### §7-1 말투 축을 겹치지 않게 배분한다

```
문장 길이     짧음 P01 P04 P05 P08 P15 P16 P18 P19 P22 P25 · 중간 P02 P07 P10 P12 P14 P20 P21 P24 · 긴 P03 P06 P11 P13 P17 P23
길이 미상     P09  🔴 카드에도 위 목록에도 근거가 없다 — 추정하지 않고 비워 둔다
이모티콘      없음 P02 P04 P06 P08 P09 P12 P15 P18 P19 P21 P22 P23 · 가끔 P01 P05 P14 P20 P24 P25 · 자주 P03 P11 P13 P17
오타          없음 P04 P09 P23 · 가끔 P05 P12 P19 P20 P22 P24 P25 · 잦음 P03 P10 P11 P13 P17
말끝          ~해요 / ~네요 / ~더라고요 / ~같아요 를 분산 배정
```

🔴 **25명이 같은 축에 몰리면 variation 을 아무리 늘려도 티가 난다.**

### §7-2 전원 공통 `noGoExpressions`

```
🔴 "추천드립니다" · "도움이 되셨으면 좋겠습니다"
🔴 먼저/다음으로/마지막으로 구조화 · 불릿 · 번호 · 마크다운
🔴 과도한 존댓말 일관성 · 이모지 남용
```

## §8 Memory 설계

### §8-1 네 갈래

| 종류 | 무엇을 담나 | 보존 | 🔴 담지 않는 것 |
|---|---|---|---|
| **Self Memory** | 이 페르소나가 과거에 한 말 · 설정한 사실 | 영구 | 원문 전문 — 요약만 |
| **Relationship Memory** | 특정 회원과의 관계 | §8-2 | 🔴 회원이 공개하지 않은 것 |
| **Topic Memory** | 자주 반응한 주제 · 반응 유형 | 롤링 | 개별 글 원문 |
| **Negative Memory** | 이 회원에게 피해야 할 말 · 실패한 반응 | 영구 | 회원 평가 · 낙인 |

### §8-2 🔴 Relationship Memory 원칙

```
🟢 저장한다   회원이 **직접 공개한 사실** { factKey, summary, statedAt, sourcePostId }
             반복되는 고민 주제 · 불편해한 주제(doNotMention) · 거리감 수치

🔴 저장하지 않는다
   추론한 사실          "이 정도면 이혼했겠네"
   진단 · 평가          건강 상태 추정 · 성격 판단
   회원의 원문 문장      요약만 둔다
   회원 닉네임 원문      Gate ⑥ — 참조는 userId 로
```

**과하면 무섭다.** 회원이 말하지 않은 것을 페르소나가 알고 있으면 온기가 아니라 감시다.

```
🟢 가능   "저번에 말씀하신 그 일은 좀 나아지셨어요?"
🔴 금지   "○○ 때문에 힘드셨죠?"     ← 회원이 원인을 말한 적 없다
🔴 금지   "지난번보다 좋아 보이세요"  ← 상태를 평가한다
```

### §8-3 요약 축약 원칙

```
6개월 경과   상세 → 한 줄 요약
12개월 경과  한 줄 → 주제 태그만
🔴 언제든    회원이 그 주제를 doNotMention 에 넣으면 즉시 참조 중단
```

**기억은 쌓이기만 하면 부담이 된다.** 오래된 것일수록 흐릿해지는 것이 사람에 가깝다.

### §8-4 🔴 삭제 · 탈퇴 시

```
회원 탈퇴        해당 RelationshipMemory **즉시 전량 삭제** — 익명화가 아니라 삭제
글 삭제          그 글을 sourcePostId 로 가진 항목 삭제
회원 요청        해당 factKey 삭제 · doNotMention 에 등록
페르소나 은퇴     Self Memory 보존(이력) · Relationship Memory 삭제
```

🔴 **"관계를 기억한다" 는 것이 "지우지 않는다" 는 뜻이 아니다.**

| 생성 · 승인 · 수정 · 폐기 이력 | 🔴 전건 기록 — 어드민 요건 |
| Gate 통과의 의미 | 🟢 1단계 승인 대기열 · 2~3단계 발행 가능 후보 ([전략 §4-1](2026-08-29-persona-network-strategy.md)) |

### 🔴 외부 비공개와 "실제 회원인 척하는 장치" 는 다르다

```
🔴 하지 않는다   실제 회원처럼 보이게 하는 장치
                 (가입일 위조 · 활동 이력 조작 · 실명형 닉네임)
🟢 한다          사람처럼 자연스러운 말투와 리듬
```

**둘은 다르다.** 앞은 이력을 조작하는 것이고 뒤는 어색하지 않게 만드는 것이다.
외부 비공개는 **표시를 하지 않는 것**이지 **없는 이력을 만들어내는 것**이 아니다.
카드의 `noGo` 가 전부 뒤쪽에 있고 앞쪽 장치는 하나도 없다.

🔴 가입일 · 활동 이력 조작 여부는 **이 문서가 결정하지 않는다** — 별도 결정 사안이다.
