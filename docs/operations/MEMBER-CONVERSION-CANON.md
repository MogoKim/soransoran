# 소란소란 콘텐츠 완독 → 회원가입 전환 정본

> 문서 상태: **v3.0 · 상위 프로젝트 재정의 — 고객 구성 기준선은 완료된 보조 측정 축으로 재배치**
> 마지막 창업자 싱크: **2026-10-06 KST**
> 현재 단계: **M1 — 전환 경로 읽기 전용 진단 (제품 구현 전)**
> 기획·검증 책임: **Codex [2] 회원가입 전환 마스터**
> 실행 책임: **Claude [2] — 승인된 한 단계씩**

## 0. 이 문서의 역할

이 문서는 **유입된 비회원이 콘텐츠를 읽고 가입·첫 참여로 이어지는 전환 프로젝트**의 단일 기획 정본이다.

- 운영 문서의 권위 지도는 [`README.md`](./README.md)를 따른다. 이 문서는 그 지도 안의 **전환 영역 프로젝트 정본**이다.
- 고객·제품 본질·장기 North Star는 [`NORTH-STAR.md`](./NORTH-STAR.md)가 정한다. 이 문서는 그보다 상위 권위가 아니다.
- D100 콘텐츠 자동화의 단계·정책·현재 상태는 D100 canon과 [`CURRENT-MILESTONE.md`](./CURRENT-MILESTONE.md)가 정한다.
  이 문서의 M0~M7은 **전환 프로젝트 단계**이며 D100 단계와 별개다.
- 전환 정책·계측·가입 경로의 의미는 이 문서가 정한다. 콘텐츠 내용과 발행은 정하지 않는다.
- 코드·DB·카카오 콘솔·Vercel 변경은 이 문서만으로 자동 승인되지 않는다. 단계마다 별도 승인한다.
- 기획이 바뀌면 구현보다 먼저 이 문서를 고친다.

### 문장 상태

| 표기 | 뜻 |
|---|---|
| `확정` | 창업자와 합의한 방향 |
| `관측` | 현재 코드·DB·콘솔에서 확인한 사실 |
| `제안` | 진단 뒤 승인할 수 있는 안 — 아직 승인되지 않음 |
| `보류` | 지금 만들지 않는 후속 범위 |

## 1. 프로젝트 정의

| 항목 | 정본 |
|---|---|
| 프로젝트명 | **소란소란 콘텐츠 완독 → 회원가입 전환** |
| 목적 | 유입된 비회원이 콘텐츠를 충분히 읽은 뒤 방해받지 않는 가입 제안을 받고, 실제 목표 여성 회원으로 가입하고 첫 참여까지 이어지게 한다 |
| 핵심 고객 | **50대 여성 → 40대 후반 여성 → 60대 초·중반 여성** |
| 남성 | 핵심 전환·고객 지표에서 제외한다. 현재 가입 접근 정책 자체는 별도 승인 없이 바꾸지 않는다 |
| 콘텐츠 내용과 발행 | Codex [1]·Codex [3]의 책임 |
| 전환 정책·계측·가입 경로 | Codex [2] 마스터의 책임 |
| 실행 | Claude [2]가 승인된 한 단계만 수행 |

### 상위 전환 흐름 `확정`

```text
콘텐츠 유입
→ 콘텐츠를 충분히 읽음
→ 가입 제안
→ 카카오 인증 시작
→ 온보딩 시작
→ 가입 완료
→ 첫 글 또는 댓글
→ 이후 재방문·참여
```

### 한 줄 정본

> **읽을 만큼 읽은 비회원에게 방해하지 않는 가입 제안을 하고, 목표 여성 회원의 가입과 첫 참여로 잇는다.**

## 2. 측정의 세 축

이 프로젝트는 세 가지를 섞지 않고 따로 본다.

| 축 | 질문 | 상태 |
|---|---|---|
| 1. 전환 퍼널 | 유입이 가입을 얼마나 만드는가 | 완독부터 가입 완료까지 연결된 **통합 전환 기준선은 아직 없음**. 기존 부분 계측은 M1에서 재사용 가능 여부를 확인 |
| 2. 고객 구성 | 가입자가 목표 여성·연령대와 맞는가 | **완료** — 고객 구성 어드민 Production 검증 완료(§12) |
| 3. 가입 후 참여 | 가입자가 글·댓글과 재방문으로 이어지는가 | 일부 완료 — 글·댓글·7일 내 참여는 고객 구성 어드민에 있음. 재방문은 측정 불가 |

- 2026-10-06 Production에서 완료된 **고객 구성 어드민과 운영 실측은 보존**한다(§12).
- 고객 구성 기준선은 이 프로젝트의 **완료된 보조 측정 축**이다. 전체 프로젝트의 최종 목표나 현재 대기 단계가 아니다.
- 재방문 계측 자체의 정의와 North Star 측정은 [`NORTH-STAR.md`](./NORTH-STAR.md)와 `CURRENT-MILESTONE.md`가 맡는다.
  이 프로젝트는 그 측정이 생기면 가입 코호트와 연결하는 쪽만 다룬다(M7).

## 3. 현재 문제 정의

- 현재 유입과 회원 수가 매우 적어 **단순 관측만으로는 개선이 일어나지 않는다.**
- 표본 1명의 비율로 시장이나 고객 가설을 결론 내리지 않는다.
- 그렇다고 유입이 커질 때까지 **아무것도 하지 않고 기다리지 않는다.**
- 지금 할 일은 전환 경로·계측·정책을 준비하는 것이다.
- **정책과 측정 기준 없이 팝업부터 구현하지 않는다.**

## 4. 제안 중인 제품 흐름 `제안`

```text
콘텐츠 유입 → 충분한 읽기 → 가입 제안 노출 → 가입 제안 클릭
→ 카카오 인증 → 온보딩 → 가입 완료 → 첫 참여
```

가입 제안을 한다는 것은 `확정`된 방향이다(§1). 그 제안을 **어떤 UI로 할지**는 아래 `제안` 상태이며,
M1 진단과 M2 정책 결정 뒤에 승인할 구현 후보다.

### 하단 가입 제안(바텀 시트) — 현재 상태

| 항목 | 정본 |
|---|---|
| 위치 | 유력한 첫 전환 장치 |
| 승인 상태 | **아직 구현 승인 전** |
| 형태 | 전체 화면을 막는 강제 팝업이 아니라 **비차단형 바텀 시트 우선 검토** |
| 사용성 | 모바일에서 닫기 쉽고 콘텐츠 소비를 방해하지 않아야 한다 |
| 대상 | **비회원에게만** 노출 |

구현 전에 먼저 정해야 하는 것(M2):

1. 완독 기준 — 무엇을 "충분히 읽었다"로 볼 것인가
2. 노출 대상 콘텐츠 — 어떤 콘텐츠 유형에서 먼저 보일 것인가
3. 노출 빈도 — 한 사람에게 얼마나 자주 보일 것인가
4. 닫은 뒤 재노출 — 닫으면 언제 다시 보일 것인가
5. 가입 후 복귀 위치 — 가입을 마친 뒤 어디로 돌아갈 것인가

## 5. 최소 측정 후보 `제안`

현재 설계 후보는 다음 여덟 단계뿐이다.

1. 콘텐츠 조회
2. 콘텐츠 완독
3. 가입 제안 노출
4. 가입 제안 클릭
5. 카카오 인증 시작
6. 온보딩 시작
7. 가입 완료
8. 첫 글 또는 댓글

- 개인정보, 콘텐츠 제목·본문, 회원 ID를 분석 이벤트로 복제하지 않는다.
- GA4로 충분한지, 어드민 표시를 위해 최소 서버 데이터가 필요한지는 **M1 읽기 전용 진단 후 결정**한다.
- 처음부터 범용 이벤트 원장·복잡한 `flow_id`·데이터 웨어하우스를 확정하지 않는다.
- `관측`(CB-M1, 2026-10-06): GA4 `sign_up`은 온보딩 성공 뒤 클라이언트에서 보내는 이벤트라 서버 가입 완료의
  정본이 아니다. 가입 완료 시각의 서버 근거는 최초 `Agreement(TERMS_OF_SERVICE).agreedAt`이다(§12 CB-3).
  나머지 단계의 현재 계측 여부는 M1에서 다시 확인한다.

## 6. 개인정보 방침

- 기존 카카오 성별·출생연도·이메일·전화번호 수집을 **삭제하거나 축소하지 않는다.**
- 고객 구성과 향후 고객 운영을 위한 기존 값은 유지한다.
- **전화번호 보유가 바로 마케팅 메시지 발송 권한을 뜻하지는 않는다.**
- 카카오 메시지 발송은 이번 단계 범위가 아니다.
- 마케팅 발송 전에 동의·철회·제외·발송 이력을 별도로 설계한다.
- 어드민과 분석은 집계만 보여 주며 이메일·전화번호를 분석 차원으로 쓰지 않는다.
- 현재 공개 개인정보 문구와 실제 수집·마케팅 동의 기록 사이의 불일치는 별도 정합성 작업으로 남긴다.
  문구가 정리되기 전에는 새 마케팅 발송을 시작하지 않는다.

- 저유입 단계이므로 초기에는 **복잡한 A/B 테스트나 통계적 승자를 주장하지 않는다.**
  한 번에 하나씩 바꾸고 절대 수치와 실제 사례를 함께 본다.
- 고객 구성의 7일·28일 관측(첫 7일 2026-10-13 KST, 첫 28일 2026-11-03 KST)은 **보조 모니터링**으로
  유지한다. 다음 전환 작업을 막는 대기 조건이 아니다.
- 구현 완료와 운영 숫자 검증은 별도로 판정한다.

## 8. 현재 단계의 금지

현재 M1 읽기 전용 진단 단계에서는 다음을 하지 않는다.

- 바텀 시트 구현
- 가입 화면 변경
- 새 DB 테이블·migration
- 카카오 콘솔 변경
- 마케팅 메시지 발송
- Production 배포
- 복잡한 A/B 플랫폼
- 개인정보 이벤트 복제

## 9. 역할

### 창업자

- 고객 가설과 사업 우선순위 결정
- 전환 장치의 노출 정책과 DB migration·merge·Production 배포 승인
- 전환 결과를 보고 콘텐츠·가입 개선·마케팅 우선순위 결정

### Codex [2] 마스터

- 이 문서와 전환 프로젝트 범위 관리
- 전환 정책·계측·가입 경로 설계와 Claude 실행 계약 작성
- 지표 의미와 PASS/FAIL 독립 검증
- Codex [1]·Codex [3]에 전환·고객 구성 결과와 한계 전달

### Claude [2]

- 승인된 한 단계만 진단·구현·검사·보고
- 지표 의미·노출 정책·보관기간을 임의로 결정하지 않음
- 승인 없는 migration·merge·Production 배포 금지
- 다른 Codex·Claude 세션과 worktree·브랜치·파일을 공유하지 않음 — 단계마다 지정된 전용 worktree만 사용

### Codex [1]·Codex [3]

- 콘텐츠 주제와 발행 결정 — 전환·고객 구성 집계는 참고 자료
- 이 프로젝트의 계측·집계 로직을 병행 수정하지 않음

## 10. 변경 절차

범위를 바꿀 때는 다음을 확인한다.

1. 이 변경이 목표 여성 비회원의 가입이나 첫 참여를 실제로 늘리는 데 필요한가?
2. 기존 화면·이벤트·데이터로 해결할 수 있는가?
3. 콘텐츠를 읽는 사람의 경험을 해치지 않는가?
4. 측정 기준 없이 구현부터 하고 있지 않은가?
5. 후속 단계로 미뤄도 지금 단계의 판단이 정확한가?

후속으로 미룰 수 있으면 지금 넣지 않는다. 같은 결정을 여러 문서에 복제하지 않는다.

## 11. 현재 다음 행동

현재 단계는 **M1 읽기 전용 진단**이다. Codex [2]의 진단 계약에 따라 아래 경로의 현재 상태를 코드·화면·계측 근거로 분류한다.

1. 공개 콘텐츠 화면 — 커뮤니티 글 상세·매거진 글에서 비회원이 보는 것
2. 기존 CTA — 글쓰기·로그인 유도 등 이미 있는 가입 진입점
3. GA4 이벤트 — 현재 보내는 이벤트와 빠진 단계
4. 카카오 인증 시작과 실패·이탈 경로
5. 온보딩 시작·완료
6. 가입 완료의 서버 근거
7. 첫 글 또는 댓글
8. 가입 후 복귀 위치

M2 정책 결정을 창업자에게 올린다.

카카오 설정과 고객분석의 관계: 카카오는 성별·출생연도 등 원재료를 제공하고, 회원 DB는 회원별 원래 값을

사실만으로 연령대별 실제 활동이 계산되지 않으므로, 기존 DB에서 안전하게 집계한다.

### CB-1. 분석 대상

다음을 모두 만족하는 회원만 핵심 고객 지표에 넣는다.

1. 카카오 인증 계정이 있는 실제 회원
2. 현재 `isOnboarded=true`인 가입 완료 회원
3. 저장된 성별이 `female`로 확인된 회원
4. Persona·운영자·관리자·봇·시험용 운영 예외 계정이 아닌 회원

운영·시험 계정은 `User.isAdmin`, `SORAN_ADMIN_EMAILS`, `SIGNUP_ALLOWLIST`, Persona 관계,
OperatorWriter 관계를 모두 확인해 제외한다. `SIGNUP_ALLOWLIST`는 이메일뿐 아니라 카카오 계정 ID 예외도
포함하므로 두 종류를 모두 처리한다. 이 제외 조건은 고객 구성 전용으로 만들며 공용
`REAL_MEMBER_WHERE`의 의미는 바꾸지 않는다.

| 대상 | 처리 |
|---|---|
| 확인된 남성 | 핵심 고객 수와 비율에서 제외 |
| 성별 미확인 | 여성으로 추정하지 않고 `성별 미확인`으로 별도 표시 |
| 출생연도 미확인 | 여성 전체에는 포함하되 연령 분석에서 `연령 미확인`으로 표시 |
| Persona·운영자·관리자·봇 | 모든 실제 고객 지표에서 제외 |
| `SIGNUP_ALLOWLIST` 시험·운영 계정 | 모든 실제 고객 지표에서 제외 |
| 가입 미완료 계정 | 가입 완료 고객 수에서 제외 |
| 차단된 실제 여성 회원 | 고객 구성에는 포함하고 차단 수를 별도 표시하되 현재 참여 지표에서는 제외 |

`관측`: 현재 가입 정책은 확인된 신규 남성을 차단하지만 기존 계정과 성별 미확인 계정은 통과시킨다.
고객 구성은 이 접근 정책을 변경하지 않고, 핵심 고객 지표에는 확인된 여성만 넣어 숫자가 섞이지 않게 한다.

### CB-2. 연령 구간

현재 저장되는 값은 생년월일 전체가 아니라 `birthyear`다. 연령대 구성과 참여 분석에는 출생연도로 충분하다.

```text
45세 미만
45~49세
50~54세
55~59세
60~64세
65~69세
70세 이상
연령 미확인
```

- 50대 전체 요약과 `50~54`·`55~59` 상세를 함께 제공한다.
- 출생연도만으로 생일 전후의 정확한 만 나이는 알 수 없다.
- `기준연도 - 출생연도`를 **분석연령**으로 사용하고 화면에서 만 나이라고 부르지 않는다.
- 원본 `birthyear`는 그대로 보관하고 `ageBand`를 회원 테이블에 중복 저장하지 않는다.
- 잘못된 형식이나 미래 출생연도는 `연령 미확인`으로 분류해 데이터 문제를 숨기지 않는다.

### CB-3. 최소 지표

**고객 구성**

- 가입 완료한 실제 여성 회원 수
- 연령 구간별 회원 수와 비율
- 성별 미확인 수
- 연령 미확인 수

**실제 참여** — 연령 구간별로 다음을 집계한다.

- 글을 한 번 이상 작성한 실제 회원 수
- 댓글을 한 번 이상 작성한 실제 회원 수
- 글 또는 댓글을 한 번 이상 작성한 실제 회원 수
- 게시판별 글 작성 회원 수와 댓글 작성 회원 수
- 가입인사를 작성한 실제 회원 수 — 일반 글 참여와 분리

주 참여 지표는 현재 유효한 공개 활동만 센다.

- 글: 실제 회원이 작성한 `PUBLISHED` 글만 포함하고 `HIDDEN`·`DELETED`는 제외한다.
- 일반 글 참여: `category='가입인사'` 글을 제외한다.
- 가입인사: 일반 글과 합치지 않고 고유 작성 회원 수를 별도로 표시한다.
- 댓글: `commentOrigin='MEMBER'`이고 삭제되지 않았으며 공개 글에 남은 댓글만 포함한다.
- 차단 회원의 과거 활동은 현재 참여 지표에서 제외한다.
- 한 회원이 여러 건을 작성해도 `참여 회원 수`에서는 한 명으로 센다. 행동 건수와 혼용하지 않는다.

개별 회원의 활동 목록을 보여주지 않는다. 콘텐츠 팀에는 연령 구간·게시판 단위의 집계만 전달한다.

**가입 후 7일 내 참여**

> 가입 완료 뒤 7일 안에 글이나 댓글을 남긴 실제 여성 회원 수

이 지표만으로 **재방문**까지 증명하지 않는다. 같은 가입 세션에서 바로 참여했을 수도 있기 때문이다.
현재 시스템에는 별도의 재방문 증거가 없으므로 어드민은 `7일 내 참여`로만 표시한다.

`관측`: `User.createdAt`은 인증 계정 생성 시각이지 가입 완료 시각이 아니다. 가입 완료일로 사용하지 않는다.

`확정`: 새 `onboardedAt` 컬럼을 추가하지 않는다. 온보딩 완료 트랜잭션에서 함께 기록되는 가장 이른
`Agreement(TERMS_OF_SERVICE).agreedAt`을 **가입 완료 시각의 제한적 근거**로 사용한다.
`User.createdAt`, `profileConsentAt`, `marketingConsentAt`, 가입인사 시각, GA4 `sign_up`은 대신 사용하지 않는다.

- 화면과 코드에서 Agreement 시각을 일반적인 계정 생성일과 혼동하지 않는다.
- 약관 동의 기록이 없는 과거 회원은 임의 날짜로 보정하지 않고 `7일 지표 산정 불가`로 분리한다.
- 특정 커밋일이나 마이그레이션 날짜를 운영 적용일로 간주해 하드코딩하지 않는다.
- 가입 완료 후 7일이 아직 지나지 않은 회원은 실패가 아니라 `관측 중`으로 분리한다.
- 향후 재동의 흐름이나 Agreement 작성 경로가 추가되면 이 근거를 다시 검토한다.

가입 완료 시각이 없는 과거 회원은 현재 구성·누적 참여에는 포함할 수 있지만, 정확한 7일 내 참여율의
분모에는 넣지 않는다.

### CB-4. 최소 어드민

경로는 `/admin/members/composition`이고 기존 회원 화면에서 링크한다. 상위 운영 메뉴는 늘리지 않으며
기존 `회원` 메뉴가 활성 상태를 유지한다.

첫 화면:

1. 실제 여성 가입 완료 회원 총수
2. 연령대별 인원과 비율
3. 성별·연령 미확인 수와 차단 고객 수
4. 연령대별 글·댓글 참여 회원 수
5. 가입인사 고유 작성 회원 수 — 일반 글과 분리
6. 연령대별 7일 내 참여 회원 수 — Agreement 근거가 있고 관측이 끝난 코호트부터
7. 7일 관측 중 수와 과거 산정 불가 수
8. 게시판별 참여 회원 수
9. 데이터 기준일과 집계 한계 안내

표시 원칙:

- 개인별 이름·닉네임·이메일·전화번호를 이 화면에 표시하지 않는다.
- 비율에는 실제 인원인 분자와 분모를 함께 표시한다.
- 표본이 작을 때는 퍼센트만 강조하지 않는다.
- 오늘의 작은 변동보다 누적·7일·28일 흐름을 우선한다.
- 아직 7일이 지나지 않은 신규 회원을 미재참여로 계산하지 않는다.
- 과거 데이터와 신규 정확 측정 코호트를 섞지 않는다.

### CB-5. 가볍게 구현하는 원칙

1. 기존 `User`, `Account`, `Post`, `Comment`를 먼저 사용한다.
2. 고객 구성은 서버 집계 쿼리로 계산하고 별도 데이터 웨어하우스를 만들지 않는다.
3. `gender`, `birthyear`, 이메일, 전화번호를 새 이벤트 테이블에 복사하지 않는다.
4. 연령 구간은 조회 시 계산하고 회원마다 중복 저장하지 않는다.
5. 새 범용 이벤트 원장이나 분석 SDK를 만들지 않는다.
6. 새 DB 필드는 정확한 지표에 반드시 필요하다는 진단 증거와 창업자 승인이 있을 때만 추가한다.
7. 조회 성능 문제는 실제 쿼리 증거가 있을 때만 인덱스로 해결한다.
8. 집계 오류가 회원가입·로그인·글쓰기·댓글을 막아서는 안 된다.
9. 전체 Post·Comment 행을 무제한으로 애플리케이션 메모리에 가져오지 않는다. DB의 `count`, `groupBy`,
   관계 존재 조건을 우선하고 불가피한 행 조회는 대상과 기간을 제한한다.

로직은 `대상 필터`, `연령 구간 계산`, `집계 쿼리`, `어드민 표시` 네 부분으로 제한한다.
