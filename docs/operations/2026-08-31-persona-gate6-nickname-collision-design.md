## §1 목적

페르소나 `displayName` 을 작명하기 **전에**, 아래와 충돌하지 않는지 검사하는 설계를 고정한다.

```
🔴 실회원 표시명
🔴 크롤 author
🔴 기존 persona displayName
🔴 출처 커뮤니티 marker
🔴 운영자 / AI 느낌 이름
🔴 정확한 나이 · 지역 · 병명 · 가족상태가 드러나는 이름
```

### 🔴 이 문서가 정하지 않는 것

```
🔴 실제 displayName 작명       — 이 설계가 승인된 뒤에 한다
🔴 판정부 구현 · fixture 작성
🔴 DB schema · migration
🔴 정규화 해시 컬럼 신설 여부   — §4-3 창업자 결정
🔴 유사도 임계값의 최종 수치    — §6-3 실측 후
```

## §2 🔴 ⑥ 은 두 갈래다 — 합치지 않는다

Gate 문서 §3-⑥ 의 *"생성물 ↔ source comment author · 회원 닉네임 · 학습 데이터 author"* 안에는
**성격이 다른 두 검사**가 섞여 있다.

| 갈래 | 무엇을 보는가 | 언제 도는가 | 실패 조치 |
|---|---|---|---|
| **⑥-A 생성물 혼입** | 생성된 **글 · 댓글 본문**에 남의 닉네임이 섞여 나왔는가 | 생성물마다 | `regenerate` |
| **⑥-B 작명 충돌** | 페르소나 **`displayName` 후보**가 남의 이름과 겹치는가 | 작명 · 재배정 시 | `reject` / `review` |

🔴 **입력이 다르다.** A 는 긴 텍스트를, B 는 이름 문자열 하나를 본다.
🔴 **주기가 다르다.** A 는 생성마다, B 는 배정 시 1회.
🔴 **실패 의미가 다르다.** A 는 문장을 다시 쓰면 되고, B 는 **이름 자체를 버려야** 한다.

Gate ⑤ 가 두 갈래(타겟 설명어 · 브랜드 금지어)를 하나의 배열로 합치지 않은 것과 같은 이유다.
합치면 실패 로그만 보고 무엇을 고쳐야 할지 알 수 없다.

**이 문서는 ⑥-B 를 정한다.** ⑥-A 는 기존 §3-⑥ 계약을 그대로 둔다.

## §3 ⑥-B 검사 대상 6종

| # | 대상 | 원천 | 실패 시 |
|---|---|---|---|
| **B1** | 실회원 표시명 | `User` — §4-1 | `reject` |
| **B2** | 크롤 author | `VoiceSource.authorHash` · `VoiceSourceComment.authorHash` — §4-2 | `reject` |
| **B3** | 기존 persona displayName | `Persona` (활성 · 은퇴 포함) | `reject` |
| **B4** | 출처 커뮤니티 marker | `SOURCE_SPECIFIC_TERMS` (8) · `SOURCE_CONTEXT_TERMS` (8) | `reject` |
| **B5** | 운영자 / AI 느낌 | §5-4 규칙 | `regenerate` |
| **B6** | 나이 · 지역 · 병명 · 가족상태 노출 | §5-5 규칙 | `regenerate` |

🔴 **B3 은 은퇴한 페르소나까지 본다.** `retired` 를 풀면 같은 이름이 다시 나타나 회원이 혼동한다.
같은 이유로 `paused` 도 포함한다. 즉 **`status` 와 무관하게 전부** 대조한다.

## §4 🔴 데이터 접근 비대칭 — 설계를 가르는 실측

세 대상의 **접근 가능성이 서로 다르다.** 이것을 모르고 설계하면 작동하지 않는 검사를 만들게 된다.

### §4-1 실회원 — 원문 접근 가능. 단 필드가 **2개**다

`src/lib/display-name.ts` 실측:

```
표시명 = nickname  ??  name  ??  ANONYMOUS_NAME
```

🔴 **`nickname` 만 보면 대다수 회원을 놓친다.**
`prisma/schema.prisma` 주석과 `src/lib/auth.config.ts` 실측 기준:

```
가입 시      카카오 닉네임 → User.name 에 들어간다
User.nickname  사용자가 직접 설정할 때만 채워진다 (nullable · @unique)
```

즉 **직접 설정하지 않은 회원의 표시명은 `name` 에 있다.**
`name` 에는 `@unique` 제약이 없으므로 **DB 가 막아주지도 않는다.**

```
🔴 B1 의 대조 집합 = User.nickname ∪ User.name   (둘 다 · NULL 제외)
```

### §4-2 크롤 author — 🔴 원문이 없다. 단방향 해시뿐이다

`scripts/lib/voice-unao-readonly.mts` 실측:

```
authorHashOf(author, salt) = "sha256:" + sha256(salt + "::" + author)
```

스키마 주석이 이유를 적어 뒀다 — *닉네임 원문을 두면 3~7자라 검색으로 특정된다.*
**이 정책은 바꾸지 않는다.** 그러나 대가가 있다.

| 검사 | 해시로 가능한가 |
|---|---|
| **완전 일치** | 🟢 가능 — 후보를 같은 salt 로 해시해 비교 |
| **정규화 후 일치** | 🟡 조건부 — 정규화한 문자열의 해시를 **따로 갖고 있어야** 가능 (§4-3) |
| **부분 포함 · 유사도** | 🔴 **불가능** — 해시는 부분 문자열도 거리도 보존하지 않는다 |

🔴 **B2 에서 유사 검사를 하겠다고 쓰면 그것은 거짓 설계다.** 해시로는 못 한다.

### §4-3 🔴 그래서 B2 는 무엇을 할 수 있는가 — 3안

| 안 | 방식 | 대가 |
|---|---|---|
| **가-1** | 완전 일치만 한다 | 🟢 추가 저장 없음 · 🔴 변형 통과 |
| **가-2** | 정규화 해시 컬럼을 **추가로** 둔다 (`authorHashNorm`) | 🟢 정규화 일치까지 · 🔴 컬럼 신설 + 재계산. **원문은 여전히 저장하지 않는다** |
| **가-3** | 대조 시점에 우나어 원본을 read-only 로 읽는다 | 🟢 유사도까지 · 🔴 외부 의존 · 원문을 메모리에 올린다 |

**권고: 가-2 — 🔴 단 `N2` 기준으로만.** 실측 근거는 §6-4.

```
🟢 만든다      authorHashNorm  =  hash(N2(author))
🔴 만들지 않는다 N3 기준 컬럼 — 빈 문자열 10.4~10.5% · 고유 12~13% 뭉침 (§5-1)
```

| 대상 | 권고 |
|---|---|
| `VoiceSource.authorHashNorm` | 🟢 **둔다** |
| `VoiceCommentSignal.authorHashNorm` | 🟢 **둔다** — 댓글 author 가 더 크고(2.2배) 성질이 같다 (§6-4) |

🔴 **컬럼 신설은 창업자 결정 사항**이며 이 문서가 진행하지 않는다. migration 도 하지 않는다.
가-3 은 `voice-unao-readonly.mts` 가 이미 존재해 기술적으로 가능하지만,
**작명 1회를 위해 원문을 메모리에 올리는 것**은 해시 정책의 취지와 어긋난다.

### §4-4 3중 비대칭 요약

```
B1 실회원        원문 O  →  전 방식 가능
B3 persona       원문 O  →  전 방식 가능
B2 크롤 author   원문 X  →  일치 계열만 (§4-3)
```

🔴 **이 비대칭을 문서에 남긴다.** 나중에 "왜 B2 만 약한가" 를 다시 묻지 않기 위해서다.

## §5 검사 방식

### §5-1 정규화 4단계 — 🔴 N3 는 충돌 판정 키가 아니다

```
N0  원본
N1  trim + 유니코드 NFC 정규화 + 소문자화
N2  공백 · 기호 전부 제거        (· _ - . ~ ♡ ★ 등)
N3  숫자 · 영문 제거 후 한글만 남김
```

| 단계 | 역할 |
|---|---|
| **N0 · N1 · N2** | 🟢 **충돌 판정 키** — 일치하면 `reject` |
| **N3** | 🔴 **판정 키가 아니다.** 재대조용 보조 신호 · `review` 참고 신호로만 |

각 단계마다 대조하고 **어느 단계에서 걸렸는지 기록**한다.

#### 🔴 N3 를 판정 키에서 뺀 이유 — 실측 (§6-4)

N3 를 대조 키로 쓰면 **거짓 충돌이 대량 발생한다.**

| 근거 | 글 author | 댓글 author |
|---|---|---|
| 🔴 **N3 결과가 빈 문자열** | **10.4%** | **10.5%** |
| 🔴 **N3 에서 고유 개수 감소** | **12.2%** | **13.4%** |

빈 문자열이 되는 것은 **한글이 없는 이름**(영문 · 숫자만)이다.
이들을 N3 로 대조하면 **서로 전부 같아진다** — 열에 하나가 근거 없이 `reject` 된다.
게다가 서로 다른 이름 12~13% 가 N3 에서 뭉친다.

```
🔴 N3 일치      → reject 하지 않는다. review 신호로만 기록
🟢 N3 결과가 빈 문자열이면  → 대조에서 제외한다 (비교 자체를 하지 않는다)
```

**N2 까지가 판정 경계다.**

### §5-2 한글 변형

| 변형 | 처리 |
|---|---|
| **자모 분해 / 결합** | NFC 로 통일 (N1) — 분해형 입력을 결합형으로 |
| **숫자 · 영문 접미** | N3 에서 제거 후 재대조 |
| **반복 문자** | 3회 이상 연속은 1회로 축약한 뒤 재대조 |

🔴 **자모 단위 유사도(초성만 같음 등)는 하지 않는다.** 한글에서 초성 일치는 너무 흔해
오탐이 폭증한다. N3 까지가 실용 경계다.

### §5-3 유사도 — B1 · B3 에만

편집 거리(Levenshtein) 기반. **B2 에는 적용하지 않는다**(§4-2 — 해시로 불가능).

```
거리 0            완전 일치
거리 1 이하        🔴 매우 위험 — 한 글자만 다르다
거리 2 이하        🟡 review
```

### §5-4 B5 — 운영자 / AI 느낌 (규칙)

```
🔴 운영 주체 연상   "지기" · "관리" · "운영" · "매니저" · "봇" 계열 어미/접두
🔴 AI 연상         AI · GPT · bot 등 영문 · 숫자 접미 · 영문 혼용
```

전략 §10-7 · Pool §3-2 가 이미 금지한 항목이다. 여기서는 **판정 가능한 형태**로만 옮긴다.

### §5-5 B6 — 식별 정보 노출 (규칙)

```
🔴 나이       두 자리 숫자 + "세" · "대" 결합
🔴 지역       행정구역 접미(시 · 구 · 동 · 읍 · 면)를 가진 실지명
🔴 병명       Gate §5 조언 제한이 나열한 병명 어휘
🔴 가족상태   "엄마" · "며느리" · "시어머니" 등 관계어 단독 사용
```

🔴 **B6 은 Gate ③ 식별 디테일과 다르다.** ③ 은 생성물 본문을, B6 은 **이름 한 개**를 본다.
이름은 모든 글에 반복 노출되므로 본문보다 기준이 엄격해야 한다.

## §6 짧은 닉네임 오탐 방지

### §6-1 문제

우나어 · 소란소란 닉네임은 **3~7자**가 다수다. 짧은 문자열에서는

```
편집 거리 1  =  3자 중 1자 차이  =  33% 다름
편집 거리 1  =  7자 중 1자 차이  =  14% 다름
```

같은 거리 1 이라도 의미가 전혀 다르다. **절대 거리를 그대로 쓰면 짧은 이름이 전부 걸린다.**

### §6-2 처리

```
길이 2 이하        🔴 유사도 검사 제외 — 완전 일치만 본다
길이 3~4          거리 1 → review (reject 아님)
길이 5 이상        거리 1 → reject · 거리 2 → review
```

또한 **부분 포함 검사는 길이 3 이상에서만** 한다. 2자 부분 일치는 우연이 지배한다.

### §6-3 🔴 임계는 실측 후 확정한다

위 수치는 **출발점이지 확정이 아니다.** 확정 전 필요한 read-only 측정:

```
① 실회원 표시명 길이 분포        (nickname ∪ name)
② 후보 작명 규칙으로 뽑은 표본이 B1 · B3 에 걸리는 비율
③ 길이 구간별 오탐률
```

🔴 측정 없이 수치를 굳히면 **작명 자체가 불가능해지거나(과탐) 검사가 무의미해진다(과소).**


### §6-4 ✅ read-only 측정 결과 (2026-08-31)

🔴 **닉네임 · author 원문은 출력하지 않는다.** 분포와 비율만 남긴다.

#### 실회원 표시명 — 🔴 표본이 너무 작다

```
User 4명 · 표시명 6개
  nickname 만 25.0%  ·  name 만 25.0%  ·  둘 다 50.0%  ·  둘 다 없음 0%
```

🟢 **§4-1 이 실측으로 확인됐다** — `name` 만 가진 회원이 실재한다. `nickname` 만 보면 놓친다.
🔴 **그러나 임계는 확정할 수 없다.** 6개로는 중복률도 오탐률도 전부 0 이 나온다.
합성 후보 245개 대 회원 표시명 충돌 **0%** 는 "안전" 이 아니라 **"측정 불가"** 다.

#### 크롤 author — 여기가 실질 대조 집합이다

| 항목 | 수 |
|---|---|
| 소란소란 고유 `authorHash` (글+댓글) | **17,992** |
| 회원 표시명 | 6 |

🔴 **대조 집합의 99.97% 가 크롤 author 다.**
합성 후보 245개를 같은 salt 로 해시해 대조한 결과 **8개(3.3%) 가 완전 일치**했다.
회원 쪽 0% 와 대비된다 — **B2 가 실질 방어선이다.**

#### 정규화 변화율 — 글 author 와 댓글 author 가 같은 성질이다

🔴 **아래 표는 우나어 전체 · 고유 author 기준이다.**
backfill 대상(소란소란 적재분)의 값은 다르다 — §6-5 를 함께 볼 것.

우나어 read-only 에서 원문의 정규화 변화만 측정했다(원문 미출력).

| 지표 | 글 author | 댓글 author |
|---|---|---|
| 고유 개수 | 12,493 | **27,590** |
| N1 변화율 | 3.8% | 4.1% |
| 🟢 **N2 변화율** | **10.0%** | **9.5%** |
| 🟢 **N2 고유 감소(과탐)** | **0.2%** | **0.3%** |
| 🔴 N3 변화율 | 24.2% | 24.3% |
| 🔴 **N3 빈 문자열** | **10.4%** | **10.5%** |
| 🔴 **N3 고유 감소(과탐)** | **12.2%** | **13.4%** |

**두 집합의 값이 거의 같다.** 길이 분포도 같다(5-7자 42~43% · 3-4자 38~39%).
→ 🟢 **`authorHashNorm` 을 `VoiceSource` 와 `VoiceCommentSignal` 양쪽에 두는 근거**다.
한쪽만 두면 **더 큰 쪽(댓글 author 27,590 · 2.2배)을 방치**하게 된다.

#### N2 의 실익 대비 위험

```
추가로 잡히는 변형   10.0% / 9.5%
과탐                0.2% / 0.3%
                    → 실익 대비 위험비 약 30~50배
```

#### 🔴 이 측정이 확정하지 못한 것

```
🔴 회원 측 오탐률 · 길이 임계   표본 6개. 회원이 늘기 전까지 확정 불가
🔴 합성 후보군의 대표성        실제 작명 어휘군이 정해지면 재측정
🟡 코퍼스 증가 영향            댓글 author 고유는 우나어 전체 기준 27,590 이나
                              소란소란 적재분은 15,345 — 코퍼스가 늘면 대조 집합도 커진다
```


### §6-5 🔴 backfill 실측 (2026-08-31) — 모집단이 다르면 값도 다르다

migration 0013 적용 후 68,926 건을 backfill 하고 전량 검증했다.

#### 🔴 §6-4 의 10.0% / 9.5% 는 이 검사의 기준이 아니다

| 기준 | VoiceSource | VoiceCommentSignal |
|---|---|---|
| **row 기준 · 소란소란 적재분** (검증이 재는 것) | **14.4%** (1,396 / 9,674) | **15.7%** (9,324 / 59,252) |
| 고유 author 기준 · 소란소란 적재분 | 13.7% (698 / 5,088) | 14.4% (2,214 / 15,345) |
| 고유 author 기준 · **우나어 전체** (§6-4) | 10.0% | 9.5% |

차이는 두 가지가 겹친 것이다.

```
① 모집단   §6-4 는 우나어 전체(글 12,493 · 댓글 27,590 고유)를 쟀다.
           backfill 대상은 소란소란에 적재된 고품질 코퍼스의 author
           (글 5,088 · 댓글 15,345 고유)다. 그 부분집합이 공백·기호를 더 갖고 있다.
② 단위     §6-4 는 고유 author 기준, 검증은 row 기준이다.
           공백·기호를 가진 author 가 평균보다 많이 쓰면 row 비율이 더 높아진다.
```

🔴 **처음 `--check` 임계를 §6-4 의 9~11% 로 잡았다가 정상 데이터를 실패로 판정했다.**
임계는 **13~17%**(row 기준 · 적재분 기준)로 정정했다.
같은 실수를 막으려고 기준을 코드 주석에도 적어 뒀다.

#### 🟢 데이터는 전량 정확하다

임계를 바꾸기 전에 데이터 정확성을 **독립적으로** 증명했다.
원문에서 다시 계산해 DB 값과 1건 단위로 대조한 결과다.

| 검증 | VoiceSource | VoiceCommentSignal |
|---|---|---|
| `authorHashNorm == hash(N2(원문))` | **9,674 / 9,674** ✅ | **59,252 / 59,252** ✅ |
| `authorHash` 무결 (원문 재해시 일치) | **9,674 / 9,674** ✅ | **59,252 / 59,252** ✅ |

**68,926 건 전량이 일치했고 오차는 0 이다.** `authorHash` 는 한 행도 변경되지 않았다.

🔴 **임계를 넓힌 것이 아니라 맞는 모집단의 값으로 바꾼 것이다.**
데이터가 맞는다는 증명이 먼저이고, 임계 정정은 그 위에 있다.

#### 적용 상태

```
🟢 migration 0013   적용 완료 — 컬럼 2/2 · TEXT · nullable
🟢 backfill         완료 — 68,926 건 · NULL 0 · sha256 형식 오류 0
🔴 원문 author 컬럼  추가 0 — 저장하지 않는다
```

## §7 결과 상태 4종

| 상태 | 의미 | 조치 |
|---|---|---|
| **`pass`** | 충돌 없음 | 배정 가능 |
| **`review`** | 유사하나 단정 불가 | 🔴 **운영자 판단** — 자동 배정 금지 |
| **`regenerate`** | 규칙 위반 (B5 · B6) | 후보를 다시 만든다 |
| **`reject`** | 실제 충돌 (B1 · B2 · B3 · B4) | 🔴 **이 이름을 영구 폐기** |

### 🔴 `regenerate` 와 `reject` 를 나누는 이유

```
regenerate   이름 짓는 방식이 잘못됐다   → 규칙을 지켜 다시 만들면 된다
reject       이 이름은 이미 남의 것이다   → 다시 만들어도 같은 결과
```

⑨(출처 marker)가 `regenerate` 와 `reject` 를 나눈 것과 같은 구조다.

### 판정 순서

```
B4 · B5 · B6 (규칙)  →  B3 (persona)  →  B1 (회원)  →  B2 (크롤 author)
        싼 검사부터                        DB 조회는 뒤로
```

🔴 **가장 엄격한 결과를 따른다.** 하나라도 `reject` 면 최종 `reject` 다.

## §8 🔴 닉네임 문자열을 출력하지 않는다

**이 원칙이 이 설계에서 가장 자주 깨질 위험이 있다.** 충돌을 설명하려면 이름을 말하고 싶어지기 때문이다.

```
🔴 문서 · 로그 · 어드민 목록 · 에러 메시지 어디에도
   실회원 닉네임 · 크롤 author 원문을 출력하지 않는다
```

| 대신 남기는 것 | 예 |
|---|---|
| **충돌 종류** | `B1` · `B2` · `B3` |
| **정규화 단계** | `N0` ~ `N3` |
| **거리** | `0` · `1` · `2` |
| **대상 참조** | `userId` · `personaId` · `authorHash` (해시 그대로) |
| **집계** | `충돌 후보 N 종` |

🔴 **판정부 반환값에 원문 문자열 필드를 두지 않는다.** Gate ⑤ 판정부가 `reason` 에
원문 조각 대신 상수 term 만 담은 것과 같은 원칙이다.

🔴 **B4 만 예외다.** 출처 marker 는 개인 닉네임이 아니라 **공개된 집단 호칭**이고
이미 코드 상수(`SOURCE_SPECIFIC_TERMS`)에 있으므로 term 을 그대로 기록할 수 있다.

## §9 displayName 작명과의 관계

```
🔴 Gate ⑥-B 설계 승인 전   작명하지 않는다
🔴 작명 후에도             ⑥-B `pass` 전에는 고객에게 노출하지 않는다
🟢 어드민에서는            `pass` 전에도 후보로 보인다 (status = draft)
```

### 🔴 어드민에서 `displayName` 은 단독으로 서지 않는다

```
고객 화면    displayName 만 보인다
어드민       displayName + personaId + P 코드 + status  가 항상 함께 붙는다
```

전략 §10-2 · §10-7 이 정한 것이다. **어드민에서 이름만 보이면 추적이 불가능하다.**

### 🔴 배정 시점이 검사 시점이다

작명 시 `pass` 였어도 **배정 사이에 회원이 같은 닉네임을 만들 수 있다.**

```
🔴 배정 직전에 다시 검사한다
🔴 User.nickname 의 @unique 는 완전 일치만 막는다 — 그리고 name 은 unique 가 아니다
```

DB 제약을 방어선으로 믿지 않는다(§4-1).

## §11 판정부 설계 방향

Gate ⑤ · ⑨ 판정부(`scripts/lib/persona-gate-*.mts`)의 구조를 따른다.

```
🔴 판정부는 DB 에 접근하지 않는다
   대조 집합을 인자로 받는다 — 조회는 호출부의 책임
🔴 LLM · API · 파일 IO · 네트워크 없음
🔴 반환값에 원문 문자열 필드 없음 (§8)
```

이유: Gate ⑤ · ⑨ 가 순수 함수라서 fixture 로 역검증이 가능했다.
DB 를 직접 읽으면 그 검증 구조가 무너진다.

🔴 **다만 ⑥-B 는 ⑤ · ⑨ 와 달리 외부 상태(회원 닉네임)에 의존한다.**
그래서 **조회 계층과 판정 계층을 분리**하는 것이 ⑤ · ⑨ 보다 더 중요하다.

### fixture 계획 (구현 시)

```
🟢 합성 문자열만 쓴다 — 실회원 닉네임 · 크롤 author 를 fixture 에 넣지 않는다
🔴 역검증: 정규화 단계를 하나 빼면 fixture 가 잡는가
🔴 역검증: 길이 가드를 풀면 짧은 이름 오탐이 드러나는가
```

Gate ⑨ fixture 에서 **정렬을 빼도 우연히 통과하던 결함**을 소스 스캔으로 잡았던 사례가 있다.
같은 방식의 소스 스캔 assertion 을 둔다.
