## 0. 하나의 루프와 하나의 질문

D100 전체는 루프 하나다.

```text
지금의 원문 기회(source opportunity) -> 다음 공개 슬롯 -> 그 시점에 만든 Persona 글
-> 대화 -> 감사와 학습 -> 다음 슬롯
```

공개 여부를 정하는 질문도 하나다.

> **이 원문 기회는 예정된 공개 슬롯에서도 여전히 대화할 가치가 있는가?**

D3 · D5 · D10 · D20 · D30 · D50 · D100 은 모두 같은 답을 쓴다. 단계가 바꾸는 것은
처리량과 필요한 용량이지 콘텐츠를 고르는 철학이 아니다.

🔴 **사고마다 규칙을 하나씩 더하지 않는다.** 콘텐츠 종류, 이벤트 규칙, 대체 경로, 예외를 덧대는
대신 틀린 정책을 바꾸고 옛 경로를 지운다. 새 정책은 자기가 대체한 옛 경로를 §11 표에 같은
변경으로 적는다. 같은 결정을 내리는 정본이 둘이면 결함이다.

## 1. 목표 (변경 불가)

> **지금의 커뮤니티형 원문 기반 글을 Persona 가 자연스럽게 작성하고,
> 하루 3 → 5 → 10 → 20 → 30 → 50 → 100편으로 확대 발행한다.
> SEO 는 별도 글 종류가 아니라, 이 커뮤니티 글들이 검색에 노출되어 유입을 만드는 결과다.**

- 단위는 **공개 발행**이다. Shadow·Queue 후보·내부 생성이 아니다.
- D100 은 무인 시스템이 지금의 원문 기회를 하루 최대 100편의 쓸모 있는 공개 커뮤니티 글과
  제한된 대화·감사·복구로 바꿀 수 있다는 **용량 목표이자 시운전 증명**이다.
- **North Star 는 주간 재방문 참여 실사용자**다([`NORTH-STAR.md`](./NORTH-STAR.md)).
  공개 글 100/day 는 그것을 움직이는 **수단**이다.

### 1.1 Dn 은 인증된 최대 용량이다 (2026-10-15)

- `Dn` 은 무인 시스템이 하루 자동으로 운영할 수 있다고 **증명된 최대 용량**이다. 매일 채워야 하는 할당량이 아니다.
- **평상시**: 지금 가치 있는 원문 기회만큼 `0..Dn` 편을 공개한다. 좋은 현재 원천이 적은 날은 적게 낸다.
  평상시의 부족분은 다음 날의 실패 증거가 아니다.
- **증명일**: controller 가 연 증명일에는 자동 READY 글 정확히 `N` 편과 §6 의 관련 계약을 자동으로 증명한다.
- **자연 증거 승계**: controller 가 만든 평상시 `HOLD`·`PREPARE` 운영일도 자동 READY 글이 정확히 `N` 편이고
  §6의 실질 조건을 모두 만족하면 현재 Dn의 운영 PASS 증거로 승계한다. 사람 게시·댓글·stage·READY·장부 수정이
  조금이라도 섞인 날은 승계하지 않는다. 평상시 `N-1`은 정상 운영이지 FAIL이나 재시험 부채가 아니다.
- 증명일 사이를 매일의 재증명으로 채우지 않는다. 증명일은 다음 단계 시험이나 재시험이 필요할 때만 잡는다.
- 수동 게시·댓글·stage·장부 수정은 어떤 Dn 의 증거도 아니다.
- 속도를 늦추는 임의 관측일·달력 대기를 두지 않는다. 현재 단계가 운영 PASS이고 다음 단계 preflight가 green이면
  같은 날 남은 슬롯 또는 다음 첫 유효 슬롯에서 자동 시험한다. 더 높은 단계의 Persona·scheduler·profile·관측 용량은
  파일과 운영 경계가 겹치지 않는 범위에서 미리 병렬 준비한다.

판단 순서는 `실사용자 가치 → 지금의 대화 가치 → 안전과 사실 → 무인 운영 신뢰성 →
속도·비용 효율 → 구현 완성도` 다.

## 2. source-to-slot 판정 — 원문 기회를 슬롯에 거는 판정은 하나다

### 2.1 원문 증거 용어

| 용어 | 뜻 | 쓰는 곳 |
|---|---|---|
| `sourcePostedAt` | 원천에 글이 올라온 시각. 신뢰할 수 있을 때만 | 원문 나이의 1순위 |
| `sourceListedAt` | 원천 목록에서 그 글을 본 시각. 신뢰할 수 있을 때만 | 게시 시각을 모를 때의 원문 나이 근거 |
| `sourceCapturedAt` | 소란소란이 그 원문을 수집한 시각 | 수집 기록. **원문 게시 시각이 아니다** |
| 원천 상대 반응 증거 | 수집 시점에 관측한 조회·댓글·목록 순위 등을 **같은 원천 안에서** 정규화한 값 | 반응 비교 |
| 참여 동력 | 원문이 반응을 얻은 이유(논쟁·공감·궁금증·시의성·생활 효용·웃음) | 대화 가치와 생성 보존 |
| 예정 슬롯 `slotAt` | 이 원문 기회가 공개될 구체적인 다음 슬롯 시각 | 판정 기준 시각 |
| release 판정 기록 | 판정 결과·기준 슬롯·판정 시각·사유를 발행 트랜잭션 안에서 남긴 도장 | 단계 증거 |

🔴 **capture 시각은 게시 시각을 대신하지 않는다.** 초안을 만든 시각도 마찬가지다.
수집하거나 초안을 만든 시각이 최근이라는 이유로 원문이 지금의 이야기가 되지 않는다.

🔴 **날짜만 아는 게시 시각을 그날 00:00 으로 지어내지 않는다** (2026-10-11). 목록이 날짜만 보여 주면
그 정밀도(날짜 구간 또는 정밀도 모름)를 그대로 보존하고, 판정은 그 불확실성을 fail-closed 로 다룬다.

원문 증거(게시·목록·수집 시각, 수집 시점 반응, 출처 추적, 개인정보 없는 지문)는 수집부터 발행까지
바꾸지 않고 보존한다. 반응은 원천별로 정규화한다. 큰 원천이 원시 숫자가 크다는 이유로 이기지 않는다.
관측 하나로 속도(velocity)를 지어내지 않는다.

### 2.2 판정 함수는 하나다

한 개의 정본 판정 함수가 원문 기회 하나와 예정 슬롯 하나를 받아 `eligible · ineligible · unknown`
과 사유 코드를 낸다. 입력은 다음뿐이다.

1. 영구 hard gate 결과 — 안전·개인정보·사실성·독창성·Persona 생활사·중복·예산. 가산점이 아니다.
   반응이 아무리 커도 hard gate 를 넘지 못한다.
2. 신뢰할 수 있는 원문 나이 — 예정 슬롯 기준. 원문 시각을 모르거나 손상됐으면 `unknown` 이다.
3. 원천 상대 반응 증거 — 없으면 `unknown` 이다.
4. 기대 대화 가치 — 참여 동력이 보존돼 있는가.
5. Persona 적합과 다양성 — 그 슬롯에 맞는 화자를 배정할 수 있는가.

`unknown` 은 공개 경로에 들어가지 않는다(fail-closed). 나이 상한·정규화 방식 같은 구체값은
이 판정 함수 한 곳에만 둔다. 새 숫자를 만들면 근거와 함께 이 문서의 결정 기록에 적는다.

같은 판정을 부르는 자리는 다섯뿐이다.

| 자리 | 하는 일 |
|---|---|
| 유료 생성 전 | 예정 슬롯에서 유효하지 않을 원문은 생성하지 않는다 |
| 발행 선택 | 그 슬롯의 후보를 같은 판정의 순위로 고른다 |
| 발행 트랜잭션 재판정 | **발행 직전** 같은 판정을 다시 돌린다. 식었거나 모르게 됐으면 만료하고 다음 기회로 넘어간다 |
| 단계 증거 | 공개된 증명 글이 이 판정을 통과한 기록을 가졌는가 |
| 준비도·health 화면 | 같은 판정으로 센다. 화면마다 다른 재고 수를 계산하지 않는다 |

이 밖에서 신선도·재고·준비도를 따로 계산하면 두 번째 정본이다.

### 2.3 원천 순위는 하나다 — 신선도 1순위 (2026-10-19 창업자 재확정)

수집과 공급·발행 선택은 같은 비교 계약 하나를 쓴다.

```text
hard safety/truth -> 발행 자격 gate (품질·독창성·반응 관측 등 §2.2) -> 신선도 -> 동률 반응 -> 결정적 tie
```

- hard gate 는 통과·실패다. 가산점이 아니다.
- 발행 자격은 자격 gate 다 (안전·사실·중복·독창성·Persona 배정·반응 관측 존재). 자격을 통과한 뒤
  **오래된 고반응 글이 최신 글을 앞서지 않는다** — 가장 가까운 공개 슬롯 기준 원문 나이가 가장 어린 글부터
  수집→생성→READY→발행이 같은 순서로 흐른다.
- 반응 백분위·velocity 는 **실질적으로 같은 게시 시각일 때만** 선다. 그 뒤에만 결정적 id 로 간다.
- 🔴 **출처별 우대 없음.** 레몬테라스·우아한갱년기·wgang·향후 82cook 가운데 어느 사이트도
  순위에 가산점·quota·예약석을 받지 않는다.
- 🔴 **주제형 숫자 보너스 없음.** 중심 주제가 갱년기인지는 §7 의 게시판 라우팅이 다룬다 —
  순위에 "갱년기 보너스" 를 끼우지 않는다 (창업자 미승인).
- 72시간이 지난 원문은 자격 밖이다. 4·12·24·48·72h 는 관측 구간일 뿐 runtime 분기·quota 가 아니다 (관측 목표
  p50≤4h · p90≤12h · 정상 max≤24h · >24h 조사 · ≥72h 0).
- 레몬테라스 쫑알쫑알은 1페이지를 제외하고 2~16페이지를 보며, 회차 상세는 `jjong 10 + humor 1` 을 유지한다.

### 2.4 하지 않는 것

- 명절·선거·방송·날씨 같은 사건 종류별 신선도 분기를 만들지 않는다. 급함은 원문 시각, 관측된
  반응, 슬롯 시점의 가치에서 나온다.
- 이미 돈을 들여 만든 글이라는 이유로 식은 글을 내보내는 대체 경로를 만들지 않는다.
  **매몰 비용은 지금의 사용자 가치를 이기지 못한다.**
- 후보가 모자라면 오래된 글로 채우지 않는다. 그 슬롯은 비운 채 원인 코드로 보고한다.

## 3. JIT 공급 — 용량은 미리, 공개 활동은 늦게

미리 준비하는 것은 **생산 용량**이다. 식는 공개 활동은 쌓아 두지 않는다.

| 미리 준비한다 | 그 시점에 만든다 |
|---|---|
| 원천 connector · 수집 빈도 · 신뢰할 수 있는 메타데이터 추출 | 토픽 글 본문 |
| 원천 정규화 · 순위 · 중복 제거 · replay fixture | 다음 슬롯에 걸 원문 선택 |
| Persona 설계 · 자격 검증 · 말투/생활사 근거 · cadence · 계약 유효 reserve | 그 원문에 맞는 Persona 배정 |
| 생성 처리량 · 매칭 · scheduler 용량 | 공개된 글의 첫 댓글 |
| 안전·예산·감사·관측·복구·rollback · 상시 실행 주인 하나 | 실제 스레드에 대한 답글과 계속/멈춤 판단 |

- 생성 수요는 **가장 가까운 실제 공개 기회**에서 나온다(2026-10-11). 오늘 남은 가까운 안전 슬롯과 다음 첫 운영
  기회의 수에서, 그 시점에 판정상 유효하게 남을 READY 수를 뺀 만큼만 만든다. 보충량은 그 가까운 기회·실측 수율·지연·
  Persona 용량·비용에서 나온다.
- 공개 단계보다 큰 준비 단계의 내일 슬롯 전체나 며칠치 완성 글은 오늘의 생성 수요가 아니다. Persona 여력도 같은
  가까운 수요 지평으로 계산한다. 증명일의 추가 슬롯은 그날 공급이 채운다.
- 원문 후보는 잠깐 기다릴 수 있다. 생성된 토픽 글·댓글·답글은 오래 가는 재고가 되지 않는다.
- 준비한 용량을 소진하기 위해 Persona 활동을 만들지 않는다.

### 3.1 보충량은 고정 할증이 아니라 실측이다

필요 READY와 상세 원천 수를 공개 목표에 고정 비율로 더하지 않는다. 특히 `공개 목표 × 120%`와
과거 전환율로 만든 단계별 상세 원천 수는 정책 숫자가 아니다. 준비도는 다음을 같은 창에서 측정해
필요량을 계산한다.

```text
다가오는 슬롯 수 + 실측 실패·만료·감사 HOLD·재시도 손실 + 복구 시간 여유
```

- 아직 실측이 없거나 같은 계약의 slot-valid 수율이 0이면 `UNKNOWN`으로 닫되, 부족 슬롯당 최대 3개 최신 원천의
  작은 회복 canary로 측정한다. 공개·적재 상한은 부족 슬롯 수 그대로라 글 수를 부풀리지 않는다.
  근거 없는 20%를 영구 gate로 만들지 않는다.
- 실측 여유는 원천별·단계별로 다시 계산하고, 정상화되면 자동으로 줄어야 한다.
- 수집 상세 수는 관측·용량 계획값이다. 원천 반응과 슬롯 가치를 통과한 기회 수를 대신하지 않는다.
- preflight는 “오늘 목표보다 완성 글이 몇 건 더 있는가”가 아니라, 슬롯마다 유효한 기회와 그날의
  실측 보충·복구 능력이 있는가를 본다.
- 🔴 **preflight의 시계는 둘이고 의미를 섞지 않는다** (2026-10-20). 이미 끝난 단계의 품질·댓글·감사·비용
  증명은 해당 증명일까지의 KST 달력 창만 읽는다. 다음 단계의 READY·workset·공급비 용량은 판정 스냅샷
  `now` 직전 롤링 72시간만 읽고 `now` 이후 행은 넣지 않는다. 오늘 새벽 자연 공급을 전날 자정에서 잘라
  준비도 0으로 만드는 경로와, 오늘 데이터를 과거 PASS에 섞는 경로를 모두 금지한다.

### 3.2 증명일 준비도와 지속 준비도

- **증명일 준비도**: 다음 단계의 증명일 슬롯 전체를 채울 만큼 그 슬롯들에서 판정상 유효한
  원문 기회가 있고, 수집·생성·Persona·댓글·감사·예산 용량이 실측으로 그날 보충을 감당한다.
- **지속 준비도**: 그 단계에서 처리량·지연·품질·비용·복구가 **반복 관측**으로 유지된다.

둘 다 완성 글을 며칠 치 쌓아 둔 양으로 증명하지 않는다.

### 3.3 실행 구조 — event-assisted, 시간표는 fallback (2026-10-11)

- **수집 완료가 공급을 깨운다.** 새 원천이 있고 가까운 기회에 부족분이 있을 때만 공급이 돈다.
- **공개 commit 이 첫 댓글을 깨운다.** commit 전에는 댓글을 깨우지 않는다.
- 기존 고정 schedule 은 fallback 과 recovery 로 유지한다. 시간표가 정상 경로의 유일한 주인이 아니다.
- 예약 실행 · 이벤트 실행 · 복구 실행은 **같은 실행 lease/token 과 예산 소유권**을 쓴다. 실행 중에 도착한 trigger 는
  한 번의 재실행으로 합친다(coalescing). 같은 lock · 같은 일 예산 상한을 재사용한다.
- 안전성은 idempotent at-least-once 로 확보한다. 별도 거대 큐나 exactly-once 시스템을 새로 만들지 않는다.

### 3.4 raw 와 비용 (2026-10-11)

- raw 축 원천은 자동 소비자에서 제외한다. 사람 라벨 replay 전에는 raw quota 나 새 검토 lane 을 만들지 않는다.
- 생성 낭비를 먼저 줄이고 실측한 뒤에 요청량·예산 확대를 판단한다. 지출 확대는 허용되지만 원인 불명 낭비는 아니다.
- 미정산 비용은 실제 근거 없이 정산 처리하지 않는다. 예약액은 실제 비용이 아니다.
- 다음 단계의 **제한 시험 진입**은 정산 요청 20건 이상, `usageUnknown` 1건 이하, 정산 비율 95% 이상이고,
  미상 요청에 현재 계약 metadata와 양수 예약액이 있으며 `정산 총액 + 미상 예약액`으로 계산한 목표 단계의
  투영 위험액이 현재 공급 일 상한 안일 때만 허용할 수 있다. 예약액은 실제 비용이나 확정 상한이 아니라 시험 진입의
  위험 envelope일 뿐이며, 미상 요청을 정산으로 바꾸지 않는다. 그 시험일 자체의 운영 PASS에는 미상 비용 0이 필요하다.

## 4. Persona 확장 계약 — 네 상태

Persona는 이름만 다른 계정 수가 아니라 실제로 글과 댓글을 맡을 수 있는 **계약 유효 화자**다.

| 상태 | 뜻 |
|---|---|
| designed | 설계만 있다 |
| qualification-pending | 적재됐지만 자격 검증이 끝나지 않았다 |
| contract-valid reserve | 자격을 모두 통과했고 아직 단계에 투입하지 않았다 |
| stage-active | 현재 단계의 처리량을 위해 투입됐다 |

🔴 **이름이나 active 행은 용량이 아니다.** 용량은 contract-valid 수로만 센다.
contract-valid 는 뚜렷한 목소리와 관점, 일관된 생활사, 주제·관계 역할 범위, no-go 경계,
cadence 를 갖추고 **글 자격과 댓글 자격을 따로** 통과한 상태다.

- 단계별 canary 하한과 지속 다양성 목표는 아래 표가 정책 정본이다. 코드는 두 필드로 구현한다.
- reserve 는 낮은 단계 운영과 병렬로 쌓는다. 단계를 열려고 하한을 낮추지 않고, 창업자가 routine
  Persona 를 손으로 만들지 않는다. 부족한 축을 측정하는 즉시 자동으로 보강한다.
- 현재 처리량에 필요한 cohort 와 실측 여유만 stage-active 로 올린다.
- 인원 목표를 채워도 같은 목소리·생활사에 몰리거나 실제 배정 가능 인원이 부족하면 미달이다.


아래 canary 하한(코드 `PERSONA_CANARY_FLOOR`)은 계약 유효 수로 세는, 자동 canary를 실행할 **운영 하한**일 뿐
제품 다양성 목표와 같은 값이 아니다. 반복 운영은 아래 계약 유효 Persona 목표를 충족해야 완료다.
다음 단계 preflight 는 **올라갈 단계의** canary 하한을 본다 — D1 에서 D3 를 열려면 D3 하한이 먼저 필요하다.
계약 유효 수가 D3 하한보다 작으면 D1→D3 부터 막힌다.

| 단계 | 공개 글/day | canary 운영 하한 | 지속 운영 다양성 | 첫 댓글 증명/day | 추가 대화 |
|---|---:|---:|---:|---:|---|
| D3 | 3 | 24 | 24 | 3 | reply-worthiness 실측 |
| D5 | 5 | 24 | 24 | 5 | reply-worthiness 실측 |
| D10 | 10 | 30 | 30 | 10 | reply-worthiness 실측 |
| D20 | 20 | 40 | 60 | 20 | reply-worthiness 실측 |
| D30 | 30 | 60 | 90 | 30 | reply-worthiness 실측 |
| D50 | 50 | 100 | 150 | 50 | reply-worthiness 실측 |
| D100 | 100 | 180 | **300+** | 100 | reply-worthiness 실측 |

READY 생산량과 상세 원천 필요량은 §3.1의 실측 보충 계약으로 계산한다. 댓글의 단계 최솟값은
첫 댓글 증명 수이고, 총 댓글·답글 수의 고정 상한이나 목표가 아니다.
D3·D5 하한은 공개량보다 넉넉한 풀이라 더 올리지 않는다. D100의 300명은 상한이
아니라 첫 지속 운영 목표(지속 다양성 목표)다. 이 수는 Persona 1명당 주간 게시 편수로 계산한 산식이 아니며,
코드의 Persona 주간 게시 상한은 집중을 막는 안전 상한이지 고정 생산 목표가 아니다. 실제 글·댓글 집중도,
cadence, 매칭 실패를 단계마다 측정해 재검증하고, 그것이 높으면 300명보다 더 늘린다.

### 4.1 원천 요구와 Persona 선택을 분리한다 (2026-10-11)

- 첫 유료 판독은 Persona 중립의 원천 요구(stance · self-basis · 보존해야 할 사실)만 구조화한다.
- **유료 초안 생성 전에 코드가** 기존 말투·생활사·no-go·cadence·상한 authority 로 그 요구를 맡을 Persona 를 확정한다.
- 초안·의미 검수는 확정된 Persona 를 고정한다. 생성기가 Persona 후보를 임의로 다시 고르지 않는다.
- 공개 직전에는 같은 Persona 의 상태·상한·말투 출처를 다시 확인한다. 다른 Persona 로 바꿔 내보내지 않는다.
- 계약 유효 Persona 30명은 D10에 충분하다. D10 통과를 위해 Persona 를 늘리지 않는다.
  D20 은 canary 하한 40명을 먼저, 지속 운영 60명을 그다음으로 검증한다.

### 4.2 확장 Persona 의 이름은 실제 고객 작명 분포를 닮되 복사하지 않는다 (2026-10-16)

- 기존 30명은 이름을 고르게 맞추기 위해 일괄 변경하지 않는다. 공개 이력이 있는 이름은 Persona 정체성의 일부다.
- D20 이후 확장 cohort 의 합성 `displayName`은 실제 목표 고객 크롤에서 관측한 **길이·리듬·평범한 작명 습관의
  분포**를 입력으로 삼는다. 한 가지 감성어·계절어·규칙적인 조합으로 몰아 AI 작명처럼 보이게 하지 않는다.
- 크롤 작성자나 실제 회원 닉네임의 문자열을 후보로 복사·변형·노출하지 않는다. 원문 닉네임은 이름 생성 출력이나
  공개 로그에 남기지 않고, 분포·충돌 판정에 필요한 비식별 근거만 사용한다.
- 최종 배정 직전에는 현재 회원·기존 Persona·같은 신규 cohort·수집 작성자 대조를 다시 실행한다. exact 충돌뿐 아니라
  일반 사용자가 같은 사람으로 오인할 가까운 이름도 거절한다.
- 자연스러운 이름은 계약 유효성의 한 축일 뿐이다. 이름을 정했다고 용량으로 세지 않고, 말투 근거·생활사·no-go·
  글/댓글 자격·cadence 를 모두 통과한 뒤에만 `contract-valid`로 센다.

## 5. 대화 — 첫 댓글에서 선택적 다중 턴으로

- **첫 댓글**: 대상 글마다 60분 안에 Persona 첫 댓글 1건. 규모 증명의 기본이다.
- 첫 댓글 1건은 증명용 하한이지 실제 글마다 댓글을 정확히 하나만 달라는 제품 정책이 아니다.
- **선택적 다중 턴 답글**은 그다음 제품 층이다. 첫 댓글이 끝이라고 읽지 않는다.
- 🔴 **2026-10-15 창업자 결정:** 자동 글의 Persona 댓글은 첫 댓글 1건과 선택적 추가 댓글·답글 0~4건,
  합계 `1..5`건이다. 추가 답글은 부모 댓글을 가리키는 실제 스레드 행으로 저장한다. 모든 글을 5건으로
  채우지 않고, 답할 가치가 없으면 첫 댓글에서 끝낸다.
- 🔴 **2026-10-19 창업자 결정:** 추가 댓글 기능의 사용 가능 여부를 Dn 단계로 나누지 않는다. 승인된 운영 공통
  profile은 d5·d10·d20·d30·d50·d100에서 같은 안전 관문을 쓰며, Dn은 공개량·Persona·비용·처리 용량만 바꾼다.
  단계 전용 profile은 제한 시험이 필요할 때만 쓸 수 있고, 다른 단계에서는 fail-closed다.
- 제한 canary에서 자동 추가 답글은 Persona 댓글 또는 아직 쓰지 않은 글의 대화 hook만 대상으로 한다.
  실회원 댓글에는 자동으로 답하지 않는다. 실회원 대화를 침범하지 않는다는 증거와 별도 승인이 생기기 전까지
  이 경계를 넓히지 않는다.
- 실회원 댓글과 Persona 댓글에 **같은 reply-worthiness 판정**을 쓴다. 실회원 대화가 우선한다.
- 이어지는 질문·경험·반론·쓸모 있는 보탬에는 다시 답할 수 있다. 인사·이모지만·반복·자연스러운
  마무리에는 답하지 않아도 된다.
- 데이터는 스레드 root 와 직접 답글 대상을 모두 보존한다. 화면은 끝없는 들여쓰기 대신 읽을 수 있는
  한 줄기 스레드로 보여 준다.
- 공개 Persona 표시 여부는 창업자·법무·브랜드의 별도 결정이다. "AI 인지 모른다" 는 합격 기준이 아니다.
- 글마다 대화량을 똑같이 맞추지 않는다. 반응할 가치가 없으면 첫 댓글 뒤 끝나고, 실회원의 질문·반론·
  경험이 이어지면 예산과 안전 범위에서 여러 번 이어진다.
- 🔴 **2026-10-14 창업자 결정:** North Star 계측은 선택적 다중 턴의 제한 canary 와 병렬로 진행한다.
  계측 미완료만으로 canary 를 막지 않는다. 단, Persona·운영자 활동은 North Star 의 분자·분모에서 제외하고,
  첫 댓글 우선·실회원 우선·승인 profile·비용·중복·감사·kill switch·rollback 은 계속 필수다.
- 🔴 **자동 증명에는 자동 runner provenance 가 있는 댓글만 센다** (2026-10-11). Persona 댓글이라는 표시만으로는
  자동 첫 댓글 증거가 아니다. 수동 Persona 댓글은 정상 활동일 수 있어도 단계 증거가 아니다.
- 🔴 첫 댓글 runner 는 stale lock 회수와 bounded recovery 의 대상이다. 놓친 회차를 한 번만 복구하고,
  복구가 중복 댓글·자기 댓글·예산 우회를 만들지 않는다.

🔴 **답글 안전 불변식 — 전부 0 이어야 한다.**

```text
자기 답글 · 중복 답글 · 고아 답글 · 상한 없는 깊이 · 두 화자 자동 루프 ·
삭제·신고된 대상에 대한 답글 · 안전 우회 · 예산 우회
```

## 6. 단계 사다리와 PASS — 수동 물량은 성공이 아니다

자동 사다리는 `D1 -> D3 -> D5 -> D10 -> D20 -> D30 -> D50 -> D100` 이다.

🔴 **증명일에는 아래 PASS 조건을 정확한 `N`으로 적용한다** (2026-10-15 · §1.1). 평상시는 인증된 공개 상한 안에서
`0..Dn` 편이 정상이고, 평상시 공개량이 목표보다 적다는 사실은 FAIL 증거가 아니다. 다만 controller가 만든 평상시
`HOLD`·`PREPARE` 운영일이 우연히 정확한 `N`과 아래 조건을 전부 충족하면 현재 Dn의 자연 운영 PASS로 승계한다.
증명일의 `N-1`은 FAIL, `N`은 PASS, `N+1`은 상한 위반이다.

한 단계의 운영 PASS 는 창업자·운영자의 생산 작업 없이 다음을 모두 만족할 때다.

1. Stage controller가 사람 명령 없이 단계와 그 증명일 슬롯 전체를 고른다.
2. 모든 대상 글이 source-to-slot 판정과 자동 READY 경로에서 나온다.
3. 예약 발행이 서로 다른 적격 Persona 로 목표를 채우고 특정 Persona 에 몰리지 않는다.
4. 모든 대상 글에 60분 안에 첫 댓글이 공개된다.
5. 정본 감사 표본 `ceil(자동 발행 N × 20%)`이 1건 이상 자동 선정되고, 선정된 표본의 감사와
   다음 회차 open/close 판정이 자동으로 끝난다. 전수 감사를 새 선행조건으로 만들지 않는다.
   중복·자기 댓글 보호와 공개면/DB 일치가 통과한다.
6. 비용·runner 건강·복구·rollback 이 승인 범위 안이다.
7. 공개된 증명 글 자체가 현재 원문 증거·release 판정 계약을 만족한다.
8. 다음 단계 결정이 자동으로 기록된다.

수동 `--apply`, `manual-live`, 임시 env override, 운영자 발행·댓글은 진단 또는 commissioning이다.
이 결과로 D3·D5·D10·D20·D30·D50·D100 PASS를 선언하지 않는다.
사람이 승인한 READY 가 예약 작업으로 발행되더라도 정상 서비스 물량일 뿐 자동 단계의
목표 편수에는 포함하지 않는다. 단계 목표 편수는 자동 READY 글만으로 채워야 한다.

- PASS 이고 다음 단계 준비도가 green 이면 다음 증명일을 자동으로 잡는다. 같은 날 남은 유효 슬롯으로
  다음 목표 전체를 증명할 수 있으면 즉시 시작하고, 그럴 수 없으면 다음 KST 운영일의 첫 유효 슬롯에서
  시작한다. 임의의 달력 대기를 넣지 않는다. 사람이 env나 stage를 바꾸지 않는다.
- FAIL 또는 UNKNOWN 이면 원인을 고친 뒤 같은 단계의 증명일을 다시 잡는다. 실패 뒤 재시험은 증명일로만 하고,
  증명일 사이를 매일의 자동 재증명으로 채우지 않는다. 다른 개발은 멈추지 않는다.
- 🔴 **단계 authority 는 하나다**: 그날의 단계는 `StageDecision` 행 하나가 정한다. GitHub stage Variables ·
  env 의 단계 값 · canary 창은 단계를 정하지 않는다. **자동 일정 owner 도 하나다**: D100 레인 job 은 상시 호스트의
  launchd 하나가 돌린다(GitHub Actions 예약과 겹치지 않는다). 구현·배포 상태는 `CURRENT-MILESTONE.md` 가 적는다.
- 🔴 **상시 호스트는 D100의 마지막 마일스톤이 아니라 모든 증명일의 선행조건이다.** 운영 창에 잠들거나
  덮개가 닫히는 개인 이동용 노트북은 유일한 owner가 될 수 없다. M7은 상시 호스트를 처음 마련하는 단계가 아니라,
  장애 복구와 반복 지속성을 D100 규모에서 증명하는 단계다.
- 🔴 **계약 경계**: 더 약한 release 계약 아래 만든 옛 증명은 계약이 바뀐 뒤 더 높은 단계를 열지 못한다.
  다시 증명하거나 증거로 이관한다.

## 7. 생동감 계약 — 원문의 참여 동력을 보존한다

- 논쟁, 연예, 방송, 가십, 결혼, 시가·친정, 돈, 일, 평범한 건강 질문, 거친 불만과 이견을
  단지 불편하다는 이유로 제거하지 않는다.
- 원천의 긴장, 질문, 관점과 받아칠 거리를 보존한다. 남녀 갈등이 반응의 원인이면 그 쟁점을
  일반적인 위로·교훈으로 평탄화하지 않는다.
- 잔잔한 원천은 잔잔하게 살려도 된다. 원천에 없는 논쟁·분노·선정성을 만들어내지 않는다.
- 선택은 원천 상대 반응 증거와 원문 나이를 §2 판정 하나로 쓰고, 생성은 논쟁·공감·궁금증·
  시의성·생활 효용·웃음 중 실제 참여 동력을 보존한다.
- 참여 신호는 안전·사실 검사를 우회하지 않는다. 성별 전체 비하, 허위 단정, 표적 공격은
  계속 막되 불편한 의견이나 성별 간 입장 차이 자체를 결함으로 보지 않는다.
- 위해와 주제를 분리한다. 개인정보, 실제 회원 원문, 명예훼손성 단정, 괴롭힘·혐오·위협,
  위험한 의료·재무 지시, 실질 복제는 계속 막는다.
- Founder gold와 최근 운영 HOLD·DROP을 모든 품질 계약 변경에서 함께 재생한다. 안전한 논쟁
  소재의 false HOLD·DROP 증가는 회귀다.
- 같은 도입·결말·길이·말투·질문형을 반복하는 Persona 동질화도 품질 실패로 측정한다.
- 🔴 **창작 허용 경계** (2026-10-19): 원문 핵심을 바꾸지 않는 감상·반응·독자 질문·비유·연결 문장·일반 관찰·
  새로운 구성은 허용한다. 원문 요약문만 만들기 위해 이런 표현을 결함으로 보지 않는다.
- 원문에 없는 배우자·자녀·건강·돈·나이·거주지 같은 Persona 개인 사실, 사건 당사자에 관한 새 주장,
  허가되지 않은 실제 경험형 1인칭 서사, 사실관계·결론의 왜곡, 중요한 내용 누락, 사진·영상 없이는 완성되지 않는 글,
  잘린 원문을 완성한 척하는 글은 계속 차단한다.
- 평범한 욕·거친 말·가십·불만·안전한 이견은 자동 reject 사유가 아니다. 개인정보 침해 · 근거 없는 사실 단정 ·
  명예훼손 · 위협·혐오·괴롭힘 · 위험한 의료 지시 · 실질 복제 · 정치 선동은 hard gate 다.
- 🔴 **기계 초안 자동 생명주기** (2026-10-19): 현재 품질 계약에서 자동 적격인 초안은 다음 자동 READY 도장까지
  `autoReadyPending` WIP로 센다. 경고·품질 예외는 `qualityQuarantine`으로 자동 발행하지 않고 Persona WIP도
  점유하지 않는다. 옛 계약·무효 도장·gate 차단 행은 증거로 보존하지만 routine 운영자 구제 대상으로 삼지 않는다.
- 창업자·운영자는 기계 초안마다 `ready/edit/reject`를 결정하지 않는다. 실제 데이터 복구·배정 예외 같은 운영 장애만
  사람 복구 대상으로 남긴다. 발행 후 20% 표본 감사와 확정 결함 차단은 그대로 유지한다.
- 격리된 과거 초안을 살리는 무제한 자동 재작성 lane은 만들지 않는다. 재작성은 현재 원천·현재 수요 안에서 생성
  품질과 비용이 증명된 별도 개선으로만 도입한다.

- 출처 사이트·원천 게시판·Persona·검색어로 게시판을 추정하지 않는다. 레몬테라스·우아한갱년기·향후 82cook 모두

- 현재 판(`auto-judge-v4`)은 `boardTopic`이 없거나 `null`·잘못된 값이면 발행하지 않는다(fail-closed).
- 실제로 운영됐던 호환 판은 `auto-judge-v3` 하나다. `autoJudge` 자체가 없거나 v3인 옛 행만 자유게시판으로
  보존한다. 존재하는데 손상됐거나 모르는/미래 판이면 임의로 자유게시판에 보내지 않고 발행을 막는다.

### 7.1 정치와 공개 인물을 한 필터로 묶지 않는다

- 창업자가 확정한 정치인·정당·선거운동·정치 선동 목록은 제외한다.
- 연예인·배우·가수·방송인·셀럽·드라마·예능은 정상 원문 기회다. 이름이 있다는 이유로 수집 전
  제거하지 않고, §2의 반응·현재성·대화 가치 판정으로 경쟁시킨다.
- 루머를 사실로 단정하기, 사생활 침해, 가족 공격, 명예훼손, 혐오·괴롭힘은 공개 인물 여부와 별개의
  hard gate다. 정치 필터를 이 안전 검사 대신 쓰지 않는다.
- 최저임금·전세·상속·세금·의료처럼 정치 기사에도 나오는 단어가 생활 경험에 등장했다는 이유만으로
  생활 글을 막지 않는다. 정치적 조직화·선동과 생활 이야기를 문맥으로 분리한다.

### 7.2 홈·베스트는 실회원 반응을 우선한다

- Persona 댓글 수를 실회원 인기처럼 합산해 홈 순위를 올리지 않는다. 합성 활동은 운영 지표로 따로 센다.
- 홈은 현재성·실회원 반응·대화 가능성을, 베스트는 검증된 실회원 참여를 우선한다.
- 자동 글도 홈·베스트 후보가 될 수 있지만, Persona끼리 만든 반응만으로 인기 글이 되면 실패다.

### 7.3 고객 조회수는 실제 열람·노출만 센다 (2026-10-15)

- 고객 화면은 기존처럼 댓글 수와 조회수를 단순하게 표시한다. 별도 합성 활동 배지나 무작위 숫자를 만들지 않는다.
- 공개 조회수는 실제 상세 열람과 실제 목록 노출을 합산할 수 있다. 내부 원장에서는 두 값을 분리하고, 같은 방문자의
  짧은 반복을 중복 제거하며 관리자·Persona·자동화·검색봇을 제외한다.
- 댓글 수에 임의 배수를 곱하거나 최소값·난수를 더한 수를 조회수라고 표시하지 않는다.
- 조회수는 North Star가 아니며, Persona 활동이나 공개 조회수를 실회원 반응으로 바꿔 홈·베스트 순위를 올리지 않는다.

## 12. 구현과 보고

`npm run d100:readiness`는 위 정책 목표와 현재 코드·runtime·DB의 차이를 만든다. 보고서는
다음 값을 반드시 분리한다.

- 증명일 준비도(증명일 슬롯의 slot-valid 기회 + 실측 보충 용량) / 지속 준비도(반복 관측)
- canary Persona 하한 / 지속 다양성 목표 / contract-valid 수(active 행 수 아님)
- 첫 운영 PASS / 반복 안정성
- 지원 scheduler / 미구현 scheduler
- 자동 stage 전이 / 사람 명령 또는 env override

단계는 `d3 · d5 · d10 · d20 · d30 · d50 · d100`이다. 구현이 표와 다르면 문서를 현재 코드에
맞추지 말고 충돌로 보고하고 코드를 정본에 맞춘다.

보수적인 canary 가 그것을 가를 첫 관측이다.
