## §1 이 Gate 의 목적

### 🔴 자동 발행을 **가능하게 하기 위한** 방어선이다

**Gate 는 자동 발행을 막기 위한 장치가 아니다.** 최종 목표는 완전 자동화이고
([전략 §4-0](2026-08-29-persona-network-strategy.md)), Gate 는 **그 자동화를 열 수 있게 만드는 방어선**이다.

🔴 **Gate 통과의 의미는 단계에 따라 다르다.**

| 단계 | Gate 통과 = |
|---|---|
| **1. MVP / 초기 검증** | **운영자 승인 대기열 진입** — 발행이 아니다 |
| **2. 제한 자동화** | 저위험 유형은 **발행 가능 후보** |
| **3. 완전 자동화** | **발행 가능 후보** — 어드민은 관제 · 중지 · 감사 |

```
실패       →  재생성 (최대 3회)
반복 실패  →  폐기
```

Gate 없이는 어느 단계도 열 수 없다. **Gate 가 튼튼할수록 자동화를 빨리 연다.**

### 왜 생성기보다 먼저 만드는가

VE-M3 에서 배운 것이다.

> **가드를 나중에 붙이면 이미 나간 것을 되돌릴 수 없다.**

VE-M3 전량 분석 9,411건에서 저장 output 20자 유출 **0건** · 금지 호칭 저장 **0건** ·
raw output 전문 저장 **0건** 을 지킬 수 있었던 이유는, 가드가 **실행보다 먼저** 있었기 때문이다.
33건이 terminal skip 됐는데 그것은 실패가 아니라 **가드가 일한 증거**다.

생성기를 먼저 만들면 "일단 만들고 나중에 막자" 가 된다. 그 순서는 되돌릴 수 없다.

## §2 Gate 의 위치

```
① Crawler / Trend Ingestion
        ↓
② Topic / Story Extraction          🔴 문장이 아니라 구조를 추출
        ↓
③ Persona Matching                  누구의 경험인가
        ↓
④ Draft Generation                  Identity + Variation + Mood
        ↓
🔴 ⑤ Safety / Originality Gate      ← 여기서 막지 못하면 사람에게 간다
        ↓
⑥ Publish Gate                      1단계 승인 · 3단계 자동 (전략 §4-1)
        ↓
⑦ Publish
        ↓
⑧ Metrics Loop                      → 다음 선택에 반영
```

**Gate 는 ④와 ⑥ 사이에 있다.** 생성물이 사람 눈에 닿기 전 마지막 자동 관문이다.

🔴 **위기 신호만 예외다.** ①~③ 단계에서 감지되면 **④ 생성 자체를 시작하지 않는다**(§4).

## §3 9개 필수 관문

각 관문은 독립이다. 하나라도 실패하면 그 자리에서 멈춘다.

### ① 20자 연속 유출

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물 전문 ↔ source body · source comments · 학습 anchor(voice_gold few-shot) |
| **실패 기준** | 공백 제거 후 **20자 이상 연속 일치 1건** |
| **조치** | 🔴 `regenerate` — 1건이라도 예외 없음 |
| **재사용 자산** | 🟢 `assertNoSourceLeak(outputText, sourceTexts, minRun = M3_LEAK_RUN_MIN)` — **그대로 쓸 수 있다.** 9,411건에서 검증됨 |
| **새로 필요** | 대조 대상에 **학습 anchor 추가** (VE-M3 는 원문만 봤다) |

**실측으로 확인한 시그니처**
```ts
assertNoSourceLeak(outputText: string, sourceTexts: readonly string[], minRun = M3_LEAK_RUN_MIN)
  → { ok: boolean; leaked: boolean }
공백을 제거하고 비교한다 — 띄어쓰기로 우회할 수 없다
```

🔴 **`minRun` 을 호출부에서 넘기지 않는다.** VE-M3 fixture 가 인자 3개 호출을 차단하고 있고,
같은 규칙을 Gate 에도 적용한다. 완화 가능한 가드는 가드가 아니다.

#### 🔴 댓글이라고 20자 룰을 완화하지 않는다

②는 생성물 종류에 따라 코퍼스를 바꾸지만, **①은 바꾸지 않는다.**

```
🔴 A-grade seed 라도 20자 이상 동일하면 복붙 위험으로 본다
🟢 A-grade seed 는 본래 짧다 — "맞아요"(3자) · "고생하셨어요"(6자)
   20자에 닿지 않으므로 애초에 ① 에 걸리지 않는다
🔴 20자 이상 연속 일치가 나왔다면 그것은 seed 가 아니라 문장 복사다
```

**①은 seed 정책의 안전핀이다.** ②를 댓글 쪽으로 넓히면서 ①까지 함께 풀면
"짧은 반응 허용" 이 "댓글 복사 허용" 으로 미끄러진다.

### ② 고유 표현 / 특이 조어 복제

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물 ↔ source 의 **희귀 n-gram** |
| **실패 기준** | 아래 3단 판정 |
| **조치** | 희귀도 높음 → `regenerate` · 중간 → `review` |
| **재사용 자산** | 🟡 없음 |
| **새로 필요** | 🔴 **희귀도 사전 2벌**(본문 · 댓글) + n-gram 추출기 |

**20자 룰로 못 잡는 것을 잡는다.** *"남의편"* 같은 표현은 3글자라 ①을 통과하지만,
그 사람의 말버릇이라면 복제해서는 안 된다.

#### 🔴 기준 코퍼스는 **생성물 종류에 따라 다르다**

```
post / body 생성물   본문 코퍼스
                     voice_gold 135 + voice_silver 1,065 + story_topic 1,304 = 2,504건

comment 생성물       댓글 코퍼스
                     VoiceCommentSignal 대상 댓글 59,252건 (9,674글)
```

🔴 **댓글 생성물을 본문 코퍼스로 재면 자연스러운 짧은 반응이 오탐된다.**
사람들이 댓글에서 하루에도 수백 번 쓰는 말이 본문에는 거의 나오지 않기 때문이다.

```
실측 (동일 표현, 코퍼스만 바꿔 측정)

  표현            본문 코퍼스 2,504건        댓글 코퍼스 59,252건
  ────────────────────────────────────────────────────────────────
  맞아요           12건  🟢 허용              441건  🟢 허용
  힘내세요          2건  🟡 review            191건  🟢 허용
  저도요            1건  🔴 regenerate         76건  🟢 허용
  그러게요          1건  🔴 regenerate         74건  🟢 허용
  고생하셨어요      0건  🔴 regenerate         69건  🟢 허용
  공감해요          0건  🔴 regenerate         42건  🟢 허용

🔴 본문 코퍼스만 쓰면 위 6개 중 4개가 regenerate 된다.
   댓글에서 가장 흔한 맞장구가 "고유 표현" 으로 잡히는 것이다.
```

```
판정 3단 (코퍼스는 생성물 종류에 맞춰 고른다)
  a. source 에서 3~10자 n-gram 추출
  b. **해당 코퍼스** 빈도 조회
  c. 희귀도 판정
       코퍼스 빈도 0~1회  → 🔴 고유 표현. 생성물에 있으면 regenerate
       빈도 2~5회         → 🟡 review
       빈도 6회 이상      → 🟢 일반 표현. 허용
```

🔴 **"흔한 표현" 의 기준을 코퍼스로 정한다.** 사람이 목록을 관리하면 반드시 빠진다.
🔴 **코퍼스를 섞지 않는다.** 본문 생성물을 댓글 코퍼스로 재면 반대 방향의 오탐이 난다 —
본문에 쓰면 안 될 구어 표현이 "흔하다" 는 이유로 통과한다.

#### 🔴 comment seed 등급은 **2축**으로 정한다

[M3 반응 지도](2026-08-30-m3-reaction-map-design.md)가 원문 댓글을
**source comment seed 기반 재맥락화**에 쓴다. 그 등급 판정의 계약을 여기 고정한다.

```
축 1  빈도축 — 위 댓글 코퍼스 희귀도
        빈도 6회 이상   → A 후보
        빈도 2~5회      → B 후보
        빈도 0~1회      → C 후보

축 2  내용안전축 — 빈도와 무관하게 등급을 끌어내린다
        의료 · 법률 · 재무 조언
        식별 디테일 (지명 · 기관 · 병원 · 날짜 · 금액)
        개인 경험의 구체 사실
        닉네임 · 외부 커뮤니티 흔적
        Persona identity 와 맞지 않는 1인칭 경험

🔴 최종 등급 = 두 축 중 **더 엄격한 쪽**을 따른다
```

🔴 **자주 나오는 문장이어도 내용이 위험하면 A 가 될 수 없다.**

```
실측 예 — 빈도축과 내용안전축이 어긋나는 경우
  "병원 가보세요"   댓글 코퍼스 11건 → 빈도축 A
                    그러나 의료 조언 → 🔴 내용안전축 C
                    최종 등급 C. 문장 재사용 금지, 역할만 쓴다
```

| 등급 | 문장 | 역할 | 비고 |
|---|---|---|---|
| **A** | 🟢 유사 표현 seed 허용 | 🟢 | 🔴 동일 문장 반복 · 외부 호칭 금지 |
| **B** | 🟡 페르소나 voice 로 재작성 | 🟢 | 1인칭 경험은 identity 와 맞을 때만 |
| **C** | 🔴 재사용 금지 | 🟢 역할만 | 구조만 참고 |

#### 🔴 용어를 고정한다

```
🟢 쓴다     source comment seed 기반 재맥락화
🔴 안 쓴다  "댓글 복붙 허용" · "약간 수정" · "살짝 고쳐서 가져오기"
```

이 정책은 **댓글 문장을 복사하는 시스템이 아니다.** seed 는 페르소나의
identity · voice variation · mood · memory 에 맞게 **다시 말해야** 한다.

### ③ 식별 디테일

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물의 고유명사 · 수치 · 관계 조합 |
| **실패 기준** | 아래 카테고리 **2개 이상 결합** |
| **조치** | 2개 → `review` · 3개 이상 → `regenerate` |
| **재사용 자산** | 🟡 VE-M3 의 `IDENT` 판정 정규식(개념만) |
| **새로 필요** | 카테고리 분류기 · 결합 판정 |

```
카테고리
  지명(시·구·동) · 병원 · 학교 · 회사 · 구체 날짜 · 정확한 나이
  금액 · 가족관계 특이조합 · 희귀 사건

🟢 단일 일반 표현은 허용
   "집 근처 병원" · "50대 초반" · "수도권"
🔴 2개 이상 결합은 특정 가능
   "분당 ○○병원" + "3월 12일" → review
   + "둘째 딸 결혼식 전날" → regenerate
```

🔴 **페르소나의 1인칭 경험 진술에는 더 좁게 적용한다.**
회원의 사적인 이야기는 본인의 사실이지만, 페르소나의 "저도 그랬어요" 는 **없었던 일**이다.
없었던 일에 검증 가능한 사실이 붙으면 그것은 공감이 아니라 **판단 근거**가 된다(§5).

```
🟢 허용   "저도 그맘때 그랬어요"                    구체 사실 없음
🔴 금지   "저도 그때 ○○병원 다녀와서 괜찮아졌어요"   기관 + 결과
🔴 금지   "저는 그거 3개월 먹고 나았어요"            약/기간 + 결과
```

**사적인 이야기가 위험한 게 아니다.** 위험한 것은 **결합**이다.
이 원칙은 [학습 후보 선별 정책](2026-08-29-voice-m3-learning-policy.md) 에서 확정한
*"식별 디테일은 차단이 아니라 일반화"* 와 같다.

### ④ 원문 문장 순서 / 구조 과복제

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물의 사건 전개 순서 ↔ source 전개 순서 |
| **실패 기준** | 🔴 **핵심 전개 3개 이상이 같은 순서** |
| **조치** | 3개 → `review` · 4개 이상 → `regenerate` |
| **재사용 자산** | 🟡 없음 |
| **새로 필요** | 전개 단위 추출 · 순서 정렬 비교 |

**문장을 다 바꿔도 사건 순서가 같으면 그것은 복제다.**

```
🟢 허용 — 흔한 상황 구조
   "일이 있었다 → 속상했다 → 시간이 지났다"
   "병원에 갔다 → 검사했다 → 결과를 기다린다"
   → 이런 구조는 누가 써도 비슷하다. 막으면 아무 글도 못 쓴다

🔴 차단 — 고유 전개
   source 특유의 사건 순서가 3개 이상 그대로 유지되는 경우
```

판정은 **일반 구조 사전**을 두고, 거기 없는 전개가 순서까지 같을 때만 잡는다.

### ⑤ 금지 호칭 / 브랜드 금칙어

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물 전문 |
| **실패 기준** | 금칙어 **1개라도 포함** |
| **조치** | 🔴 `regenerate` — 저장·발행 전 반드시 차단 |
| **재사용 자산** | 🟢 **상수 두 갈래** — `TARGET_DESCRIPTOR_TERMS`(15) · `BRAND_BANNED_WORDS`(4). 아래 🔴 참조 |
| **새로 필요** | 두 갈래를 함께 보는 판정부 (상수 자체는 이미 있다) |

#### 🔴 ⑤ 는 상수 **하나**가 아니라 **둘**을 본다

이전 판본은 `M3_FORBIDDEN_ADDRESS_TERMS` 하나만 보면 *시니어 · 어르신 · 노인 · 실버*까지
잡히는 것처럼 적었다. **그 상수에 그 네 단어는 없다.** 실측으로 정정한다.

```
갈래 1  타겟 설명어 — "우리가 만들어내면 안 되는 설명"
  scripts/lib/voice-style-signals.mts : TARGET_DESCRIPTOR_TERMS (15개)
  → voice-m3-contract.mts 가 M3_FORBIDDEN_ADDRESS_TERMS 로 재수출
     '우리 또래분들' · '우리 또래 분들' · '우리또래분들' · '우리 또래'
     '40대 여성분들' · '50대 여성분들' · '60대 여성분들'
     '40대 여성' · '50대 여성' · '60대 여성'
     '중년 여성분들' · '중년 여성' · '같은 세대 분들' · '같은 세대분들' · '같은 세대'
  🔴 시니어 · 어르신 · 노인 · 실버 는 여기 없다

갈래 2  브랜드 금지어 — "브랜드가 쓰지 않는 말"
  src/lib/content-guard.ts : BRAND_BANNED_WORDS (4개)
     '시니어' · '어르신' · '노인' · '실버'

허용 기준선
  SORANSORAN_REGISTER_TERMS (4개) → M3_ALLOWED_ADDRESS_TERMS
```

**둘 다 보지 않으면 ⑤ 는 절반만 작동한다.** 문서대로 갈래 1만 붙이면
페르소나가 "어르신" 이라고 써도 통과한다.

#### 🔴 회원 글과 페르소나 생성물은 다르다

`src/lib/micro-seed-guard.ts` 에 의도가 주석으로 남아 있다 —
**회원이 자기 말로 "어르신" 이라고 쓰는 것까지 막지 않는다.** 그건 회원의 말이다.

```
회원이 쓴 글        → BRAND_BANNED_WORDS 적용 안 함  (의도된 예외)
페르소나 생성물      → 🔴 적용한다. 운영 생성물이지 회원의 말이 아니다
```

`scripts/` 에서 `src/lib` import 는 이미 여러 곳에서 쓰이므로 경로 제약은 없다.

🔴 **원문에 있어도 우리가 만들어내지 않는다.** 이것이 VE-M3 의 원칙이고 Gate 도 그대로 따른다.
계약 주석에 *"'우리 또래분들' 이 한 번 좋은 치환어로 문서에 적혔다가 폐기됐다(PR #100).
사람은 같은 실수를 반복한다"* 고 적혀 있다.

#### 🔴 ⑤ 와 ⑨ 는 다른 관문이다

| | ⑤ 금지 호칭 / 브랜드 금칙어 | ⑨ Source Community Marker |
|---|---|---|
| 막는 것 | **소란소란 브랜드 · 대상 호칭 정책 위반** | **외부 출처의 흔적** |
| 예 | 우리 또래분들 · 중년 여성 (설명어) · 시니어 · 어르신 · 노인 · 실버 (브랜드 금지어) | 82님들 · 우갱님들 · 레테님들 · 우리 카페 |
| 근거 | 브랜드 규칙 (원문에 있어도 만들지 않는다) | 재맥락화 실패 (여기 글이 아니게 된다) |
| 자산 | 🟢 `TARGET_DESCRIPTOR_TERMS` 15 **+** `BRAND_BANNED_WORDS` 4 — **둘 다 이미 있다** | 🟢 `SOURCE_SPECIFIC_TERMS` 8 을 **확장한다** (백지 아님) |

**두 관문을 합치면 안 된다.** 하나는 브랜드 정책이고 하나는 출처 세탁이다.
실패했을 때 필요한 조치도 다르다 — ⑤는 표현 교체, ⑨는 **호칭이 필요한지부터 재검토**.

### ⑥ 닉네임 / author 재사용

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물 ↔ source comment author · 회원 닉네임 · 학습 데이터 author |
| **실패 기준** | 1건이라도 등장 |
| **조치** | 🔴 `regenerate` |
| **재사용 자산** | 🟢 PR #200/#204 의 두 함수 원칙 |
| **새로 필요** | 회원 닉네임 대조 (실시간 조회) |

### 🔴 두 함수의 비대칭을 그대로 유지한다

```
학습 추출 (commentBodiesForLearning)
  content 만 읽는다. author 에 **접근조차 하지 않는다**
  → 닉네임을 문체로 배우지 않게

유출 대조 (topCommentsToText)
  author 를 **포함해서** 넓게 읽는다
  → 닉네임이 생성물에 섞여 나오는 것도 잡아야 하므로
  → 실측: author 포함 시 대조 문자열이 8.8% 넓어진다 = 놓칠 위험이 준다
```

**Gate 는 후자를 쓴다.** 학습에서 뺀 것과 검사에서 빼는 것은 정반대 방향이다.

### ⑦ Persona Consistency

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물 ↔ Persona Identity · Voice Core · No-Go · SelfMemory |
| **실패 기준** | 모순 1건 |
| **조치** | `regenerate` (같은 persona 로 prompt 수정) 또는 persona 변경 |
| **재사용 자산** | 🟡 없음 |
| **새로 필요** | 사실 추출기 + 모순 판정 |

```
🔴 모순 예시
   이혼 · 사별 · 별거 설정인데 남편과 화목한 현재형 서술
   자녀 없음인데 딸 결혼 이야기를 자기 경험처럼
   갱년기 후 설정인데 갱년기 시작 전처럼
   작년에 "자녀 둘" 이라 했는데 오늘 "하나"
   No-Go 에 걸리는 말
```

🔴 **설정과 일치해도 걸리는 것이 있다.**
⑦ 은 *페르소나가 자기 설정과 모순되는가* 를 본다. 그런데 설정과 완벽히 일치하면서도
**읽는 사람이 사실로 믿고 판단하게 만드는 진술**이 있다.

```
🔴 존재하지 않는 가족의 검증 가능한 사실을 판단 근거처럼 쓰는 것
   "우리 딸도 그 병원 갔어요"          ← 설정에 딸이 있어도 금지
   "저희 남편도 그 약 먹고 좋아졌어요"   ← 설정에 남편이 있어도 금지
```

설정상 딸이 있는 것과, **그 딸의 병원 경험을 남의 결정 근거로 내미는 것**은 다르다.
⑦ 은 이것도 `regenerate` 로 잡는다. 판정 기준은 §5 의 1인칭 경험 진술 경계를 따른다.

**Mood 는 표현의 진폭만 바꾼다**([Architecture §6](2026-08-30-persona-architecture-design.md)).
mood 를 이유로 관계나 사실이 바뀌면 그것은 모순이다.

### ⑧ Voice Fingerprint / 반복 패턴

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물 ↔ **같은 persona 의 최근 발행물** · 🆕 **최근 전체 발행물의 seed 사용 이력** |
| **실패 기준** | 상위 빈출 n-gram 점유율 임계 초과 · 🆕 동일 seed 재사용 간격 미달 |
| **조치** | `regenerate` — **다른 variation 또는 다른 seed 로** |
| **재사용 자산** | 🟢 헌법 §9-7 **문장 지문 중복률** 개념 · `VoiceVariation` 모델 |
| **새로 필요** | n-gram 점유율 계산기 · 🆕 **seed 사용 이력 저장** · 임계 확정 |

**고정 말투 1개가 반복되어 AI 티 나는 것을 막는 관문이다.**
[Architecture §5](2026-08-30-persona-architecture-design.md) 의 Voice Variations ·
Mood State · Activity Rhythm 과 직접 연결된다.

```
검사 축
  최근 N건의 시작 문장 패턴      같은 hookType 반복
  말끝 분포                     같은 ending 반복
  이모티콘 패턴                 빈도 · 위치
  구조화 나열 / 마크다운 말투     🔴 "추천드립니다" · 먼저/다음으로/마지막으로
                                불릿 · 번호 · 마크다운 · 과도한 존댓말 일관성
  상위 빈출 n-gram 점유율        🔴 헌법 §9-7 역지표
  🆕 seed 재사용                 같은 source comment seed 의 반복 배분

🔴 우나어에는 이 지표가 없어 225명의 실효 다양성을 아무도 몰랐다.
```

#### 🆕 seed 재사용 축 — `seedReuseRate`

②가 A 등급 seed 를 허용하는 순간 새 위험이 생긴다.

```
🔴 같은 source comment seed 가 여러 페르소나에게 반복 배분되면 AI 티가 난다
   "맞아요" 는 개별로는 자연스럽지만, 세 페르소나가 나란히 쓰면 기계다
   같은 맞장구 · 같은 시작 문장 · 같은 결말이 반복되면 ⑧ 이 잡는다
```

**②는 "이 표현을 써도 되는가" 를 보고, ⑧은 "이 표현을 또 쓰는가" 를 본다.**
두 관문이 같은 seed 를 다른 각도에서 본다 — 어느 하나로 합칠 수 없다.

```
검사 축 (seed 재사용)
  같은 seed 의 최근 N건 내 사용 횟수
  여러 페르소나에 걸친 동일 seed 배분율      🔴 persona 단위가 아니라 전체 단위로 본다
  같은 hookType · ending 의 반복             기존 축과 함께 본다

🔴 수치 기본값은 **구현 시 결정**한다.
   운영 데이터 없이 임계를 정하면 오탐이거나 무력하다.
   조정 손잡이가 있다는 것만 여기서 고정한다.
```

🔴 **`seedReuseRate` 는 AI 티가 났을 때 낮추는 손잡이다.**
[M3 반응 지도](2026-08-30-m3-reaction-map-design.md)의 `roleWeights` ·
`firstRole` 후보 · `commentCount` range · persona eligibility 와 같은 층에 둔다.

🔴 **"AI 말투"를 별도 관문으로 두지 않는다.** 구조화 나열 · 마크다운 말투는 **⑧의 축 하나**다.
문제의 뿌리가 같기 때문이다 — *고정된 한 가지 말투가 반복되어 사람이 쓴 글로 읽히지 않는 것*.
따로 세면 관문 수만 늘고, 실패 로그에서 원인이 두 곳으로 갈라진다.

```
🟢 오히려 필요한 것
  오타 · 불규칙 띄어쓰기 · 줄바꿈 습관 · "ㅋㅋ" · "..." 같은 구어 표지
```

### ⑨ Source Community Marker — 외부 커뮤니티 흔적

| 항목 | 내용 |
|---|---|
| **검사 대상** | 생성물 전문 ↔ **sourceSite 별 marker dictionary** · 외부 커뮤니티 별칭 · 카페 내부 호칭 |
| **실패 기준** | marker 1건이라도 잔존 |
| **조치** | 기본 `regenerate` · 애매하면 `review` · 🔴 source 자체가 카페 운영/공지/광고 문맥이면 `reject` |
| **재사용 자산** | 🟢 `SOURCE_SPECIFIC_TERMS` (**8개 · site 매핑 포함**) · `computeCommunityRegister()` · 🟡 VE-M3 `sourceSite` 메타데이터 |
| **새로 필요** | 출처 맥락어 · 신규 sourceSite marker · alias 보강 · 소란소란 호칭 variation list |

**20자 유출이 없어도 외부 커뮤니티 내부 호칭이 남으면 소란소란 글이 아니다.**
①이 잡는 것은 *문장의 복제*이고, ⑨가 잡는 것은 *출처의 흔적*이다. 둘은 다른 문제다.

#### 🟢 marker dictionary 는 백지에서 시작하지 않는다 — 씨앗이 이미 있다

이전 판본의 *"marker dictionary 를 새로 만든다"* 는 부정확하다. **site 매핑까지 붙은 8개가 이미 있다.**

```
실측 — scripts/lib/voice-style-signals.mts : SOURCE_SPECIFIC_TERMS
  82님들 · 82님          → 82cook
  우갱님들 · 우갱님       → navercafe:wgang
  레테님들 · 레테님       → navercafe:remonterrace
  은오님들 · 은오님       → navercafe:dlxogns01

주석: "🔴 치환 대상이다. 그대로 쓰면 소란소란 글이 다른 커뮤니티에서 옮겨온 티를 낸다"
```

`computeCommunityRegister()` 는 **긴 것부터 세는 중복 방지 로직**까지 갖고 있다
(`82님들` 을 먼저 세지 않으면 `82님` 이 두 번 잡힌다).
**⑨ 는 이 함수를 확장하는 작업이지 새로 만드는 작업이 아니다.**

| 구분 | 내용 |
|---|---|
| 🟢 **확장** | `SOURCE_SPECIFIC_TERMS` 8개 — 기존 4개 출처의 호칭 |
| 🔴 **추가 자산** | 출처 맥락 표현 — `우리 카페` · `이 카페` · `카페 회원님들` (상수에 없다) |
| 🔴 **추가 자산** | 출처별 별칭 · 약칭 보강 |
| 🔴 **추가 자산** | 신규 `sourceSite` 의 marker |
| 🟡 **별도 확인** | `sourceSite` **6종** 대비 기존 marker 가 **4종**만 덮는다 — 갭 확인은 read-only 과제로 남긴다(§14-⑬) |

#### Source Community Marker 의 정의

```
외부 커뮤니티 이름 · 별칭 · 약칭
외부 카페 내부 호칭 (그 카페에서만 자연스러운 부름말)
외부 카페 운영 문구 (공지 · 등업 · 규정 안내)
출처 맥락 표현 — "우리 카페" · "이 카페" · "카페 회원님들"
```

#### 예시 (유형 예시일 뿐, 실제 sourceRef·URL·원문은 담지 않는다)

| 유형 | 예 |
|---|---|
| 커뮤니티명 · 약칭 | `82쿡님들` · `82님들` · `레몬테라스님들` · `레테님들` |
| 카페 내부 호칭 | `우갱님들` · `우갱 언니들` · `은오 회원님들` |
| 역할 기반 호칭 | `맘님들` · `선배맘님들` · `카페 회원님들` |
| 출처 맥락 | `우리 카페` · `이 카페` · `여기 카페에서는` |

#### 실패 판정 5종

```
□ 생성물에 외부 출처명이 남아 있다
□ 외부 커뮤니티 내부 호칭이 남아 있다
□ 외부 카페 맥락의 "여기 / 우리 / 카페" 가 그대로 남았다
□ 원문 댓글 닉네임이나 외부 카페 호칭을 **소란소란 호칭처럼 재사용**했다
□ sourceSite 별 marker dictionary 에 걸리는 표현이 있다
```

#### 🔴 단순 일괄 치환은 금지한다

```
🔴 금지  "82쿡님들" → "소란소란님들" 로 기계적 치환
```

치환하면 문장은 통과하지만 **말투가 죽는다.** 그 자리에 호칭이 꼭 필요한지부터 다시 본다.
댓글은 호칭 없이 바로 공감으로 시작해도 된다.

## §3-1 🔴 소란소란 내부 호칭 원칙

⑨가 외부 호칭을 걷어낸 자리에 **무엇을 넣을 것인가**의 문제다.

### 무조건 "소란소란님들" 로 치환하지 않는다

```
🔴 금지  모든 외부 호칭 → "소란소란님들" 일괄 치환
```

**항상 같은 호칭을 쓰면 그것이 곧 AI 티다.**
[Architecture §5](2026-08-30-persona-architecture-design.md) 의 Voice Variations 와
같은 이유다 — 고정된 표현의 반복이 사람이 아님을 드러낸다.

### 페르소나 성향별 선택

| 성향 | 어울리는 호칭 |
|---|---|
| 조심스러운 | `여기 계신 분들` · `혹시 저 같은 분 계세요?` · `저만 이런가요?` |
| 친근한 | `언니들` · `소란님들` |
| 담담한 | **무호칭** |
| 공통 | 🟢 **댓글은 호칭 없이 바로 공감으로 시작해도 된다** |

```
🔴 한 페르소나가 같은 호칭만 반복하면 ⑧ Voice Fingerprint 에 걸린다
```

### 🔴 허용 후보와 코드 상수의 충돌 — 결정 필요

Codex 가 제시한 허용 후보 중 **`우리 또래분들` 은 코드상 금지어다.**

```
실측 — scripts/lib/voice-style-signals.mts

TARGET_DESCRIPTOR_TERMS (15개, ⑤ 가 차단)
  '우리 또래분들' · '우리 또래 분들' · '우리또래분들' · '우리 또래'
  '40대 여성분들' · '50대 여성분들' · '60대 여성분들' · '40대 여성' · '50대 여성' · '60대 여성'
  '중년 여성분들' · '중년 여성' · '같은 세대 분들' · '같은 세대분들' · '같은 세대'

SORANSORAN_REGISTER_TERMS (4개, 허용)
  '소란소란님들' · '소란소란님' · '소란님들' · '소란님'
```

**⑨가 `우리 또래분들` 로 치환하면 ⑤가 즉시 `regenerate` 시킨다.**
계약 주석이 그 이유를 남겨 두었다 —
*"'우리 또래분들' 이 한 번 좋은 치환어로 문서에 적혔다가 폐기됐다(PR #100). 사람은 같은 실수를 반복한다."*

| 후보 | 상태 |
|---|---|
| `소란님들` · `소란소란님들` · `소란소란님` · `소란님` | 🟢 `SORANSORAN_REGISTER_TERMS` 4개에 있음 |
| `우리 소란님들` | 🟡 register term 에 없음 — 아래 🔴 참조 |
| `여기 계신 분들` | 🟢 **`GENERIC_COMMUNITY_TERMS` 에 명시**된 일반 커뮤니티 표현 |
| `저만 이런가요?` · `혹시 저 같은 분 계세요?` | 🟢 `저만 그런가요` · `혹시 저만` 계열의 변형 |
| `언니들` | 🟢 금지어 아님 — 단 ⚠️ 연령 관계 전제 (아래) |
| 무호칭 | 🟢 검사 대상 문자열이 없다 — 어떤 목록에도 걸리지 않는다 |
| 🔴 `우리 또래분들` | **금지어 15개에 포함. 현행 코드에서는 쓸 수 없다** |

#### 🔴 `우리 소란님들` — "unknown 이라 차단된다" 는 부정확하다

```
텍스트 스캔  computeCommunityRegister()
  '우리 소란님들' 안의 '소란님들' 이 잡힌다   →  🟢 register 로 인식 · 통과

후보 검증   validateAddressCandidates()
  배열 정확 일치 검사                        →  🟡 unknown

🔴 그리고 validateAddressCandidates() 는 현재 **런타임 차단 경로에 없다.**
   호출부는 scripts/voice-m3-check.mts (fixture · 자가검사) 뿐이다.
   실제 저장 전 차단은 voice-m3-run.mts 의 M3_FORBIDDEN_ADDRESS_TERMS.filter(...) 가 한다.
```

정확한 표현은 이렇다 — **후보 검증 관점에서는 `unknown` 이고, 그 판정이 오늘 차단으로 이어지지는 않는다.**
두 경로가 같은 표현을 다르게 본다는 점이 ⑨ 구현의 결정값이다(§14-⑭).

> **권고 — ⑨ 는 텍스트 스캔 중심으로 만든다.**
> `computeCommunityRegister()` 를 확장해 생성물 전문을 훑는다.
> `validateAddressCandidates()` 는 **후보 목록 검증용 별도 도구**로 두고, ⑨ 의 차단 경로에 넣지 않는다.

#### ⚠️ `언니들` 은 Persona Identity 와 맞아야 한다

`언니들` 은 화자가 청자보다 어리다는 **연령 관계를 전제**한다.
60대 초반 페르소나가 40대 중반 독자에게 쓰면 어긋난다.
**성향만이 아니라 Identity 의 연령 설정과 묶어서 배정**한다.

#### 🟢 `GENERIC_COMMUNITY_TERMS` — 살리는 갈래

`여기 계신 분들` 은 "상수에 없어서 애매한" 표현이 아니다. **네 번째 목록에 명시돼 있다.**

```
실측 — scripts/lib/voice-style-signals.mts : GENERIC_COMMUNITY_TERMS (11개)
  여기 계신 분들 · 여기계신 분들 · 혹시 저만 · 저만 그런가요 · 다들 어떠세요
  다들 · 혹시 · 조언 부탁 · 경험 있으신 · 어떻게 하세요 · 있으세요

주석: "일반 커뮤니티 표현 — 🟢 학습하고 살린다. 출처를 드러내지 않는다"
```

**이 갈래는 지우는 대상이 아니라 살리는 대상이다.** 출처를 드러내지 않으면서 커뮤니티의 온기를 만든다.

#### 호칭 상수는 2갈래가 아니라 **4갈래**다

| 갈래 | 방향 | 개수 | 관문 |
|---|---|---|---|
| `SOURCE_SPECIFIC_TERMS` | 🔴 치환 대상 — 출처 흔적 | 8 | ⑨ |
| `SORANSORAN_REGISTER_TERMS` | ✅ 치환 결과 — 허용 기준선 | 4 | ⑤ ⑨ |
| `TARGET_DESCRIPTOR_TERMS` | 🔴 생성 금지 — 타겟 설명어 | 15 | ⑤ |
| `BRAND_BANNED_WORDS` | 🔴 생성 금지 — 브랜드 금지어 | 4 | ⑤ |
| `GENERIC_COMMUNITY_TERMS` | 🟢 살린다 — 일반 표현 | 11 | (해당 없음) |

🔴 **어디에도 "이 목록에 없으면 금지" 라는 규칙은 없다.**
금지 대상은 **설명어와 브랜드 금지어**이지 부름말 전반이 아니다.
`TARGET_DESCRIPTOR_TERMS` 주석이 이유를 말한다 —
*"커뮤니티 안에서 사람들은 서로를 설명하지 않는다. 그냥 부른다."*

### 🟢 최종 호칭 정책 권고

| 표현 | 판단 |
|---|---|
| `소란소란님들` · `소란소란님` · `소란님들` · `소란님` | 🟢 **허용** |
| `언니들` · `여기 계신 분들` · `저만 이런가요?` · `혹시 저 같은 분 계세요?` · 무호칭 | 🟢 **페르소나 성향 · 연령에 맞게 허용** |
| `우리 소란님들` | 🟡 **register term 추가 보류** — 실익 대비 상수 변경 비용이 크다 |
| 🔴 `우리 또래분들` · `우리 또래` · `같은 세대 분들` | **금지 유지** |
| 🔴 `40대 / 50대 / 60대 여성분들` · `중년 여성` | **금지 유지** |
| 🔴 `시니어` · `어르신` · `노인` · `실버` | **금지 유지** — `BRAND_BANNED_WORDS` 로 페르소나 생성물에서 차단 |

```
🟢 댓글은 무호칭을 기본값으로 한다
   실제 커뮤니티 댓글은 호칭 없이 바로 공감으로 시작한다
   호칭을 덜 쓰면 ⑨ 가 잡을 일 자체가 줄고 ⑧ 반복 위험도 사라진다

🔴 외부 호칭을 무조건 '소란소란님들' 로 일괄 치환하지 않는다
🔴 한 페르소나에 호칭을 1개만 주지 않는다 — 성향당 2~3개를 주고 상황·mood 로 고른다
🔴 같은 호칭 반복은 ⑧ Voice Fingerprint 가 잡는다
```

**`우리 또래분들` 을 푸는 결정은 §14-⑩ 으로 남긴다.** 다만 이 문서의 권고는 **금지 유지**다 —
`여기 계신 분들` · `언니들` · 무호칭이 그 자리를 이미 채우므로 **푸는 실익이 없다.**

## §4 위기 신호 별도 경로

### 🔴 이것은 Gate 관문이 아니라 **선행 차단**이다

```
자해 · 자살 · 극단 선택 · 학대 · 폭력
긴급 의료 위기 · 긴급 법률 위기 · 긴급 재무 위기
```

### 흐름

```
① Trend Ingestion / ③ Persona Matching 단계에서 감지
        ↓
🔴 ④ Draft Generation 을 시작하지 않는다
        ↓
crisis_hold 상태로 기록
        ↓
운영자 알림 → 필요 시 사람이 수동 대응
```

**페르소나는 상담자처럼 답하지 않는다.**
봇이 위로하려다 상황을 악화시키는 것이 최악이다. **사람에게 넘긴다.**

### 규칙

```
🔴 위기 신호 글에 페르소나 댓글 생성 금지
🔴 crisis_hold 는 재생성하지 않는다 (§8)
🔴 persona 를 바꿔도 생성하지 않는다 — source 자체가 대상이 아니다
```

**운영자 알림 경로는 아직 미정으로 남긴다**(§14).

## §5 조언 제한 정책

### 🔴 금지

```
진단                        "그거 갑상선일 수 있어요"
약 · 용량                   "○○ 하루 두 알 드세요"
병원 · 의사 특정 추천        "○○병원 △△ 선생님이 잘 봐요"
법적 판단                   "그건 명백히 위자료 대상이에요"
투자 · 대출 · 보험 단정      "지금 사두면 올라요"
구체 금액 지시               "500만 원 정도면 충분해요"
가족관계 단정               "그건 이혼 사유예요"
```

### 🟢 허용

```
자기 경험 공유              "저도 그맘때 그랬어요"
감정 공감                   "얼마나 답답하셨을까요"
일반 권유                   "병원에 한번 가보시는 게 좋겠어요"
                           "전문가한테 물어보시는 게 나을 것 같아요"
조심스러운 표현              "제 경우엔 그랬는데 사람마다 다르더라고요"
```

**경계는 "단정" 이다.** 경험을 나누는 것과 판단을 내려주는 것은 다르다.

### 🔴 1인칭 경험 진술의 경계

공개 정책은 **외부 비공개 / 내부 어드민 명확 구분**으로 확정됐다
([Strategy §10](2026-08-29-persona-network-strategy.md) · [Architecture §15](2026-08-30-persona-architecture-design.md)).
🔴 **그래서 이 경계가 더 엄격해진다.** 고객은 상대가 페르소나임을 모른 채 읽고,
댓글 본문은 **1인칭 경험담**으로 나간다.

> **위험한 것은 페르소나를 표시하느냐 마느냐가 아니라,
> 페르소나가 실제 사람처럼 검증 가능한 경험을 말해서 읽는 사람이 그걸 근거로 결정하는 것이다.**

| 단계 | 예 | 판단 |
|---|---|---|
| **감정 공감** | "저도 속상했어요" · "읽는데 마음이 무거웠어요" | 🟢 **허용** — 경험 주장이 아니라 정서 표현 |
| **일반 경험 공감** | "저도 그맘때 그랬어요" · "제 경우엔 그랬는데 사람마다 다르더라고요" | 🟡 **제한적 허용** — 구체 사실과 결합하면 금지 |
| **구체 사실 결합** | 병원 · 약 · 치료 · 날짜 · 금액 · 기관 · 수치가 붙는 순간 | 🔴 **금지** |
| **결과 진술** | "저는 그거 먹고 나았어요" | 🔴 **금지** — 사실상 조언 |
| **가족 경유 진술** | "우리 딸도 그 병원 갔어요" | 🔴 **금지** — 존재하지 않는 가족의 검증 가능한 사실 |
| **전문 판단** | 의료 · 법률 · 재무 판단 | 🔴 **금지** — 위 §5 금지와 동일 |

```
🟢 안전한 형태   감정 + 일반화 + 사람마다 다름
   "저도 그맘때 힘들었어요. 사람마다 다르다니까 한번 여쭤보시면 좋겠어요"

🔴 위험한 형태   1인칭 + 구체 사실 + 결과
   "저도 작년에 그래서 ○○ 먹었는데 두 달 만에 괜찮아졌어요"
```

#### 🔴 이것 때문에 10번째 관문을 만들지 않는다

새 관문을 세우지 않고 **기존 관문과 정책 안에 넣는다. 관문 수는 9 를 유지한다.**

| 넣는 곳 | 무엇을 맡는가 |
|---|---|
| **③ 식별 디테일** | 병원 · 약 · 날짜 · 금액 · 기관의 **결합** 자체 |
| **⑤ 브랜드 금칙어** | 브랜드가 쓰지 않는 말 (별개 축이지만 같은 판정부에서 함께 본다) |
| **⑦ Persona Consistency** | 존재하지 않는 가족의 검증 가능한 사실을 판단 근거로 쓰는 것 |
| **§5 조언 제한** | 결과 진술 · 전문 판단 — 이 절이 정본이다 |

**따로 세면 관문 수만 늘고, 실패 로그에서 원인이 네 곳으로 갈라진다.**
⑧ 이 "AI 말투" 를 하위 축으로 흡수한 것과 같은 판단이다.

## §6 Originality 의 정확한 의미

### 🔴 원문 0% 유사성이 목표가 아니다

원문을 한 단어도 못 쓰게 하면 *"시어머니"* 도 *"갱년기"* 도 쓸 수 없다.
그러면 소란소란 글이 될 수 없다.

| 허용 🟢 | 금지 🔴 |
|---|---|
| 주제 (간병 · 가족갈등 · 몸 · 돈 · 외로움) | 긴 문장 복사 |
| 흔한 상황 | 고유 표현 · 특이 조어 |
| 감정 흐름 | 식별 디테일 |
| 일반 표현 · 관용구 | 원문 문장 순서 과복제 |
| 댓글 **반응 구조** | **원댓글 문장 복사** |
| 문단 호흡 · 줄바꿈 습관 | 닉네임 재사용 |

### "오리지널리티 강화" 의 정의

> **소스 글을 소란소란 페르소나의 삶과 기억으로 재맥락화하는 것.**

같은 주제를 다루되, **그 페르소나가 겪었다면 어땠을까**로 다시 쓰는 것이다.
50대 초반 간병 중인 페르소나와 40대 후반 재취업 준비 중인 페르소나는
같은 소재를 완전히 다르게 쓴다. 그 차이가 오리지널리티다.

## §7 Gate 결과 상태

| 상태 | 의미 | 다음 액션 |
|---|---|---|
| **`pass`** | 9관문 전부 통과 | → 1단계 **승인 대기열** · 2~3단계 **발행 가능 후보** |
| **`review`** | 위험은 있으나 판단이 필요 | → 대기열 + **위험 항목 표시**. 운영자가 확인 |
| **`regenerate`** | 명백한 실패. 다시 만들면 해결 가능 | → 재생성 (최대 3회) |
| **`reject`** | 재생성으로 해결 불가 | → **후보 폐기** · 사유 기록 |
| **`crisis_hold`** | 위기 신호 | → 🔴 **페르소나 응답 금지** · 운영자 알림 |

### 관문 → 상태 매핑

| 관문 | 실패 시 기본 상태 |
|---|---|
| ① 20자 연속 유출 | `regenerate` |
| ② 고유 표현 / 특이 조어 복제 | 희귀도 높음 `regenerate` · 중간 `review` |
| ③ 식별 디테일 | 2개 `review` · 3개+ `regenerate` |
| ④ 원문 문장 순서 / 구조 과복제 | 3개 `review` · 4개+ `regenerate` |
| ⑤ 금지 호칭 / 브랜드 금칙어 | `regenerate` |
| ⑥ 닉네임 / author 재사용 | `regenerate` |
| ⑦ Persona Consistency | `regenerate` |
| ⑧ Voice Fingerprint / 반복 패턴 | `regenerate` (다른 variation) · 구조화 나열/마크다운 말투 포함 |
| ⑨ Source Community Marker | `regenerate` · 애매하면 `review` · 🔴 source 가 카페 운영/공지/광고면 `reject` |
| 위기 신호 | 🔴 `crisis_hold` |

🔴 **`pass` 도 발행이 아니다.** 대기열로 갈 자격을 얻은 것뿐이다.

## §8 재생성 정책

```
최대 3회
같은 실패가 반복되면 → reject (폐기)
```

### 실패 유형별 처리

| 실패 | 처리 |
|---|---|
| **source leak** (①②) | 재작성 — 같은 persona, prompt 에 회피 지시 강화 |
| **식별 디테일** (③) | 일반화 지시 추가 후 재작성 |
| **문장 순서** (④) | 전개 재구성 지시 |
| **금지 호칭** (⑤) · **닉네임** (⑥) | 재작성 |
| **Persona 모순** (⑦) | 🔴 **persona 변경** 또는 prompt 수정 |
| **지문 중복** (⑧) | 🔴 **다른 variation 으로** 재생성 |
| **Source Marker** (⑨) | 🔴 **일괄 치환 금지.** 호칭이 필요한지부터 재검토 후 재작성 |
| **crisis** | 🔴 **재생성 금지** |
| 🔴 **source 자체가 위험** | **persona 를 바꿔도 재생성하지 않는다** |

**마지막 줄이 중요하다.** 소스가 문제인데 페르소나만 바꾸면 같은 문제가 반복된다.
소스 단위로 `reject` 하고 그 소스를 후보에서 뺀다.

## §9 Gate 로그 설계

🔴 **DB schema 변경은 하지 않는다. 후보만 제시한다.**

```
PersonaGenerationLog
  id · personaId · sourceTopicId · targetType(post|comment)
  generationAttempt · model · inputTokens · outputTokens · costUsd
  createdAt

PersonaGateResult
  id · generationLogId
  gateVersion            🔴 기준이 바뀌면 과거 판정을 재해석할 수 있어야 한다

  failedChecks[]         ['LEAK_20', 'IDENT_DETAIL', ...]  코드만

  riskSummary            요약 문자열 (원문 조각 금지)
  regenerationCount
  reviewerDecision       approve | edit | reject | null
  reviewerEdited         boolean
  editDiffHash           🔴 수정 내용은 해시로
  finalAction
  checkedAt
```

### 🔴 저장 금지 / 저장 가능

| 저장 금지 | 저장 가능 |
|---|---|
| 원문 · 댓글 전문 | 해시 |
| LLM raw output 전문 | 길이 |
| 프롬프트 전문 | risk code |

## §10 어드민 자동화 관제실과의 연결

🔴 어드민은 **승인 버튼 화면이 아니라 관제실**이다(전략 §10-2).
1단계에는 승인 대기열이 필요하고, 2~3단계에서는 **자동 발행된 것을 사후 감사하고 즉시 멈추는** 화면이 된다.

Gate 가 어드민에 넘겨야 할 것.

```
생성물          제목 · 본문 (또는 댓글) · 반응 유형
페르소나        누가 · 왜 매칭됐는지 (매칭 점수) · 어떤 variation · 오늘 mood
Gate 결과       9관문 통과/실패 · status · 실패·주의 항목
source          topic summary · 🔴 원문 링크는 운영자만
참조            story refs · voice anchors
재생성          횟수 · 실패 이력
수정            diff (승인 후 기록)
액션            [승인] [수정 후 승인] [폐기]
```

### 🔴 `review` 상태는 다르게 보여준다

`pass` 와 같은 화면에 섞으면 운영자가 위험 항목을 놓친다.
**`review` 는 실패 항목을 상단에 펼친 채로** 보여준다.

## §11 Metrics — Gate 품질을 보는 지표

| 지표 | 의미 | 나쁜 신호 |
|---|---|---|
| **gate fail rate** | 관문 실패 비율 | 너무 높으면 생성 품질 문제, 너무 낮으면 가드가 헐거움 |
| **regenerate rate** | 재생성 비율 | 50% 초과 시 검토 |
| **operator edit rate** | 운영자 수정 비율 | 🔴 30% 초과 시 검토 |
| **reject rate** | 폐기 비율 | |
| **source leak catch count** | ①②가 잡은 건수 | 🔴 **0이면 가드가 작동하는지 의심** |
| **persona contradiction count** | ⑦이 잡은 건수 | 3건 이상 시 persona 정의 재검토 |
| **repeated phrase count** | ⑧이 잡은 건수 | 상승 = AI 티 증가 |
| **source marker catch count** | ⑨가 잡은 건수 | 🔴 sourceSite 별로 본다. 특정 출처에서 높으면 dictionary 보강 |
| **crisis hold count** | 위기 신호 건수 | |
| **published content complaint count** | 발행 후 불만 | 🔴 1건이라도 즉시 중단 |
| **persona comment ratio** | 전체 댓글 중 페르소나 비율 | 🔴 **30% 초과 시 자동 감속** |

🔴 **`source leak catch count` 가 0인 것은 좋은 신호가 아니다.**
VE-M3 에서 terminal skip 33건이 나온 것이 가드가 일한 증거였다.
0이면 가드가 실제로 검사하고 있는지 역검증해야 한다.

## §12 MVP 적용 범위

```
1차   🔴 설계만. 구현하지 않는다
2차   Gate 구현 (생성기 없이 가드만) + fixture + 역검증
3차   후보 생성 — 🔴 post 보다 comment 부터 권장
4차   🔴 어드민 자동화 관제실   승인 대기열 + status · cap · kill switch · 감사 로그
5차   제한 발행                저위험 유형부터 (전략 §4-1 2단계)
6차   전면 자동 발행            (전략 §4-1 3단계)
```

### 🔴 comment 부터 권장하는 이유

| | comment | post |
|---|---|---|
| 정체성 부담 | 낮음 — 반응만 | 🔴 높음 — 사건을 만들어야 함 |
| 실패 시 영향 | 작음 | 큼 |
| Gate 검증 난이도 | 낮음 (짧다) | 높음 |
| 현재 문제와의 적합성 | 🟢 **댓글 0개 글 65%** | 간접 |

**다만 확정이 아니다** — Persona Network 는 글도 만든다. 순서 문제일 뿐이다(§14).

```
🔴 1단계에 한정   모든 후보는 운영자 승인 대기열로 보낸다
🟢 최종 목표      자동 발행 (전략 §4-0 · §4-1)
```

🔴 **"자동 발행 금지" 를 최종 정책으로 읽지 않는다.** 1단계는 자동화 조건을 **측정**하는 구간이다.
