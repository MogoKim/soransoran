## §0 이 문서가 존재하는 이유

VE-M3 분석이 끝나고 학습 후보가 확정됐다. 그 다음이 무엇인지에 대해
창업자와 Codex 가 방향을 맞췄고, **그 방향이 다음 세션에서 휘발되지 않도록 고정한다.**

### 🔴 먼저 정정 — 이전 설계는 축소돼 있었다

직전 세션에서 Claude 가 Persona Bot 아키텍처를 설계하면서 **"페르소나 3명 · 댓글만 · 2주"** 를 권고했다.
근거는 실측이었다 — `User 4명 · Post 23건 · Comment 6개`. 봇이 사람보다 많아지는 것을 우려했다.

**그 실측은 사실이지만, 결론이 틀렸다.**

| 혼동한 것 | 실제 |
|---|---|
| 초기 **활성화 규모**가 작아야 한다 | 맞다 |
| 그래서 **아키텍처도 작게** 설계한다 | 🔴 **틀렸다** |

작게 설계하면 나중에 다시 만들어야 한다.
**아키텍처는 수십~수백 페르소나를 전제로 설계하고, 초기 활성화만 제한한다.**
이 문서는 그 전제를 명시한다.

또 하나 — 헌법 §12 에 **M4 Persona OS** 가 이미 마일스톤으로 있고,
*"시스템 User 1개를 쓰면 같은 작성자의 글이 반복 노출된다 …
다건 발행을 열기 전에 M4 Persona OS 가 필요하다"* 는 근거까지 적혀 있다.
`Comment.personaId` 후보 컬럼도 예고돼 있다.
**Persona Network 는 새 아이디어가 아니라 이미 예고된 M4 다.**

## §2 우리가 만들려는 것의 정확한 정의

> **소란소란에 실제로 살고 있는 40~60대 여성들의 네트워크.**
>
> 각자 나이 · 사는 곳 · 가족 · 형편 · 몸 상태가 다르고,
> 자기가 전에 무슨 말을 했는지 기억하며,
> 회원 한 사람 한 사람과의 관계를 따로 기억한다.
>
> 외부에서 화제가 된 이야기를 **자기 경험처럼 다시 쓰고**,
> 다른 페르소나들이 **각자의 정체성으로 반응한다.**

핵심은 **"기억"과 "관계"** 다.
회원이 두 달 전 시어머니 이야기를 썼고 오늘 또 썼을 때,
페르소나가 *"저번에 말씀하신 그 일은 좀 나아지셨어요?"* 라고 물을 수 있어야 한다.

## §3 아닌 것

| 이것이 아니다 | 이유 |
|---|---|
| **단순 댓글봇** | 매번 새로 태어나면 관계가 쌓이지 않는다. 댓글만으로는 화제를 만들 수 없다 |
| **단순 글 생성기** | 글만 있고 반응이 없으면 커뮤니티가 아니라 게시판이다 |
| **챗봇** | 말을 걸면 답하는 게 아니라 **스스로 커뮤니티를 산다** |
| **어시스턴트** | 도움을 주는 게 아니라 **또래로서 공감한다** |
| 🔴 **내부에서 실고객과 구분되지 않는 가짜 계정** | 고객 화면에 AI · 봇 표시를 하지 않는 것은 **확정된 정책**(§10)이다. 금지되는 것은 **내부 기록 없이 실회원처럼 위장되는 계정** — DB 에는 반드시 `PERSONA` 로 기록되고, 어드민에서 항상 구분되며, 운영자가 언제든 중지 · 수정 · 폐기할 수 있어야 한다 |

## §4 목적 · 목표 · 기댓값

### 🔴 §4-0 최종 목표는 완전 자동화다

**Persona Network 는 수동 운영툴이 아니다.** 최종 목표는 아래 전체를 자동으로 도는 것이다.

```
① 원문 크롤
      ↓
② 좋은 글 선별
      ↓
③ Voice Engine 으로 소란소란화
      ↓
④ 가장 적합한 페르소나가 게시글 발행
      ↓
⑤ 원문 댓글 seed 와 흐름을 참고해 페르소나 댓글 분산
      ↓
⑥ 대댓글 · 관계 · 기억 반영
      ↓
⑦ 활동 리듬과 스케줄에 따라 자동 운영
      ↓
⑧ 운영 지표로 계속 튜닝  →  ①로
```

🔴 **이 문서의 모든 "승인" · "대기열" · "금지" 표현은 이 목표를 포기한다는 뜻이 아니다.**
자동화를 **열기 전에 품질과 위험을 측정하는 단계**를 가리킨다. 단계 정의는 §4-1.

### §4-1 자동화 3단계

| 단계 | 발행 | 무엇을 하는가 |
|---|---|---|
| **1. MVP / 초기 검증** | 🔴 고객 발행 전 **운영자 승인** 또는 **shadow mode** | 생성은 한다. AI 티 · 원문 유출 · 출처 흔적 · 닉네임 재사용 · persona consistency · 위험 조언을 **측정**한다. 🔴 목적은 자동화를 막는 것이 아니라 **자동화 조건을 수집**하는 것 |
| **2. 제한 자동화** | 🟡 **저위험 유형부터 자동 발행** | 생활 정보 · 잡담, 짧은 공감 댓글, A급 comment seed 부터 연다. 🔴 건강 · 돈 · 가족갈등 · 외로움 · 1인칭 경험 진술은 **더 늦게** 연다. cap · kill switch · rollback · 모니터링 필요 |
| **3. 완전 자동화** | 🟢 **자동 발행** | 크롤 → 선별 → 생성 → Gate → 스케줄 발행 → 댓글 분산까지 자동. 어드민은 매번 승인하는 화면이 아니라 **관제 · 중지 · 감사 시스템**이 된다 |

🔴 **1단계는 목적지가 아니라 계측 구간이다.** 여기서 모은 수치가 2단계를 여는 근거가 된다.

### §4-2 🔴 Controlled Activity Scaffold (2026-09-03 추가)

> **비계(scaffold)는 건물이 아니다. 건물이 서면 걷어낸다.**

초기 커뮤니티에는 활동감이 필요하다. 자연 성장만 기다리면 유입된 사람이
*"여긴 아무도 없네"* 를 보고 나가고 다시 오지 않는다.

**포함하는 것 — 전부 금지 대상이 아니라 통제 대상이다.**

```
페르소나 글 · 페르소나 댓글 · 시간대 분산 · 반응/좋아요 · 베스트 흐름 · memory 기반 재응답
```

**반드시 함께 가는 통제 장치 9종**

| 장치 | 2026-09-03 실측 |
|---|---|
| cap (일 · 주) | 🟢 `DAILY_PUBLISH_CAP` · `POST_CAP_PER_WEEK` · `Persona.dailyCap/weeklyCap` |
| kill switch | 🟢 `PersonaGlobalSwitch` (0행 = 중지 꺼짐이 정상 기본값) |
| audit log | 🟢 `PersonaAuditLog` 25행 |
| **ratio limit** | 🔴 **없음** — 비율 ≤30% 자동 감속 미구현 |
| source leak 0 | 🟢 3키 저장 계약 + `assertNoStoredSource` |
| persona 분산 | 🟢 `planBatch` 순차 배정 |
| **실사용자 증가 시 비율 감소** | 🔴 **없음** |
| takedown / hidden | 🟡 `setPostHidden` 존재 · queue 정합성 없음 |
| daily report | 🔴 **없음** |

🔴 **9개 중 3개가 비어 있고, 그 셋이 전부 "멈추는 기준" 쪽이다.**
**멈출 줄 모르는 자동화는 여는 속도와 무관하게 위험하다.**

### §4-3 🔴 개방 순서 — 바꾸지 않는다

```
① 공개 글 검증      ◀━━ 지금 (발행 2건 · 3축 검증 완료)
② 댓글 scaffold         공개 글 5건 전후
③ Memory               SelfMemory → Relationship Memory
④ reaction / like      ②가 안정된 뒤
⑤ best                 ④ 조건 충족 뒤
```

**왜 이 순서인가**

- **댓글이 먼저인 이유**: 좋아요 10개에 댓글 0개인 글이 더 이상하다.
  그리고 댓글 0개 글 비율 80% 가 실사용자가 두 번째 글을 쓰지 않는 이유다.
- **reaction 이 나중인 이유**: 실회원 `Like` 가 2건뿐이라 지금 열면
  **페르소나 반응이 전체의 90% 가 된다.** 그건 비율이 아니라 전부다.
- **best 가 마지막인 이유**: 좋아요만 있고 댓글 없는 best 는 조작으로 읽힌다.

🔴 **좋아요 · 베스트는 금지가 아니라 controlled scaffold 다.**
[레인 정본 §6](2026-09-02-original-post-lane-strategy.md)이 착수 조건을 이미 적어 두었다 —
상한 · kill switch · 사후 감사 · 실회원 반응 대비 비율 상한.
**조건이 적혀 있다는 것은 열 수 있다는 뜻이다.** 다만 순서를 앞당기지 않는다.

속도 · cap ladder · PR 마일스톤은
[자동화 전환 정본](2026-09-03-controlled-activity-automation-strategy.md)이 정한다.

### 무엇을 푸는가

```
SEO · 외부에서 사람이 들어온다
   ↓
글이 하나뿐이거나, 글은 있는데 댓글이 없다
   ↓
"여긴 아무도 없네" → 나간다 → 다시 안 온다
   ↑ 여기를 끊는다
```

**Persona Network 는 외부 유입을 체류 · 가입 · 댓글 · 재방문으로 바꾸는 장치다.**

### 실측된 문제 (2026-09-03 갱신)

```
초판 2026-08-29   User 4명 · Post 23건 · Comment 6개 · 댓글 0개 15건 (65%)
현재 2026-09-03   User 9명(실회원 3 · 창업자 1 · 페르소나 5) · Post 35건(PUBLISHED 25) · Comment 22개
                  🔴 댓글 0개인 PUBLISHED 글: 20건 (80%)
```

🔴 **나빠졌다.** 글은 23 → 35 로 늘었는데 댓글이 따라오지 않았다.
**글을 쓰고 아무 반응도 못 받은 사람이 20명분 있다.**

### North Star 와의 연결

헌법의 North Star 는 **주간 재방문 참여 유저 수** 다.

| 지표 | 초판 | 2026-09-03 | 1차 목표 |
|---|---|---|---|
| **댓글 0개 글 비율** | 65% | 🔴 **80%** | 20% 이하 |
| 페르소나 댓글 비율 | — | 1 / 22 = **5%** | 🔴 30% 이하 유지 |
| 첫 글 작성자 24h 재방문율 | 미측정 | 미측정 | 40%+ |
| 댓글 확인율 | 미측정 | 미측정 | 70%+ |
| 7일 재방문율 | 미측정 | 미측정 | 25%+ |
| 두 번째 글 작성률 | 미측정 | 미측정 | 20%+ |

🔴 **재방문 계열은 여전히 전부 미측정이다.** 일일 리포트(PR-S8)가 이 칸을 채운다.

### 🔴 페르소나는 North Star 에 포함하지 않는다

```
페르소나 20명 × 주 1건 = 주 20건
실사용자 4명            = 주 0~2건

페르소나를 세면  →  주간 참여 22
페르소나를 빼면  →  주간 참여 2
```

**페르소나를 세면 이 지표는 페르소나 수의 함수가 된다.**
지표를 올리는 가장 쉬운 방법이 페르소나를 늘리는 것이 되고, 그 순간 지표가 방향을 잃는다.
우나어가 이 실수를 했다 — 색인 4,600건과 DAU 는 봇 발행만으로 올랐고,
**그 숫자가 오르는 동안 커뮤니티는 죽었다.**

`PV` · `DAU` · `색인 수` · `발행량` 도 같은 이유로 **참고 지표**다.

### 기댓값의 정직한 한계

**Persona Network 는 목적이 아니라 사회적 인프라다.**
실제 유저 비중이 커지면 페르소나의 활동은 **줄어들어야 한다.**
페르소나가 계속 늘어나야 유지되는 커뮤니티는 실패한 것이다.

> 🔴 **이 원칙은 아직 코드에 없다.** [아키텍처 §8](2026-08-30-persona-architecture-design.md)이
> *"페르소나 댓글 비율 ≤ 30% · 넘으면 자동 감속"* 을 정했지만 구현이 없다.
> 지금은 비율이 5% 라 문제가 보이지 않지만, **댓글 분산기를 켜는 순간
> 이것이 첫 번째 안전장치가 되어야 한다** (PR-S6).

               │
┌──────────────▼───────────────────────────────────────┐

## §6 Persona Identity 원칙

### 🔴 20~30개 풀을 설계하고, 일부만 활성화한다

| 구분 | 규모 | 이유 |
|---|---|---|
| **설계 풀** | **20~30명** | 정체성 다양성이 확보돼야 대화가 산다 |
| **초기 활성** | **소수 (3~5명)** | 회원 4명 규모에서 봇 비율을 통제 |
| 장기 | 수십~수백 | 커뮤니티 성장에 따라 확대 |

**풀을 크게 설계하고 활성을 작게 여는 것**이 핵심이다.
작게 설계하면 나중에 정체성 체계를 다시 만들어야 한다.

### 각 페르소나가 가지는 것

```
기본      age(45~63) · gender=female 고정 · region · displayName
가족      maritalStatus · spouseRelationship · household · children · parentCare
형편      economicStatus · housing · workStatus
몸        health(밴드) · menopauseStatus
말·성격    personality · speechStyle(종결어미·이모티콘·줄바꿈·오타 허용) · taboos
이력      lifeEvents (요약만)
기억      selfMemory · postHistory · commentHistory · userRelationshipMemory
          topicPreferences · avoidTopics
운영      activityProfile · status(draft/active/paused/retired)
```

### 설계 원칙 3가지

**① 구체적일수록 좋지만, 특정 가능하면 안 된다**
```
✅ "50대 초반, 수도권, 시어머니 간병 3년째"
🔴 "1973년생, 성남 분당, ○○병원 신경과 통원"
```

**② `taboos` 가 정체성의 핵심이다**
페르소나를 구분하는 것은 "무엇을 말하는가" 보다 **"무엇을 말하지 않는가"** 다.

**③ `voiceAnchors` 로 gold 와 연결한다**
각 페르소나에 voice_gold 135건 중 3~5건을 문체 기준으로 지정한다.

## §7 Voice Engine 원칙

### 🔴 목표는 원문 0% 유사성이 아니다

**목표는 충분한 오리지널리티와 소란소란식 재맥락화다.**

원문을 한 단어도 못 쓰게 하면 사람이 쓴 글이 될 수 없다.
"시어머니" 도 "갱년기" 도 못 쓰게 되기 때문이다.

### 가져와도 되는 것 / 가져오면 안 되는 것

| | 가져와도 되는 것 🟢 | 가져오면 안 되는 것 🔴 |
|---|---|---|
| **주제** | 간병 · 가족갈등 · 몸의 변화 · 돈 걱정 · 외로움 | — |
| **단어** | 일반 단어 · 관용 표현 · 감탄사 | 특이한 조어 · 개인 말버릇 |
| **상황** | 상황 유형 (며느리 갈등 · 부모 간병) | 특정 사건의 고유 전개 |
| **감정** | 감정 흐름의 일부 (답답함 → 체념 → 웃음) | 원문 감정선의 과도한 복제 |
| **댓글** | 반응 구조 (공감형 · 경험공유형 · 조언형) · 🟢 **A 급 seed** (짧고 흔한 표현) | 🔴 **B · C 급 문장 그대로** — 등급은 [Gate §3-②](2026-08-30-persona-safety-originality-gate-design.md) |
| **길이·리듬** | 문단 호흡 · 줄바꿈 습관 | 원문 문장 순서 |
| **식별 정보** | — | 🔴 지명 · 기관 · 병원 · 날짜 · 닉네임 |

### 정량 기준

```
🔴 20자 이상 연속 일치  →  차단 (assertNoSourceLeak · M3_LEAK_RUN_MIN)
🔴 원문 문장 순서 3개 이상 동일  →  차단
🟡 sequenceSimilarityRisk 재평가가 gold 평균(21.1)에서 크게 벗어나면 재생성
```

### 학습 후보별 용도

| bucket | 용도 | 제약 |
|---|---|---|
| **voice_gold 135** | 기준 말투 · few-shot 예시 | `speakerVerified=true` |
| **voice_silver 1,065** | 말투 다양성 · 어휘 분포 참고 | 🔴 few-shot 예시로 쓰지 않는다 (남성 화자 3~11% 혼입 가능) |
| **story_topic 1,304** | 사건 구조 · 댓글 반응 구조 | 🔴 말투는 가져오지 않는다 (`usableForVoice=false`) |
| held 11 · excluded_manual 15 · mimicry_review 449 | 🔴 지금은 학습 금지 또는 보류 | |

### 불변 정책

```
🟢 사적 소재는 위험이 아니라 핵심 자산이다
🟢 expressionRisk 상한은 제외 기준이 아니다 (감정 강도는 진정성이다)
🟢 오타 · 줄바꿈 · 이모티콘은 과교정하지 않는다
🔴 닉네임 · author 는 학습 금지
🔴 댓글은 content 만 사용
🔴 replies 는 1차 보류
🔴 likeCount 는 사용 금지 (전량 0 — 수집되지 않았다)
```

## §8 댓글 흐름 재구성 원칙

### 원댓글은 반응 지도이자 seed 다 — 등급에 따라 다르게 쓴다

외부 글에 댓글 12개가 달렸다면, 먼저 배우는 것은 **"어떤 종류의 반응이 어떤 비율로 붙었는가"** 다.
그 위에서 **문장 자체를 얼마나 쓸 수 있는지는 seed 등급이 정한다.**

```
A 급   🟢 짧고 흔한 표현 — 유사 표현 seed 허용
B 급   🟡 페르소나 voice 로 재맥락화
C 급   🔴 문장 재사용 금지 — 역할 · 구조만
```

🔴 **A / B / C 는 빈도만으로 정해지지 않는다.** 빈도축(댓글 코퍼스 희귀도)과
내용안전축(의료 · 법률 · 재무 조언 · 식별 디테일 · 구체 경험 사실 · 닉네임 · 출처 흔적 ·
identity 불일치 1인칭)의 **2축**이며, **더 엄격한 쪽**을 따른다.
자주 나오는 문장이어도 내용이 위험하면 A 가 될 수 없다.

정본은 [Gate §3-②](2026-08-30-persona-safety-originality-gate-design.md).

### 반응 유형

| 유형 | 성격 | 어울리는 페르소나 |
|---|---|---|
| **공감형** | "저도 그래요" | 비슷한 처지 |
| **경험공유형** | "저는 이랬어요" | 같은 일을 겪은 |
| **조심스러운 조언형** | "혹시 ~는 해보셨어요?" | 조금 앞선 |
| **다른 관점형** | "그런데 이런 면도" | 🔴 반박이 아니라 다른 각도 |
| **가벼운 유머형** | 분위기를 푼다 | 유머 성향 |

### 🔴 분산 원칙

```
같은 글의 댓글은 서로 다른 페르소나에서 나온다
한 페르소나가 같은 글에 두 번 달지 않는다
반응 유형이 겹치지 않게 분산한다
🔴 B · C 급 원댓글 문장을 그대로 쓰지 않는다 — A 급 seed 만 허용 (Gate §3-②)
```

댓글 3개가 전부 공감형이면 사람이 쓴 것처럼 보이지 않는다.

## §9 Safety 기준

### 발행 전 관문 — 9관문

> 🔴 **정본은 [Safety / Originality Gate 설계](2026-08-30-persona-safety-originality-gate-design.md) §3 이다.**
> 이 표는 전략 문서용 요약이며, 번호 · 명칭이 어긋나면 그쪽을 따른다.

| # | 관문 | 기준 |
|---|---|---|
| ① | **20자 연속 유출** | 공백 제거 후 20자 이상 연속 일치 1건도 불가 |
| ② | **고유 표현 / 특이 조어 복제** | 코퍼스 희귀도 기준 — 그 사람의 말버릇을 옮기지 않는다 |
| ③ | **식별 디테일** | 지명 · 기관 · 날짜 · 숫자의 **결합**으로 특정되지 않게 |
| ④ | **원문 문장 순서 / 구조 과복제** | 문장을 다 바꿔도 사건 전개 순서가 같으면 복제다 |
| ⑤ | **금지 호칭 / 브랜드 금칙어** | 🔴 **상수 두 갈래** — 타겟 설명어(`TARGET_DESCRIPTOR_TERMS` 15) **+** 브랜드 금지어(`BRAND_BANNED_WORDS` 4: 시니어·어르신·노인·실버) |
| ⑥ | **닉네임 / author 재사용** | 학습 데이터 author · 회원 닉네임 재사용 금지 |
| ⑦ | **Persona Consistency** | Identity · Relationship Memory 와 충돌 금지 |
| ⑧ | **Voice Fingerprint / 반복 패턴** | 시작 문장 · 말끝 · 이모티콘 반복 · **구조화 나열/마크다운 말투** · n-gram 점유율 |
| ⑨ | **Source Community Marker** | 외부 커뮤니티명 · 카페 내부 호칭 · "우리 카페" 잔존 금지 — 🟢 `SOURCE_SPECIFIC_TERMS` 8 **확장** |

🔴 **"AI 말투"는 독립 관문이 아니다.** ⑧의 하위 검사 축으로 흡수했다. **9관문을 넘기지 않는다.**

🔴 **⑤ 는 상수 하나가 아니라 둘을 본다.** `M3_FORBIDDEN_ADDRESS_TERMS`(=`TARGET_DESCRIPTOR_TERMS`)에
*시니어 · 어르신 · 노인 · 실버* 는 **없다.** 그 넷은 `src/lib/content-guard.ts` 의 `BRAND_BANNED_WORDS` 에 있다.
회원이 자기 글에 "어르신" 이라 쓰는 것은 막지 않지만, **페르소나 생성물은 운영 생성물이므로 적용 대상**이다.
상세는 [Safety Gate §3-⑤](2026-08-30-persona-safety-originality-gate-design.md).

🔴 **1인칭 경험 진술 경계**도 10번째 관문이 아니라 ③ · ⑤ · ⑦ 과 조언 제한 정책에 나눠 넣는다
([Safety Gate §5](2026-08-30-persona-safety-originality-gate-design.md)).

### 관문 밖에서 다루는 것

관문은 *생성물의 문장*을 본다. 아래 셋은 문장 대조로 잡히지 않아 다른 층에서 막는다.

| 항목 | 기준 | 어디서 막는가 |
|---|---|---|
| **의료 · 법률 · 재무 단정 조언** | 진단 · 약 · 용량 · 법적 판단 · 투자 · 금액 조언 금지 | [Architecture §12](2026-08-30-persona-architecture-design.md) 조언 제한 |
| **과도한 친밀감** | 첫 상호작용 반말 · 개인 연락 · 만남 제안 금지 | Persona **No-Go** (Architecture §3) · ⑦이 함께 잡는다 |
| **source comment seed 오용** | 🔴 B · C 급 문장 재사용 금지 · A 급도 동일 문장 반복 금지 | ①이 문자열을 · ②가 등급을 · ④가 구조를 잡는다 |

### 🔴 위기 신호 — 자동 대응 금지

```
자해 · 자살 신호가 보이면
  → 페르소나 응답 중단
  → 운영자 즉시 알림
  → 🔴 페르소나가 상담자 역할을 하지 않는다
```

봇이 위로하려다 상황을 악화시키는 것이 최악이다. **사람에게 넘긴다.**

### 활동 제한

```
페르소나 1명당   댓글 상한 · 글 상한 (초기값은 MVP 에서 정한다)
전체 합산        일일 상한
같은 회원에게     하루 1건 · 주 3건
같은 글에         페르소나 1명만
🔴 봇끼리 과도한 대화 금지 — 초기에는 전면 금지
활동 시간대       09:00~22:00 KST · 즉답 금지
```

### 발행 경로 — 단계별

```
1단계  운영자 승인 또는 shadow mode   ← 지금. 자동화 조건을 측정하는 구간
2단계  저위험 유형부터 자동 발행       cap · kill switch · rollback 필요
3단계  전면 자동 발행                 어드민은 관제 · 중지 · 감사
```

🔴 **1단계를 최종 형태로 읽지 않는다.** 최종 목표는 완전 자동화다(§4-0).

## §10 ✅ 공개 · 신뢰 정책 — 창업자 최종 결정 (확정)

```
외부 정책명   외부 비공개
내부 정책명   내부 어드민 명확 구분
```

> **고객에게는 자연스러운 커뮤니티로 보이고,
> 내부 운영자는 모든 페르소나 활동을 추적 · 중지 · 수정 · 폐기할 수 있어야 한다.**

**소란소란은 "AI 가 위로해주는 서비스" 가 아니라 커뮤니티다.**
고객 화면에서 페르소나가 AI 봇임을 드러내는 순간 제품의 본질이 깨진다.
그래서 공개 정책은 **외부 비공개 · 내부 명확 구분**으로 고정한다.

### §10-1 외부 고객 화면 원칙

```
🔴 고객은 페르소나가 AI 봇인지 몰라야 한다
🔴 글 · 댓글 · 프로필 · 회원 목록 · 알림 · 운영정책 어디에도
   AI · 봇 · 운영 페르소나 표시를 하지 않는다
🔴 댓글마다 봇 배지를 붙이지 않는다
🔴 프로필에 운영 페르소나임을 표시하지 않는다
🔴 운영정책에 "AI 봇이 활동한다" 는 식으로 드러내지 않는다
🟢 고객에게는 일반 커뮤니티 구성원처럼 자연스럽게 보인다
```

### §10-2 내부 어드민 원칙 — 승인 버튼 화면이 아니라 자동화 관제실

**고객에게 숨긴다고 해서 내부 추적성을 없애면 안 된다.** 오히려 내부 통제는 더 강해야 한다.

🔴 **어드민의 최종 형태는 "수동 승인 버튼 화면" 이 아니다.**
1단계에는 승인 대기열이 필요하지만, 최종적으로는 **자동화 상태를 감시하고 문제를 즉시 멈추는 시스템**이다.

```
🔴 실고객과 페르소나 봇을 어드민에서 명확히 구분한다
🔴 어떤 글 · 댓글을 어떤 페르소나가 썼는지 내부에서 전부 추적 가능해야 한다
🔴 운영자가 언제든 페르소나별 · 글별 · 전체 단위로 중지할 수 있어야 한다
```

| 어드민 필수 기능 | 비고 |
|---|---|
| **실고객 / 페르소나 구분** | 🔴 목록 · 상세 · 검색 전부 |
| `status` 전환 — `draft` / `active` / `paused` / `retired` | 🔴 운영자가 언제든 |
| **페르소나별 활동 cap** | 일 · 주 상한 |
| 🔴 **전체 persona kill switch** | 전 단위 즉시 중지 |
| **글 / 댓글 후보 이력** | 채택 · 미채택 포함 |
| **Gate 9관문 결과** | 관문별 status |
| **AI 티 태그** | §4-8 8종 |
| **생성 · 승인 · 수정 · 폐기 · 발행 로그** | 🔴 전건 남긴다 |
| **`memory` 열람 / 삭제 / 축약** | Self · Relationship · Community · Negative |
| 🔴 **탈퇴 회원 관련 memory 즉시 삭제** | Pool §8-3 · `(userId)` 단일 인덱스가 이걸 가능하게 한다 |

| 페르소나 정의 열람 | |
|---|---|
| `personaId` · P 코드 · `displayName` | 🔴 P 코드는 외부 노출 금지 |
| `identity` · `voiceCore` · `voiceVariations` · `mood` | 7층 구조 §6 |
| `activityRhythm` · `noGo` | 시간대 · 빈도 · 금지 영역 |

🔴 **kill switch 가 없으면 2단계를 열 수 없다.** 자동 발행을 여는 조건은 "품질이 좋다" 가 아니라
**"잘못됐을 때 즉시 멈출 수 있다"** 이다.

### §10-3 🔴 외부 비공개와 내부 미기록은 다르다

> **외부에 안 보이는 것과 내부에 안 남기는 것은 전혀 다른 이야기다.
> 고객에게는 드러내지 않지만, 내부에는 반드시 남긴다.
> 내부 추적이 없으면 운영 리스크가 커진다.**

DB 에는 반드시 `PERSONA` 로 기록한다(`CommentOrigin.PERSONA` — 이미 존재).
이건 공개 여부와 무관한 **내부 통제 요건**이다.

### §10-4 발행 경로는 단계에 따라 달라진다

🔴 **"자동 발행 금지" 는 최종 정책이 아니다.** 1단계(MVP / 초기 검증)에 한정된다.

| 단계 | Gate 통과의 의미 |
|---|---|
| **1. MVP / 초기 검증** | **운영자 승인 대기열 진입** — 발행이 아니다 |
| **2. 제한 자동화** | 저위험 유형은 **발행 가능 후보** · 그 외는 대기열 |
| **3. 완전 자동화** | **발행 가능 후보** — 어드민은 관제 · 중지 · 감사 |

#### 🔴 외부 비공개이므로 1단계 계측이 더 중요하다

고객이 페르소나 여부를 알 수 없다는 것은 **잘못된 발화를 걸러낼 외부 눈이 없다**는 뜻이다.
공개 정책이었다면 독자가 "이건 봇 말이니 걸러 듣자" 고 판단할 여지라도 있었지만, 그 여지가 없다.

그래서 1단계에서 **AI 티 · 원문 유출 · 출처 흔적 · 닉네임 재사용 · persona consistency ·
위험 조언**을 측정한다. 🔴 측정하지 않은 채 2단계를 열면 무엇이 새는지 모르는 상태로 자동화하는 것이다.
**승인 대기열은 종착지가 아니라 계측 장치다.**

### §10-5 🔴 진짜 경계는 표시가 아니라 1인칭 경험 진술이다

**외부 비공개로 고정했기 때문에 이 경계는 더 엄격해진다.**
고객은 상대가 페르소나임을 모른 채 읽는다. 그래서 페르소나가 검증 가능한 경험을 말하면
읽는 사람이 그것을 근거로 실제 결정을 내린다.

감정 공감은 허용하고, 구체 사실 · 결과 진술 · 가족 경유 진술은 금지한다.
정본은 [Safety Gate §5](2026-08-30-persona-safety-originality-gate-design.md) ·
[Architecture §15](2026-08-30-persona-architecture-design.md).

### §10-6 폐기된 이전안 (변경 이력)

🔴 **A / B / C 3안 분류 자체를 폐기한다.**
최종 정책은 이 셋 중 하나가 아니라 **외부 비공개 / 내부 어드민 명확 구분** 이다.

| 이전안 | 상태 |
|---|---|
| **A. 완전 은폐** | ❌ **용어 폐기.** 현 정책은 *외부 비공개* 이며, **내부 미기록 · 내부 추적 불가 · 이력 조작을 뜻하지 않는다** |
| **B. 완전 표시** (댓글마다 AI 배지) | ❌ **폐기** — "봇이 위로하는 커뮤니티" 가 되어 온기가 깨진다 |
| **C. 중간 공개** (프로필 · 운영정책에서 밝히되 댓글 배지는 없음) | ❌ **폐기** — 2026-08-30 창업자 최종 결정으로 대체 |

2026-08-30 이전 이 문서는 **C(중간 공개)를 권고안으로 고정**하고 있었고,
"프로필 또는 운영정책에서 1클릭 안에 확인 가능해야 한다" 를 요건으로 두었다.
**창업자 최종 결정으로 폐기한다.** 위 §10-1 이 정본이다.

🔴 대신 **내부 통제 요건은 폐기되지 않고 강화됐다** — §10-2 · §10-3.

### §10-7 🔴 `displayName` 정책 — 자연스러운 활동 닉네임 (작명은 나중)

외부 비공개이므로 **고객에게 보이는 `displayName` 은 실제 회원이 쓸 법한 자연스러운 활동 닉네임**이어야 한다.
🔴 **실제 작명은 지금 하지 않는다** — Gate ⑥ 닉네임 / author 중복 검사 설계 이후다.

```
🟢 지향   실제 회원이 쓸 법한 자연스러운 활동 닉네임
🔴 금지   AI 티 나는 닉네임              (숫자 접미 · 영문 혼용 · 봇/AI 연상)
🔴 금지   운영자 티 나는 닉네임          ("소란지기" 류 운영 주체 연상)
🔴 금지   출처 커뮤니티 느낌 나는 닉네임  (출처 고유 호칭 계열)
🔴 금지   실제 회원 닉네임 · 크롤 author 와 겹치는 닉네임   ← Gate ⑥ 대조
🔴 금지   정확한 나이 · 지역 · 병명 · 가족상태가 드러나는 닉네임
```

작명 상세 정본은 [Pool 설계 §3-2](2026-08-30-persona-pool-design.md).

#### 🔴 어드민에서는 닉네임 뒤가 전부 보여야 한다

고객에게는 닉네임만 보이지만, **어드민에서는 그 닉네임 뒤가 전부 열려야 한다.**

```
displayName  →  personaId · P 코드 · status
                identity · voiceCore · voiceVariations · mood
                memory (Self · Relationship · Community · Negative)
                activityRhythm · noGo
```

🔴 어드민에서 닉네임만 보이고 뒤가 안 보이면 **§10-2 · §10-3 위반**이다.

### §10-8 이번 결정에 포함되지 않은 것

```
🔴 실제 displayName 작명        Gate ⑥ 닉네임 중복 검사 설계 이후
🔴 가입일 · 활동 이력 조작 여부   별도 결정 — 이 문서가 정하지 않는다
🔴 어드민 UI 구현               설계만. 구현 착수는 별도
🔴 DB schema 작성               별도
```

## §11 MVP 방향

### 설계와 활성화를 분리한다

| 항목 | 1차 |
|---|---|
| **Persona Pool 설계** | **20~30명** |
| **초기 활성** | **소수 (3~5명)** |
| 발행 | 🔴 **1단계 — 운영자 승인 또는 shadow mode** (§4-1). 최종 목표는 자동 발행 |
| 활동 | 댓글 + 글 (Persona Network 는 글도 만든다) |
| 대상 | 댓글 0개 글 15건 + 외부 화제 기반 신규 글 |
| 비용 | 생성량이 작아 무시 가능 (VE-M3 전량이 $42 였다) |

### MVP 0단계 — 켜기 전에 측정

```
페르소나 0명으로 기준선 측정
  댓글 0개 글 비율 · 첫 글 재방문 · 7일 재방문 · 두 번째 글 작성률
🔴 이 수치 없이는 효과를 판단할 수 없다
```

### 중단 조건

```
🔴 즉시 중단
   원문 20자 유출 1건 · 개인정보 노출 1건
   회원이 불쾌감 표현 1건 · 의료/법률/재무 단정 조언 1건
   위기 신호 글에 페르소나가 응답
🟡 검토
   운영자 수정률 30% 초과 · Safety Gate 재생성률 50% 초과 · 페르소나 모순 3건
```

## §13 명시적 금지

> 🔴 **2026-09-03 개정.** 아래 금지는 **이 문서를 쓰던 시점(2026-08-29)의 것**이었고,
> 그 뒤 창업자 승인 아래 Persona 구현 · schema 변경 · DB write · 유료 호출이 모두 열렸다.
> **초판 금지를 현행으로 읽으면 이미 있는 기능을 금지된 것으로 오해해 속도가 죽는다.**

### 초판 금지 (2026-08-29) — ✅ 전부 해제됨

```
Persona Bot 구현 · 글 생성 실험 · DB schema 변경 · DB write · 유료 LLM 호출
→ PR #300 ~ #326 으로 승인·구현 완료
```

### 현행 금지 (2026-09-03)

```
🔴 공개 발행 cap 을 정본 개정 없이 코드에서 올리는 것
🔴 topic-role 없이 페르소나 20명을 켜는 것            ← 오배정 4배
🔴 댓글 scaffold 보다 좋아요/베스트를 먼저 여는 것     ← §4-3
🔴 페르소나끼리 대댓글 (1단계)                        ← 아키텍처 §8
🔴 회원 댓글 3개 이상 붙은 글에 페르소나 개입
🔴 위기 신호 글에 페르소나 응답
🔴 --limit=1 · --apply 이중 스위치를 조용히 우회하는 것
🔴 REAL_MEMBER 가드를 방치한 채 페르소나 userId 배정을 자동화하는 것
🔴 발행 cron · 댓글 cron (수집 cron 만 열린다)
🔴 main 직접 push · 창업자 승인 전 merge
```

**금지의 성격이 바뀌었다** — "아직 만들지 마라" 에서 **"순서를 지켜라"** 로.
